Persistence and interface_config

The repository layer manages two concerns:

  1. System data — the efootprint model (serialized via ModelWeb.to_json()).
  2. Interface config — UI-only state (e.g., Sankey diagram settings) stored as a top-level interface_config key in the cached JSON.

Key principle: ModelWeb stays pure efootprint domain — it never sees or touches interface_config. The repository owns it.

  • SessionSystemRepository holds _interface_config in RAM, populated lazily on first read.
  • save_data() merges _interface_config and efootprint_interface_version into the JSON before writing.
  • persist_to_cache() on ModelWeb builds canonical and inputs-only payloads, then passes both to repository.save_data().
  • version_upgrade_handlers.py provides migration infrastructure for interface_config schema changes across versions.

interface_config.simplified_inputs is a JSON-shaped definition with title, guidance, and fields keyed by owner ID then constructor attribute; each setting contains included and authored help, without modeling values or provenance. Both repositories normalize missing/empty definitions to empty title/guidance/fields on config reads, including current-version files that bypass major-version migration. Normalization copies the definition into request-local config without writing stored model payloads. Definition validation checks catalog eligibility and required-selection completeness; reads do not revalidate saved selections.

UpdateSimplifiedDefinitionUseCase(repository, catalog) replaces a complete Configure definition or patches supplied inline field properties against the latest settings. It completes required selections, validates addresses and eligibility, retains authored help on ordinary deselection, and saves through save_interface_config(). An empty replacement field map clears retained help while preserving supplied title/guidance. The caller supplies the catalog; configuration persistence itself never hydrates the model.

Create, edit, and delete use cases require the adapter-supplied catalog factory. Their shared persist_structural_change() reconciles settings against actual surviving owners, completes required selection through the existing configuration use case with persist=False, and saves model and configuration once. Pending creation addresses resolve only after hooks; failed persistence restores request-local configuration. Deletion confirmation runs the same removal operation on a separate inputs-only model without saving, so its warning names selected fields in the actual cascade and excludes surviving shared children. Successful deletion also prunes retained help on removed owners; structural edits preserve membership when a requirement is released.

Backend payloads and computation boundaries

Pull-based contract, efootprint ≥ 23. The library's canonical payload contains inputs, the serialize-flagged computed slots (footprint totals, per-source footprints, impact-repartition matrix, edge breakdown summaries) and a values-free calculation_graph topology section. ModelWeb.to_json(save_computed_state=True) emits that graph (built with the library's calculation_graph_section over flat_efootprint_objs_dict) so that on reload json_to_system — which recomputes nothing — attaches the stored values as trusted caches when the efootprint_version matches exactly (any mismatch demotes them and recomputes lazily on read).

Redis stores this canonical representation for fast request hydration; Postgres stores a second inputs-only recovery representation from to_json(save_computed_state=False), keeping synchronous durable-cache writes small while accepting lazy recomputation after a Redis miss. The shared workspace payload budget and slot-size index continue to measure the canonical Redis representation.

Source hoisting into the top-level Sources block scans both __dict__ inputs and peeked computed slots (computed values live in reactive slots, not __dict__).

ModelWeb.to_json() itself remains passive (descriptor.peek, not pull), but persist_to_cache() first pulls System.total_footprint; this materializes every impact source's aggregate footprint pair so the payload-size guard measures the footprint-bearing steady state immediately after each mutation, while leaving projections such as the Sankey matrix lazy. Creating a Sankey card or changing its settings persists the materialized matrix; rendering a saved card by GET leaves newly computed state request-local.

Explicit user download is the complete-snapshot boundary: ModelWeb.export_json() first calls the library-owned materialize_serialized_state() helper, then serializes, so the downloaded snapshot contains every serialize=True value and the resulting topology regardless of which projections the user visited.

Toolbar exports complete a focused Simplified-input edit before requesting the saved file. A primary mouse press keeps focus in the editor so blur cannot disable the export control before activation. Only the ensuing click starts the save and continuation; an abandoned press never exports. Keyboard activation uses the same settlement check. Direct links and the two-model menu retain the normal single-model/workspace endpoints. A failed autosave blocks the requested modeling(s) until corrected/retried or explicitly discarded using a fresh field-only read. Workspace export also checks failed forms in parked resident models; single-model export checks only the active model. Configure exits use Save/Discard/Stay. A failed Simplified edit also blocks entry into Modeling or Configure until recovered or explicitly discarded, because fresh Simplified entry replaces fields from saved state. Unfinished timeseries and ordinary Modeling panels export their last saved values.

Requests replacing #main-content-block also require recovery of failed edits in every retained model. This covers adding/removing comparison models, file uploads (including rejected imports), reset and the Examples picker. Explicit model removal or reset may discard that model's failed edits through the existing destructive confirmation, which names the unsaved edits; a failed edit in the surviving sibling still blocks the replacement.

The interface_config is included in JSON exports (download) and restored on imports (upload), enabling Sankey settings to survive export/import cycles. Interface-only autosaves use ISystemRepository.save_interface_config(): the session repository patches the existing Redis canonical payload and Postgres inputs-only recovery payload independently, so a UI metadata change does not hydrate, compute, or reserialize ModelWeb and does not collapse the two backend representations into one.

Config and model saves check the shared budget before publishing session fallback settings or backend payloads. The session fallback is keyed by slot and records its System ID, copied config and interface version; recovery reads accept it only for the same System in that slot, and clearing a slot removes only that slot's fallback. If Redis has expired, a config-only save adjusts the indexed canonical size by the recovery payload's metadata-size difference instead of replacing that weight with the smaller inputs-only payload.

Canvas card order

interface_config["card_order"] stores the top-level modeling-canvas order for up-list, uj-list, external-api-list, server-list, edge-device-groups-list, and edge-devices-list. SortableJS reads each card's existing id (web_id) and, after every completed drag, POSTs all six current arrays together to save-card-order; the request is fire-and-forget and a failed save leaves the reordered DOM in place. On every full render, the adapter performs a stable rank merge for each resident model using that slot's repository-owned config: stale IDs are ignored and current objects absent from the saved order are appended in their natural relative order. The explicitly ordered lists are template context, so this interface-only state never enters ModelWeb.

Bounded recovery retention

System-model Redis entries stay hot for one hour; the generic cache policy is separate. The inputs-only Postgres recovery copy uses a session-scoped allowlisted preference (1, 3, 6, or 12 hours, or 1–14 whole days), defaults to 12 hours, and can never exceed the 14-day session-cookie lifetime. A preference change touches only the expiry of each saved slot's Postgres row—never Redis or either payload—and reports each touch independently so a concurrently expired slot does not roll back successful updates or the stored preference. A supervised maintenance command physically removes expired django_cache and django_session rows immediately at container startup and hourly thereafter; concurrent workers are safe because deletion is idempotent, and logs contain aggregate counts/duration only.

Import and re-id snapshots

Import recomputation payloads must be assembled from efootprint.api_utils.system_to_json.system_to_json() fragments (the connected System plus any orphaned objects) rather than hand-serializing objects in the interface. Import and workspace re-id are explicit complete-snapshot boundaries: they call materialize_serialized_state() before passive serialization; hydration itself never calls construction-time after_init() hooks. This keeps object serialization and top-level Sources hoisting owned by e-footprint and prevents dangling source references after calculated attributes are recomputed.

A rejected single-model upload renders saved state through a fresh repository. Its attempted configuration remains request-local, so Postgres recovery during error rendering cannot persist that configuration onto the old model.

Security and data

  • Model access is session-scoped; payloads are stored server-side in Redis and Postgres under the retention policy above. This is not browser-only storage. No PII is expected; do not log sensitive information.
  • Validate transport shape/types at adapter boundaries. Semantic modeling invariants belong to the domain/library; browser checks provide immediate feedback only. Deployment-specific data/privacy copy lives in model_builder/templates/model_builder/side_panels/data_privacy.html.
