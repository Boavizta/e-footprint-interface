Request lifecycle simplification

Status: Spec — under review · 2026-10-19 · Interface-owned

1. Problem and audience

The browser code behind Simplified inputs, and several older widgets, follow each HTTP request by hand through four HTMX lifecycle events to learn when it finished and whether it succeeded. This tracking exists because HTMX reports a response as complete about twenty milliseconds before it marks the swapped DOM as settled, and because the field editors are replaced by their own save response. The resulting state machines are correct but hard to review, duplicated per interaction, and they grow with every new flow. The 14 October save-lock feature removed the global write guard but left this per-request tracking in place.

  • Who: maintainers and agents reviewing or extending the interface. End users are affected only through the small behaviour trades listed below.
  • Why now: Simplified inputs is under review, the tracking pattern is spreading into new modules, and the project's HTMX-first rule (constitution §1.4) favours server-rendered state over client coordination.
  • Tradeoff: a few rare edge behaviours are deliberately simplified in exchange for removing most request coordination. Saves are expected to be short and editing sequential; this is the same unmeasured assumption the save-lock feature recorded.

2. Success criteria

User-observable outcomes stay as they are unless listed under "accepted changes". Each criterion is testable in Jest or Playwright.

Preserved behaviour

  • A Simplified-input value or provenance edit shows Saving…, sends one request, and then shows Saved with the accepted value, or Not saved with the accepted value restored when the server rejects it. In every case the locked controls become usable again and prerequisite-disabled controls stay disabled.
  • Changing a bookmark's membership or help updates every visible bookmark for the affected field and its companions, and shows Saved or Not saved.
  • Leaving a dirty Configure screen offers Save, Discard and Stay. Save and Discard show the saved view; a rejected save leaves the draft visible. Stay keeps the draft. The navigation that opened the dialog is not resumed in any case: the user repeats it.
  • Switching models, Results, Compare, exports and the Results panel keep their current rules, including the save-aware export boundary.
  • Jest, Python and E2E suites pass.

Accepted changes

  • Entering Simplified inputs, Configure or Discard switches the view at once; the slot shows its previous content, or nothing on first entry, dimmed behind a loader with every button and workspace control locked until the fresh read lands, exactly as during a save. A second read cannot start while one is in flight, and a model switch waits for it (amended 2026-10-20, PLAN-UPDATE-13; it previously let the user act on the stale content and let a late read land after a model switch). A dirty Configure draft keeps Save, Discard and Stay gating on every exit, including model switches.
  • A help text whose save failed is replaced by the next successful bookmark response for that field instead of being preserved as a draft.
  • The Saved text fades after a few seconds through a style rule rather than a timer.
  • An invalid draft (empty required value, out-of-range number) is refused before any request with the browser's own validation message instead of a scripted Not saved.
  • A changed Simplified value keeps the confidence the user set; today it is reset to none. The saved confidence is the one the user sees, and they can lower it themselves.
  • Switching models still restores each model's last view. After an action that rebuilds the whole builder (duplicate, start blank, import or remove a model), each model opens in its default view: Simplified inputs for a just-opened file with selected inputs, otherwise Modeling.
  • Rare edges are accepted rather than scripted around: a control already locked by another request is released when that request ends, a moment before a field save finishes; closing Results during a Sankey load may log one chart warning; a read answered by a server error leaves its slot empty or stale, visibly, so the error gets reported and fixed.
  • A request that gets no response (connection lost, timeout) leaves the field or bookmark status empty once the request ends, instead of showing Not saved. The server renders every outcome it knows; reporting an unanswered request is the shared concern parked in network-interruption-message.
  • No exit resumes the navigation it interrupted. Today Save and Discard continue to the destination the user had clicked once the saved view is in place; after this feature they only show the saved view, and the user clicks the destination again. A clean Configure screen is no longer replaced by the saved view before an exit, so a model switch leaves it in its slot and shows it again on return.
  • The bookmark Undo button is removed. It sat beside the membership toggle it reverted, so re-clicking the toggle does the same job without an inverse patch travelling with every response.
  • Both Results close controls are unavailable while a save runs. On touch devices, a swipe-down during a save still closes the panel, and a late refresh may re-fill it; the user closes it again.

Maintainability outcomes

  • No feature module stores request objects or listens to swap or settle events to sequence its own request. Completion is observed through one signal, and post-request state is whatever the server rendered.
  • The conventions document states this rule as an explicit prohibition, not a preference: feature code must not coordinate swap or settle ordering, must not keep client copies of server-owned state, and follows the HTMX philosophy that the server is the source of truth and the rendered fragment is the state. It also states that server failures are shown, not softened: no client state, listener or fallback exists only to hide a hypothetical failure or to order concurrent requests. The architecture and testing pages say the same where they describe request handling, and no longer present settle ordering as something feature code coordinates.
  • Jest tests for Simplified inputs assert visible outcomes, not event sequences.

3. Scope

Capability-level only. File paths, class/method/parameter names, refactor instructions, internal hypotheses, and "mirror pattern X" code-level decisions belong in plan.html, not here.
In scope
  • One platform setting so that HTMX finishes swapping and settling before it reports a request complete. This applies to the whole interface.
  • Simplified-input field saves: the server renders the post-save field, including its status text; the browser keeps no copy of saved values and no request bookkeeping.
  • Bookmark membership and help saves: the server answers with rendered bookmark fragments for every affected field instead of data the browser reconciles by hand.
  • Saved-view reads and Configure exits lock the interface like every save and use HTMX's completion signal; no request replacement, queue or cancellation rule exists (PLAN-UPDATE-13).
  • Locked controls during a field save exclude controls that were already disabled, removing the restore step after HTMX releases the lock.
  • The Results panel close no longer waits for in-flight recomputations. Its chevron becomes a button so the existing save lock disables it, like the close button, while a save runs.
  • A conventions rule for request handling in feature JavaScript, with the owning architecture and testing pages updated to match.
  • Rewritten Jest coverage for Simplified inputs and adjusted E2E probes.
Out of scope (this iteration)
  • The side-panel unsaved-changes guards, source-metadata autosave, timeseries preview abort, Sankey and card-order fetches, model comparison and tour hooks. Each already follows a small local pattern; the new convention governs them when they are next touched. The source-metadata, timeseries-preview and side-panel replay items are surveyed in the server-rendered-state follow-up note.
  • A central request hub or shared lifecycle helper. After this feature there is no shared tracking left to centralise.
  • Server-side persistence, validation, repair notices and export rules.
  • Any change to what Simplified inputs can edit or configure.

5. Constraints

  • Constitution §1.4, HTMX-first and minimal JS, and the mission's leanness priority; this feature is their application to request handling.
  • Owning pages: Rendering, Workspace and testing.md describe settlement and export timing today and must be reconciled.
  • The 14 October save-lock spec remains valid; this feature keeps its locking and export rules and removes only the client bookkeeping around them.
  • No change to the HTMX version or to other vendored libraries.

6. Open questions

None remaining. Ten questions were resolved on 2026-10-19 and are recorded above as accepted changes:

  • The Results panel close keeps no wait. The chevron becomes a button so the existing save lock covers it; the touch swipe remains an accepted edge case.
  • A help draft whose save failed is overwritten by the next successful bookmark response. The failure was already reported, and preserving the draft would reintroduce client-side reconciliation inside a swap.
  • Bookmark Undo is removed during plan review (PLAN-UPDATE-01): the toggle next to it already reverts the change, and dropping it removes the inverse-patch computation and its request flag.
  • No client-side "Not saved" fallback for unanswered requests (PLAN-UPDATE-04): it would duplicate the parked shared network message for one feature, and the server already answers every other failure.
  • Exits do not resume the interrupted navigation (PLAN-UPDATE-05). Guards block and the user repeats the action; the rule is recorded in the mission's eco-design section so later features follow it.
  • Server failures are visible, not softened (PLAN-UPDATE-06): a conventions rule; the field editor is declarative and field_edits.js is removed (PLAN-UPDATE-07); entering a view switches on click, not on arrival (PLAN-UPDATE-08).
  • A changed value keeps its confidence (PLAN-UPDATE-10 rejected): the server does not reset what the user set.
  • The remembered view lives on each model's slot (PLAN-UPDATE-12), so a builder rebuild resets it instead of a hook re-fetching emptied slots.
