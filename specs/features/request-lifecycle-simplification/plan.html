Request lifecycle simplification — implementation plan

Spec under review · Changed files

Draft. This plan captures design decisions reached while analysing the current code during the kickoff conversation, including facts verified against the vendored HTMX 2.0.6. It is refined, not rewritten, in the spec-plan stage after the spec is approved.

1. Follow the interactions through the code

Proposed changes, not implemented code. Paths are relative to e-footprint-interface/.

1.1 · Platform: one completion signal

Files theme/templates/base.html · specs/conventions.md · specs/architecture/rendering.html · specs/testing.md

Today HTMX fires htmx:afterRequest as soon as the response handler returns, but defers htmx:afterSettle by its default defaultSettleDelay of 20 ms. Verified in the vendored htmx.min.js (2.0.6): when the settle delay is zero, the settle step runs synchronously inside the swap, so the order becomes beforeSwap, afterSwap, afterSettle, afterRequest, then resolution of the htmx.ajax promise. That promise resolves after the response is handled for any HTTP status and rejects only on network error, abort or timeout. No project SCSS or template uses the htmx-settling or htmx-added classes that the delay exists to animate.

theme/templates/base.html Proposed, next to the HTMX script tag on line 14

<meta name="htmx-config" content='{"defaultSettleDelay": 0}'>

Every later section relies on this: htmx:afterRequest on an element now means its DOM result is final, including out-of-band fragments carried by the same response, and the HX-Trigger-After-Settle header fires before it.

The rule promoted to conventions.md under JavaScript, replacing the "listener order is part of mutation settlement" clause on line 26:

The server is the source of truth; the rendered fragment is the state. Feature JavaScript must not coordinate swap or settle ordering, must not store request objects, and must not keep client copies of server-owned state such as saved values, membership, locks or undo history. HTMX settles synchronously in this project, so htmx:afterRequest on an element means its DOM result is final. Observe completion through that event with event.detail.successful, or through the htmx.ajax promise, and nothing else. Status text, locks and undo affordances are rendered by the server. Client state is limited to drafts not yet submitted, ephemeral view state the server cannot know, and per-browser preferences. Global re-initialisation hooks on htmx:afterSettle for third-party widgets remain allowed; sequencing a feature's own request is not.

The architecture pages carry the same statement where they describe request handling, not only the removal of the old caveats: rendering.html replaces the bundle-order caveat with a short paragraph naming the synchronous settle configuration and the rule above, workspace.html states that Simplified-input state after any request is the server fragment, and testing.md rewords the export-timing hold around the single signal and tells test authors to assert rendered outcomes rather than dispatch synthetic lifecycle sequences. Unchanged consumers: the loading bar, the modal htmx:beforeSwap handler that lets error responses swap their out-of-band modal, and the accordion-state preservation in model_builder_main.js.

1.2 · Field value or provenance save

Files simplified_inputs/editor.html · simplified_inputs/field.html · field_edits.js · presenters/simplified_inputs.py · views_simplified_inputs.py · model_builder_main.js · scss/custom.scss

Trigger and lock. Blur, Enter, select change and provenance events still call saveEdit(), which triggers the form's simplified-save event. Its unchanged-blur guard no longer compares against the savedEdits snapshot: an input or change listener sets data-dirty on the control and on the form, and saveEdit() returns when the form is not dirty. The lock selector on editor.html excludes controls that are already disabled, so HTMX never has to be corrected afterwards:

simplified_inputs/editor.html Proposed lock selector

hx-disabled-elt="button:not(:disabled), [data-simplified-workspace] input:not(:disabled),
                [data-simplified-workspace] select:not(:disabled), [data-simplified-workspace] textarea:not(:disabled)"

HTMX resolves this attribute with a standard querySelectorAll and reference-counts overlapping requests before releasing, so the snapshot-and-restore block at model_builder_main.js line 361 is removed, together with the [data-disabled-by-htmx] checks inside saveEdit() and initializeEdits().

Payload. The htmx:configRequest listener at line 96 keeps its two jobs, trimming untouched provenance parameters and preserving multiple-select lists, but decides "untouched" from the control's data-dirty flag rather than from the snapshot. The source-metadata:value-changed event is dispatched when the value control is dirty.

Response. present_edited_input() and _rejected_simplified_input() both already answer with out-of-band field fragments through render_input_fields_oob(). They pass an extra outcome of saved or rejected, and field.html renders the status text into the fragment; the hx-preserve on the status span at line 39 is dropped because the span now arrives with its content.

simplified_inputs/editor.html Proposed status span; UI copy, not existing code

<span class="small" data-simplified-save-status data-outcome="{{ outcome }}" role="status">
  {% if outcome == "saved" %}Saved{% elif outcome == "rejected" %}Not saved{% endif %}
</span>

A rule in custom.scss fades [data-outcome="saved"] after three seconds; the saveStatusTimers map disappears with it. The "Saving…" text is set by the existing saveEdit() at trigger time, and the fragment replacement clears it.

Completion. The saves map, finishSave(), and the four listeners from line 116 to line 133 are removed. Two listeners remain: htmx:sendError on a [data-simplified-editor] element writes "Not saved" and clears its data-saving flag, and the existing simplifiedInputSaved notice handler. Timeseries panel closure moves to an htmx:afterRequest check of event.detail.successful on [data-simplified-timeseries].

Totals. setTotalsBusy() is replaced by hx-indicator="[data-quick-total]" on the editor form and a style rule that renders "Updating…" into [data-quick-total-status] while its total carries the htmx-request class.

1.3 · Bookmark membership and help

Files bookmarks.js · simplified_inputs/bookmark_controls.html · views_simplified_inputs.py · presenters/simplified_inputs.py

Today patch_simplified_inputs() returns JSON listing every affected address with its setting, required-by label and an inverse patch, and the htmx:afterRequest handler at line 129 walks all visible bookmarks to apply it through updateBookmark(), while protecting a dirty help draft and toggling Undo. The server already computes the affected set with the same catalog it would use to render HTML.

Proposed. The view renders one out-of-band bookmark_controls.html fragment per affected address, targeting the existing {{ field.dom_id }}-controls container, plus an out-of-band update of the bookmark's summary icon and labels. The fragment carries the status text ("Saved") and, for the bookmark that issued the request, the Undo button with its inverse patch in data-inverse-patch and hidden removed only when the inverse is non-empty. Bookmarks whose controls are still lazy, that is not yet fetched, receive only the summary update. The 422 path keeps its modal and the response still swaps nothing else, so the status shows "Not saved" through the same htmx:sendError-style fallback as fields: an htmx:afterRequest listener on [data-bookmark] writing "Not saved" when event.detail.successful is false.

Removed from bookmarks.js: the afterRequest reconciler, updateBookmark() for saved bookmarks, the "Saving…" htmx:beforeRequest at line 170 (replaced by hx-indicator on the status element), and the refreshBookmarkLocks settle hooks at line 164, since fragments arrive with the correct disabled state. Kept: saveBookmark() stashing the patch, the htmx:configRequest at line 121, and the creation-time provisional logic, which is purely client-side authoring and has no request lifecycle.

Accepted trade (decision 2, decided 2026-10-19): a help text whose save failed is overwritten by the next successful fragment for the same field. The textarea is part of the replaced fragment; no draft check runs inside the swap.

1.4 · Saved-view reads and Configure exits

Files workspace.js · model_builder_main.html · specs/architecture/workspace.html

Reads. loadView() registers five listeners per call to tie the continuation to its own XHR, abort on competing navigation and refuse a swap when the active slot changed. It becomes a promise chain, and the slot target in model_builder_main.html declares hx-sync="this:replace" so a repeated read aborts the pending one natively (the source option makes the target the issuing element, where HTMX reads hx-sync).

scripts/simplified_inputs/workspace.js Proposed replacement for loadView

function loadView(configure, then) {
    const target = targetForActiveModel();
    if (!target) return;
    window.runAfterSidePanelDiscardConfirmation(() => {
        window.htmx.ajax("GET", `/model_builder/simplified-inputs/${configure ? "?configure=1" : ""}`,
            { source: target, target, swap: "innerHTML" }).then(() => {
            if (target !== targetForActiveModel()) {
                // Configure is never parked: a read that lands after a model switch is discarded.
                if (configure) target.innerHTML = "";
                return;
            }
            window.closeAndEmptySidePanel();
            setBaseView("simplified");
            if (then) then();
        });
    });
}

The rejection path (network error or abort) does nothing. A late saved-view response renders into its own hidden slot and is simply the correct content when the user returns. A late Configure response is discarded in the same branch, so Configure is never resumed in a hidden slot and the remembered "simplified" mode reloads the saved view on the next visit through initialize(), which is unchanged. No draft can exist at that point because the form had not rendered; a dirty Configure draft still gates every exit, including model switches, through the unchanged capture click interception and htmx:confirm handler described below. pendingRead, cancelPendingRead() and the cancellation branches inside the capture click handler and the htmx:beforeRequest listener at line 179 are removed.

Configure Save then continue. savingRequest and finishConfigureSave() with their four listeners (lines 179 to 193) collapse to one:

scripts/simplified_inputs/workspace.js Proposed single completion listener

document.addEventListener("htmx:afterRequest", event => {
    if (!event.detail.elt.matches("[data-configure-form]")) return;
    const action = pendingExit;
    pendingExit = null;
    if (event.detail.successful && action) action();
});

With synchronous settle the replacement workspace is already in place when this fires, so a continuation such as a replayed click or issueRequest(true) runs against final DOM. A rejected save (422 modal) leaves the draft and clears the pending exit, matching today's behaviour. The dialog, deferExit(), the capture click interception and the htmx:confirm interception stay as they are; they are navigation gating, not request tracking.

workspace.html replaces the paragraphs on pending reads, actually issued XHRs and parked Configure with the accepted rule from the spec.

1.5 · Results panel close

Files hammer_utils.js

hidePanelResult() keeps the panel attached while a recomputation-bearing request is in flight so a late out-of-band Results refresh has a target. It tracks those XHRs in pendingResultRefreshes and waits on both htmx:afterRequest and htmx:afterSettle in finishClosing(), also matching .htmx-settling and .htmx-added in hasPendingResponse().

The wait is only reachable mid-request through controls that the save locks do not cover. The close button at result_panel.html line 87 is a real button and is already disabled by every form declaring hx-disabled-elt="button", which includes field saves and side-panel object saves. The chevron at line 8 is a div with an onclick, so it stays clickable during a save. The programmatic closes from the delete_card_modal.html and modal_template.html scripts run when a modal opens, at a request boundary rather than mid-request.

Proposed (decision 1, decided 2026-10-19). The chevron becomes a <button type="button"> with the same onclick and icon, so the existing lock disables it during every recomputation-bearing save. hidePanelResult() then drops pendingResultRefreshes, its two listeners, hasPendingResponse() and finishClosing(), and always resets the layout and empties the panel at once. The only remaining mid-request close is the touch swipe-down gesture in initHammer(); a late refresh after a swipe re-fills the Results block, and the user closes it again. Mobile is best-effort by mission, so this is accepted. The htmx:afterSettle listener at line 38, which re-applies the open-panel layout after any swap, stays: it is a global re-initialisation hook, not request tracking.

3. Decisions

  1. Results close wait — decided 2026-10-19: remove the wait, make the chevron a button. Field and side-panel saves already disable every button; converting the chevron puts the last clickable close path under that lock. The swipe gesture remains as an accepted mobile edge case. See 1.5.
  2. Failed help draft — decided 2026-10-19: accept the overwrite. Preserving the draft would need a dirty check inside the swap, which is the kind of coordination this feature removes, and the exception modal has already reported the failure. See 1.3.
  3. Scope of the convention — for review. Older modules listed as out of scope in the spec keep their patterns until touched. Recommendation: no boy-scout migration inside this feature, to keep the diff reviewable.
