# Sankey aggregation threshold persistence: broad persistence works, but zero and immediate-close paths lose the displayed value

- **Status:** CONFIRMED
- **Confidence:** high — the normal, zero-value, and immediate-close paths were reproduced against the local application; focused repository/view tests also pass and isolate the remaining gaps.
- **Reported:** “Agregation threshold in Sankey graph should be saved when closing the Results tab (actually I think it is I just tried in production and it worked, but there’s an open issue from a coworker so double check).” The broad hypothesis is outdated: ordinary non-zero changes do survive a Results close/reopen. Two narrower versions remain true: `0%` is persisted but rendered back as `1%`, and a change followed by a close inside the 300 ms debounce window is never submitted.

## Root cause

The durable persistence path itself is sound. The Sankey form POSTs every render/update to `sankey-diagram/`; the backend parses `aggregation_threshold_percent` as a float, places it in the per-card settings, updates `repository.interface_config["sankey_diagrams"]`, and calls `model_web.persist_to_cache()` (`e-footprint-interface/model_builder/templates/model_builder/result/sankey_card.html:20`, `e-footprint-interface/model_builder/templates/model_builder/result/sankey_card.html:22`, `e-footprint-interface/model_builder/adapters/views/sankey_views.py:318`, `e-footprint-interface/model_builder/adapters/views/sankey_views.py:330`, `e-footprint-interface/model_builder/adapters/views/sankey_views.py:377`, `e-footprint-interface/model_builder/adapters/views/sankey_views.py:386`, `e-footprint-interface/model_builder/adapters/views/sankey_views.py:393`). `persist_to_cache()` serializes canonical and recovery payloads through the repository (`e-footprint-interface/model_builder/domain/entities/web_core/model_web.py:187`, `e-footprint-interface/model_builder/domain/entities/web_core/model_web.py:203`, `e-footprint-interface/model_builder/domain/entities/web_core/model_web.py:206`); `SessionSystemRepository.save_data()` merges the in-memory config into both payloads and also writes a Django-session fallback (`e-footprint-interface/model_builder/adapters/repositories/session_system_repository.py:151`, `e-footprint-interface/model_builder/adapters/repositories/session_system_repository.py:172`, `e-footprint-interface/model_builder/adapters/repositories/session_system_repository.py:184`, `e-footprint-interface/model_builder/adapters/repositories/session_system_repository.py:189`). This layering matches the repository-owned `interface_config` invariant rather than putting UI state in `ModelWeb` (`e-footprint-interface/specs/constitution.md:11`, `e-footprint-interface/specs/architecture.md:188`).

On reopen, both Results entry points GET `result-chart/` into the same resident `#result-block` (`e-footprint-interface/model_builder/templates/model_builder/components/results_bar_button.html:4`, `e-footprint-interface/model_builder/templates/model_builder/components/results_bar_button.html:6`, `e-footprint-interface/model_builder/templates/model_builder/components/results_bar_button.html:7`, `e-footprint-interface/model_builder/templates/model_builder/components/show_results_toolbar_button.html:4`, `e-footprint-interface/model_builder/templates/model_builder/components/show_results_toolbar_button.html:6`, `e-footprint-interface/model_builder/templates/model_builder/components/show_results_toolbar_button.html:7`). The returned Results panel includes the Sankey section (`e-footprint-interface/model_builder/templates/model_builder/result/result_panel.html:94`, `e-footprint-interface/model_builder/templates/model_builder/result/result_panel.html:96`), whose load trigger GETs `sankey-cards/` (`e-footprint-interface/model_builder/templates/model_builder/result/sankey_section.html:28`, `e-footprint-interface/model_builder/templates/model_builder/result/sankey_section.html:29`, `e-footprint-interface/model_builder/templates/model_builder/result/sankey_section.html:30`). That endpoint reads the active repository's saved `sankey_diagrams` and supplies each record as `initial_settings` (`e-footprint-interface/model_builder/adapters/views/sankey_views.py:444`, `e-footprint-interface/model_builder/adapters/views/sankey_views.py:447`, `e-footprint-interface/model_builder/adapters/views/sankey_views.py:456`, `e-footprint-interface/model_builder/adapters/views/sankey_views.py:474`). With no saved diagrams it deliberately creates one default card (`e-footprint-interface/model_builder/adapters/views/sankey_views.py:449`, `e-footprint-interface/model_builder/adapters/views/sankey_views.py:450`), and both backend parsing and the control use `1%` as the new-card default (`e-footprint-interface/model_builder/adapters/views/sankey_views.py:330`, `e-footprint-interface/model_builder/templates/model_builder/result/sankey_card.html:52`).

Manual Results close is client-only. Desktop and mobile controls call the same `hidePanelResult()` (`e-footprint-interface/model_builder/templates/model_builder/result/result_panel.html:8`, `e-footprint-interface/model_builder/templates/model_builder/result/result_panel.html:87`); swipe-down does too (`e-footprint-interface/theme/static/scripts/hammer_utils.js:60`, `e-footprint-interface/theme/static/scripts/hammer_utils.js:66`). That function empties `#result-block` without making a persistence request (`e-footprint-interface/theme/static/scripts/hammer_utils.js:36`, `e-footprint-interface/theme/static/scripts/hammer_utils.js:40`, `e-footprint-interface/theme/static/scripts/hammer_utils.js:43`). Model switching uses the same close function when Results contains content (`e-footprint-interface/theme/static/scripts/model_comparison.js:185`, `e-footprint-interface/theme/static/scripts/model_comparison.js:197`, `e-footprint-interface/theme/static/scripts/model_comparison.js:199`), and import/error-modal paths also call it (`e-footprint-interface/model_builder/templates/model_builder/side_panels/add_model_import.html:27`, `e-footprint-interface/model_builder/templates/model_builder/side_panels/import_model.html:27`, `e-footprint-interface/model_builder/templates/model_builder/modals/modal_template.html:30`). Opening Compare is a different path: it hides the resident builder rather than closing Results, so its in-DOM transient state survives until the user returns; the architecture documents that intentional behavior (`e-footprint-interface/specs/architecture.md:233`).

Two UI mechanisms cause the remaining defects:

1. The restored slider binds `initial_settings.aggregation_threshold_percent|default:"1"` (`e-footprint-interface/model_builder/templates/model_builder/result/sankey_card.html:52`, `e-footprint-interface/model_builder/templates/model_builder/result/sankey_card.html:53`, `e-footprint-interface/model_builder/templates/model_builder/result/sankey_card.html:56`). Django's `default` filter replaces false-like values, so the valid persisted float `0.0` is displayed as `1`; subsequent form load then POSTs `1` and overwrites the previously saved zero. Local reproduction: set `0`, allow the Sankey update to complete, close Results, reopen; the control was `1`.
2. Every `change` and range `input` is delayed 300 ms (`e-footprint-interface/model_builder/templates/model_builder/result/sankey_card.html:26`). Closing removes the form at once (`e-footprint-interface/theme/static/scripts/hammer_utils.js:43`). The vendored HTMX trigger schedules delayed work and its request path refuses to issue when the source is no longer attached (`e-footprint-interface/theme/static/scripts/external_librairies/htmx.min.js:1`). Local reproduction: a saved `4.5` reopened correctly; changing it to `7` and closing in 288 ms reopened at `4.5`, proving the final value never reached the endpoint. Closing after waiting for the update reopened at `4.5`, matching the user's successful production check.

The broad issue appears to have already been fixed: git history shows `[ADD] Sankey persistence feature.` (`f666dd4c`, 2026-03-24), followed by `[ADD] session fallback for sankey config persistence.` (`e9227bf7`, 2026-03-24). Current code and tests embody those fixes. The still-open coworker issue may predate them, or it may describe one of the two boundary cases above.

## Fix approach

Keep the existing repository and endpoint design. Make the restored-value fallback distinguish “no saved settings” from the valid numeric zero; an explicit template branch (`initial_settings` present → render its threshold, absent → render `1`) is safer than another truthiness-based filter.

Make the final `change` event immediate while retaining debounced range `input` updates during dragging. For example, separate the triggers so `change` has no delay and `input from:find input[type=range]` keeps `delay:300ms`; the release event then starts the final POST before a subsequent close can detach the form. This is smaller and more reliable than teaching every close path to flush UI state, and it also covers desktop, mobile, swipe, model switch, import, and modal-driven closes through the existing shared behavior. Preserve `hx-sync="this:replace"` so the final change supersedes any in-flight preview request (`e-footprint-interface/model_builder/templates/model_builder/result/sankey_card.html:25`).

Do not add a close-time persistence endpoint or move `interface_config` into `ModelWeb`; those duplicate an already-correct save path and would violate the documented ownership boundary (`e-footprint-interface/specs/constitution.md:11`, `e-footprint-interface/specs/architecture.md:188`).

## Acceptance criteria

- A saved non-zero threshold still survives closing and reopening Results.
- A saved `0%` threshold reopens as `0%` and is not overwritten by the default.
- Changing the threshold and immediately closing Results preserves the released value on reopen across desktop/mobile close controls and any other path using `hidePanelResult()`.
- New cards still start at the documented `1%` default.
- Sankey settings remain in `repository.interface_config["sankey_diagrams"]`; no new persistence mechanism is introduced.

## Risks and side effects

- Making `change` immediate increases at most one final calculation request per completed interaction; the debounced `input` remains for drag previews, and `hx-sync="this:replace"` prevents stale same-form responses from winning (`e-footprint-interface/model_builder/templates/model_builder/result/sankey_card.html:25`, `e-footprint-interface/model_builder/templates/model_builder/result/sankey_card.html:26`).
- The fix affects all Sankey controls covered by the generic `change` trigger, not just the range. If request cost is a concern, scope the immediate trigger to the threshold range and leave other changes at their current delay; the acceptance test should then prove the close race specifically for the range.
- A Sankey build that raises the handled computation-memory limit does not save settings because persistence occurs only after a successful build (`e-footprint-interface/model_builder/adapters/views/sankey_views.py:345`, `e-footprint-interface/model_builder/adapters/views/sankey_views.py:393`, `e-footprint-interface/model_builder/adapters/views/sankey_views.py:409`). Existing tests explicitly expect no saved diagram in that case (`e-footprint-interface/tests/unit_tests/adapters/views/test_sankey_views.py:333`, `e-footprint-interface/tests/unit_tests/adapters/views/test_sankey_views.py:362`). That is adjacent intentional behavior, not this report.
