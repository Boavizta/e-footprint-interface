# Replace catalog datalists with closed-choice selects

- **Status:** CONFIRMED
- **Confidence:** high — every production datalist is generated from a closed library catalog, the library rejects off-catalog values, and the existing form/JS stack already supports native dynamic selects.
- **Reported:** Replace datalists with “lists,” notably EcoLogits external-API model names and Boavizta cloud instance types. This is a small interface simplification, not a defect. In current project terminology, the most likely target is an HTML `<select>` dropdown: static `list_values` already render through the native select template, whereas only `conditional_list_values` render as datalists (`e-footprint-interface/model_builder/adapters/forms/form_field_generator.py:331-378`; `e-footprint-interface/model_builder/templates/model_builder/side_panels/dynamic_form_fields/select_str_input.html:1-13`). If “list” instead means an always-open listbox or a searchable combobox, see **Decision fork**.

## Finding

The change is valid and well scoped. The UI currently treats two equivalent closed-choice concepts differently: an attribute in `list_values` becomes `select_str_input`, while an attribute in `conditional_list_values` becomes a text `<input list=...>` plus `<datalist>` and a `dynamic_lists` cascade (`e-footprint-interface/model_builder/adapters/forms/form_field_generator.py:331-378`; `e-footprint-interface/model_builder/templates/model_builder/side_panels/dynamic_form_fields/datalist.html:1-20`). The split exists for presentation, not domain semantics.

Free-text entry is incidental, not an intended escape hatch. EcoLogits tells users to pick provider and model from its catalog (`e-footprint/efootprint/builders/external_apis/ecologits/ecologits_external_api.py:47-60`), and its model list is constructed per provider from `ModelRepository` (`e-footprint/efootprint/builders/external_apis/ecologits/ecologits_external_api.py:65-82`). Video models and job resolutions are likewise generated from the bundled EcoLogits model capabilities (`e-footprint/efootprint/builders/external_apis/ecologits/ecologits_video_external_api.py:91-109`, `e-footprint/efootprint/builders/external_apis/ecologits/ecologits_video_external_api.py:175-191`). Boavizta explicitly treats providers and instance types as bundled snapshot enums and states that newly added upstream values do not validate until the snapshot is refreshed (`e-footprint/efootprint/builders/hardware/boavizta_cloud_server.py:22-38`). At assignment, `ModelingObject.check_belonging_to_authorized_values()` rejects a conditional child outside the values for its resolved parent, including dotted cross-object parents (`e-footprint/efootprint/abstract_modeling_classes/modeling_object.py:312-353`). The focused Boavizta test confirms a free-typed invalid instance raises `ValueError` (`e-footprint/tests/builders/hardware/test_boavizta_cloud_server.py:37-53`), and the generic dotted-path tests confirm invalid child values are rejected for both direct and cross-object dependencies (`e-footprint/tests/abstract_modeling_classes/test_modeling_object.py:395-415`). A select therefore exposes the actual contract earlier and prevents submissions the backend cannot accept.

## Smallest implementation direction

Render conditional catalog fields through the existing `select_str_input.html` template instead of `datalist.html`, while retaining the current `dynamic_lists` payload shape and dependency resolution. In `dynamic_forms.js`, point each `dynamic_lists` entry at `dynamicList.input_id` (the `<select>`) instead of `datalist_` + id, populate string items as normal `<option value="...">...</option>` elements, restore `data-default-value` during initial hydration/edit, and continue clearing the child selection when its parent changes. The existing reusable updater already handles `<select>` option replacement and value preservation for the separate object/type cascades (`e-footprint-interface/theme/static/scripts/dynamic_forms.js:78-140`, `e-footprint-interface/theme/static/scripts/dynamic_forms.js:143-177`). It can be simplified to normalize either string options or `{label, value}` options once, eliminating the `type === "datalist"` branch and the datalist-specific target-id convention without changing the backend dependency map.

Keeping `dynamic_lists` as the internal name is the smallest patch because it is threaded through creation and edition contexts (`e-footprint-interface/model_builder/adapters/forms/form_field_generator.py:126-162`; `e-footprint-interface/model_builder/adapters/forms/strategies/simple.py:110-127`; `e-footprint-interface/model_builder/adapters/forms/strategies/with_storage.py:89-118`) and is distinct from the object/type `dynamic_selects` payload built by parent-selection strategies (`e-footprint-interface/model_builder/adapters/forms/strategies/parent_selection.py:66-95`, `e-footprint-interface/model_builder/adapters/forms/strategies/parent_selection.py:131-186`). Renaming/merging those schemas can be done, but is unnecessary churn for this mini-feature. `datalist.html` can be deleted after the generator stops emitting `input_type: "datalist"`.

No form parser or persistence shape change is needed. A native select submits the same field name and string value. `parse_form_data()` already wraps any `ExplainableObject` value as `{"value": value, "label": "no label"}` and separately folds the five metadata suffixes into that same attribute (`e-footprint-interface/model_builder/adapters/forms/form_data_parser.py:140-180`, `e-footprint-interface/model_builder/adapters/forms/form_data_parser.py:205-220`). Creation and editing rebuild the `ExplainableObject` and apply source, confidence, and comment metadata independently of the input widget (`e-footprint-interface/model_builder/domain/object_factory.py:43-93`, `e-footprint-interface/model_builder/domain/object_factory.py:124-153`, `e-footprint-interface/model_builder/domain/object_factory.py:226-247`). The common dynamic-field wrapper also renders those metadata controls based on the field metadata, not its input type (`e-footprint-interface/model_builder/templates/model_builder/side_panels/dynamic_form_fields/dynamic_form_field.html:1-13`). Consequently `SourceObject` value and metadata round-trip unchanged; add a focused regression, but do not change parser/factory code.

## Risks and side effects

- Native selects remove arbitrary typing and browser datalist autocomplete. That is correct for validity, but the GenAI model catalog is long; scanning a native dropdown may be less convenient than typing to filter. If searchability is required, use a closed-choice combobox rather than retaining free text.
- Initial hydration must restore `data-default-value`; otherwise an empty server-rendered select will silently choose its first dynamic option and change imported/edited data. The current select template already exposes that default (`e-footprint-interface/model_builder/templates/model_builder/side_panels/dynamic_form_fields/select_str_input.html:1-7`).
- Parent changes must leave the child genuinely unselected when the old value is invalid. Automatically taking the first new option would be a behavior change from the current cascade, which explicitly clears the child (`e-footprint-interface/theme/static/scripts/dynamic_forms.js:151-157`).
- Cross-object resolution depends on option values remaining external-API ids rather than labels; the generator and integration test pin that invariant (`e-footprint-interface/model_builder/adapters/forms/form_field_generator.py:351-377`; `e-footprint-interface/tests/integration/test_ecologits_video.py:182-194`).
- No JSON/schema migration, library release, API change, or cross-repository ordering is involved. This only changes interface form rendering; submitted values and the e-footprint validation contract remain identical.

## Decision fork

- **Recommended interpretation:** “lists” means native single-choice `<select>` dropdowns. Proceed with the scoped simplification above; it matches the existing `list_values` UI and the closed domain catalogs.
- **Alternative:** if the intent is search-as-you-type over large catalogs, use an accessible searchable **closed-choice** combobox. That is no longer the smallest patch: it needs an explicit widget choice, keyboard/focus/accessibility behavior, HTMX reinitialization, and dedicated browser tests. An always-open `<select size>` listbox is another distinct visual requirement and should be confirmed before implementation.

## Decisions

- 2026-08-31 — Classify as a confirmed interface simplification, not a bug and not a library change.
- 2026-08-31 — Treat free-text entry as incidental because every emitted datalist is backed by closed conditional values enforced by e-footprint.
- User confirmation remains only if “lists” did not mean native dropdown selects or if searchable filtering is required.
