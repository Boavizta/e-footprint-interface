Draft for spec-plan refinement · 8 October 2026 · Interface-owned

Simple workspace mutation gate

Specification under review · Candidate changed files

Planning handoff only. This captures the conversation and verified entry points; it does not authorize implementation or freeze the proposed API. The user chose cancellation over queueing because low latency and sequential editing are expected. Recheck the current code and produce the smallest reviewable patch during the next spec-plan session.

Baseline: interface commit a9122dba, inspected 8 October 2026. The main script grew from 413 lines before simplified-inputs implementation to 552; the current mutation guard occupies lines 365–520. Preserve unrelated latency middleware and local dependency edits. No library changes are proposed.

1. Admit one workspace write

Refactor the existing guard, keeping one active operation identity and its initiating element. Remove the page-wide control snapshot, locking selectors and capture listeners whose only purpose is preventing every interaction. Relocating the existing block into another file alone does not achieve the requested simplification.

The current mutation classification treats non-GET requests as writes except timeseries previews. Start from this small policy and verify its callers; explicit per-request declarations are an alternative only if they reduce the total patch. Reads do not occupy or release the gate. Avoid a request registry or global fetch monkey-patch.

Reject an overlapping HTMX mutation before HTMX can queue it. The vendored HTMX 2.0.6 implementation handles same-element queueing before the before-request event. Evaluate a confirm-stage gate or shared HTMX synchronization with explicit cancellation feedback; a before-request listener alone is insufficient.

Reuse the card-order save bridge and diagram-deletion bridge for fetch writes. Admission must occur before optimistic UI changes. Card order changes visually before its save callback, so planning must choose the smallest honest cancellation treatment for that existing interaction.

Preserve the existing started notification and finished notification if that avoids rewiring consumers. A canceled operation is never admitted and must not emit a fake completion that clears the first operation's gate or continues an export.

Keep busy state through the admitted operation's response updates, using only the necessary request/settlement correlation. HTTP error bodies can carry OOB fragments through the existing modal error handling. The planning pass may simplify settlement bookkeeping after checking actual no-swap, error and removed-target flows; do not unlock indiscriminately whenever any request ends.

2. Cancel another write and explain what happened

Use one concise existing notice surface for “Another save was running. This change was not saved. Try again after it finishes.” The existing toast region is a candidate, not a mandated new notification abstraction. Reuse the existing field status where available.

The current simple-field save entry silently returns when the workspace is busy, and sets the form's saving flag before triggering HTMX. The provenance completion handler also silently returns while busy. Replace these silent drops with the common cancellation outcome. A rejected request may never receive the normal after-request or finished event; reset only the canceled caller's saving state and mark its still-visible editor Not saved.

Retain the attempted value in the existing DOM only. Keep the accepted-value baseline unchanged so ordinary completion can resubmit it after the gate is free, even if its value has not changed again. Do not allocate a pending payload, add Retry/Discard controls, resubmit on the first request's completion, or add a navigation guard for canceled fields.

theme/static/scripts/model_builder_main.js · Illustrative outcome, not a prescribed API

if a workspace write is active:
    do not send the new write
    notify the user
    notify the initiating editor that its save was canceled
    leave the active write unchanged
else:
    admit the write and record its identity

The same cancellation outcome must cover bookmark saves, Configure saves, ordinary forms and confidence autosaves. The latter currently calls HTMX without a widget source; supply minimal initiating context if required for honest feedback. Preserve existing explicit draft behavior, rather than redesigning it.

Server rejection of an admitted save remains different from local busy cancellation. Retain the current 422/500 modal and fresh accepted-field restoration for admitted failures. In particular, the finished handler should not accidentally mark a different canceled editor Saved or clear its Not saved status.

3. Read, navigate and export

Keep harmless reads and previews available. Model switching, imports, reset and destructive actions remain workspace writes and receive cancellation feedback while busy. Existing Configure exit confirmation and ordinary side-panel dirty-form handling remain owned by their current flows.

Allowing edits during a write changes the assumptions around workspace reads, draft-read coordination and Results target cleanup. Keep only coordination required by supported response targets. Demonstrate any concrete case in which an admitted response replaces a canceled editor before proposing additional protection; the spec does not promise draft durability across replacing that editor.

Keep a narrow check for export activation. Ordinary download anchors bypass HTMX/fetch interception, so their busy behavior needs an explicit hook. Retain the existing focused-field completion and successful export continuation. A cancellation must neither download nor leave a pending continuation that fires when another save finishes. Recheck native new-tab/context-menu activation against the toolbar links; scope any destination suppression to export controls only.

The remaining global button disabling on Results reads can still conflict with a request-only policy. Planning must compare retaining the small pre-existing disabled-button restoration helper with narrowing the broad disabling attributes in affected templates. Do not retain the current multi-map control lock merely to accommodate that convention, or migrate every template without evidence that the migration reduces complexity.
