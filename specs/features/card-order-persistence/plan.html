Persistent object-card ordering — Implementation plan

Status: Plan — under review · 2026-08-31 · Spec: spec.html

1. Approach

Keep ordering as UI-only metadata in interface_config["card_order"], next to the existing Sankey configuration. SortableJS will use each card's existing id attribute as its identifier. When a drag ends, the client gathers the complete order of all six designated lists and sends one fire-and-forget POST. The endpoint replaces only card_order, preserving all other interface configuration, and persists through the active model repository's established cache/session path.

On every full builder render, the adapter reads each resident workspace slot's own interface configuration, merges saved rank with the current objects, and supplies explicitly ordered lists to the canvas template. Saved IDs not present in the current model are ignored; current objects without a saved rank retain their natural relative order after all ranked objects. ModelWeb remains unchanged. Build the rank map once per list so restoration is O(n + m) for n current cards and m saved IDs.

Persisted shape 
{
  "interface_config": {
    "sankey_diagrams": [...],
    "card_order": {
      "up-list": ["UsagePattern_abc", "EdgeUsagePattern_xyz"],
      "uj-list": ["UsageJourney_1", "UsageJourney_2"],
      "external-api-list": ["ExternalAPI_1"],
      "server-list": ["Server_1", "Server_2"],
      "edge-device-groups-list": ["EdgeDeviceGroup_1"],
      "edge-devices-list": ["EdgeDeviceBase_1"]
    }
  }
}

3. Cross-cutting concerns

  • Tests: Use Python unit tests for ordering and repository writes, including one full six-list payload assertion against persisted interface_config. In Jest, enumerate the initialized Sortable instances and prove that ending a drag on each produces a payload containing every sortable list and its toArray() order; this is the regression gate that prevents a future sortable list from being left unpersisted. Add one Playwright workflow for the user-visible reload/export/import contract. Run the full pytest and Jest quality gates before shipping.
  • Validation: Accept one JSON object containing exactly the supported list keys whose values are arrays of string IDs. Malformed requests return 400 without altering existing interface configuration. Duplicate submitted IDs can be normalized to their first occurrence during rank-map construction so they cannot duplicate cards in output.
  • Persistence: Update repository.interface_config["card_order"] in place, then use the same model persistence route already used by Sankey configuration. Do not overwrite sibling interface_config keys.
  • Schema migration: None. card_order is optional and additive; old JSON files naturally use model order, while the existing export/import machinery already carries the complete interface_config.
  • Workspace behavior: The save endpoint targets the active repository. Full rendering must order both resident canvases from their own repository configuration so a later client-side slot switch reveals the right per-model order without re-rendering.
  • Failure behavior: The browser keeps the reordered DOM even if the background request fails. Suppress an unhandled promise rejection; a later reload may therefore show the last successfully saved order, consistent with the deliberately fire-and-forget design.
  • Docs: Update specs/architecture.md; no AGENTS.md change is needed because its existing persistence and architecture pointers remain accurate.

4. Risks

  • Resident workspace canvases: only the active canvas owns canonical list IDs, while parked canvases have suffixed IDs. Mitigation: save the active canvas only, but prepare ordered context per slot on the full render; retain the established reinitialization after slot switches.
  • New and stale object IDs: naïve sorting with repeated index() is both fragile and O(nm). Mitigation: build an ID-to-rank map once, filter stale IDs implicitly, and use original position as the stable fallback for unranked objects.
  • Lost sibling configuration: assigning a new interface-config dict could erase Sankey settings. Mitigation: mutate only card_order and assert preservation in endpoint tests.
  • Rapid consecutive drags: fire-and-forget requests can complete out of order. SortableJS onEnd normally spaces requests by user interaction, but it is still possible. Preserve the stated simple last-request model for this iteration; if tests or production evidence show reordering races, add client serialization as a follow-up rather than broadening this feature pre-emptively.
  • Import expectations: imports without interface_config currently preserve the active session's configuration. Keep that established behavior; imported files with card_order replace it as part of their complete interface configuration.

5. Alternatives considered

  • Store order in the efootprint model or ModelWeb: rejected because visual card order is interface state, not modeling truth, and would contaminate the domain boundary.
  • Save one list per request: rejected because partial state complicates persistence and import semantics; the six short arrays are cheap to send together.
  • Save continuously during dragging or add a Save button: rejected because the DOM already provides immediate session state and drag end is the single meaningful persistence boundary.
  • Reorder cards client-side after every render: rejected because the Django adapter can provide deterministic render context with no extra startup manipulation or client-side state layer.
  • Clean stale identifiers on every render: rejected because ignoring them is sufficient and avoids a write during a read-only page load.

6. Constitutional notes

The plan preserves dependency direction and the library-as-domain-truth rule: only Django adapter, template, repository-owned interface metadata, and minimal JavaScript concerns change. ModelWeb and the e-footprint repository remain untouched. The endpoint is a small HTTP persistence adapter rather than a new client-side data layer, consistent with the HTMX-first/minimal-JavaScript rule. No constitutional amendment is required.
