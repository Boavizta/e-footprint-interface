Persistent object-card ordering

Status: Spec — under review · 2026-08-31

1. Problem and audience

People building a model can drag its top-level object cards into an order that helps them understand and present the system. Today that organization exists only in the browser DOM: reloading the page returns the cards to their model-derived order, and exporting then importing the model also loses it.

This affects anyone who uses card order as part of an ongoing modeling workflow, especially larger models where a deliberate visual sequence reduces scanning effort. Persisting that preference makes the existing drag-and-drop interaction trustworthy rather than temporary.

2. Success criteria

  • After a user reorders cards in any of the six designated top-level lists, a successful page reload restores the same order.
  • Downloading a model after reordering cards and uploading that file restores the saved order.
  • Usage patterns, usage journeys, external APIs, servers, root edge-device groups, and ungrouped edge devices all participate in the persisted ordering behavior.
  • A newly added object that has no saved position appears after the saved objects in its list.
  • A saved identifier for an object that no longer exists does not prevent the modeling view from loading.
  • Dragging remains immediate: the card moves in the page without waiting for a server-rendered response or requiring a separate Save action.
  • Each model in a two-model workspace restores its own card order.

3. Scope

In scope
  • Remembering the order of cards in the six designated lists in the main modeling view.
  • Saving the complete six-list ordering after a drag finishes.
  • Restoring ordering on a fresh render, including after reload and file import.
  • Including the ordering preference in single-model and workspace JSON round trips.
  • Graceful behavior when saved and current object sets differ.
Out of scope (this iteration)
  • Moving cards between lists.
  • Ordering nested cards inside journeys, servers, or within edge-device groups.
  • A visible save indicator, retry queue, or offline synchronization for a failed background save.
  • User-account-level ordering shared across models or browser sessions.
  • Automatically pruning identifiers for deleted objects from previously saved order data.

4. UX / interface

The existing drag interaction is unchanged. This small review mockup uses arrow buttons in place of dragging: move a card, then use “Simulate reload” to see that the visible order is retained.

5. Constraints

  • The feature remains session-driven and model-scoped, consistent with specs/mission.md.
  • Ordering is interface-only state and must not enter the efootprint model or ModelWeb; this preserves the Clean Architecture boundary and the library-as-domain-truth rules in the constitution.
  • The existing HTMX-first, minimal-JavaScript architecture remains in place. The background write occurs only when a drag ends.
  • Existing JSON files without saved card ordering remain valid and render in their natural order.
