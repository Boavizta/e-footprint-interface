Weekly-pattern builder for recurrent quantities — Implementation plan

Status: Plan — approved · 2026-09-01 · Spec: spec.html

1. Approach

Implement this as a library-owned recurrent-quantity builder plus an interface-owned composite editor. The library validates normalized profile data, composes the canonical NumPy week, preserves authored inputs in JSON, and registers the subclass for deserialization. The interface explicitly registers which builders are editable for each explainable timeseries type and supplies the labels, templates, defaults, and selection behavior.

The composite editor renders all available builder sub-forms once. It hides and disables inactive sub-forms so only the selected builder submits, while their DOM values remain intact for lossless switching. A dedicated vanilla-JavaScript module manages profiles, day ownership, ranges, chronological placement, immediate validation, and serialization of the active weekly profile structure into a hidden form payload. The adapter parses that payload before the normal object factory delegates construction to ExplainableObject.from_json_dict.

Add one non-persisting draft-preview path shared by recurrent and hourly form builders. After a valid committed edit, HTMX posts the active builder inputs to a thin adapter view. The view constructs the same e-footprint builder used on save, asks generalized timeseries presentation helpers for bounded chart series, and returns an HTML partial containing server-prepared data. A generic browser renderer owns Chart.js lifecycle only; it performs no projection, weekly composition, or temporal aggregation. Migrate the current hourly usage preview onto this path and remove those calculations from usage_pattern_timeseries.js.

Proposed authored data shape 
{
  "unit": "concurrent",
  "profiles": [
    {
      "name": "weekday",
      "days": [0, 1, 2, 3, 4],
      "baseline": 10,
      "ranges": [{"start": 8, "end": 18, "value": 60}]
    },
    {
      "name": "weekend",
      "days": [5, 6],
      "baseline": 10,
      "ranges": []
    }
  ]
}

Day indices are Monday = 0 through Sunday = 6, matching the verified existing contract in ExplainableRecurrentQuantities.generate_hourly_quantities_over_timespan(). The new deserialization matcher can identify form_inputs containing profiles and unit; existing constant-builder JSON remains unambiguous through constant_value and constant_unit.

Validation and composition algorithm
  1. Validate one to seven profiles, non-empty case-sensitive unique names, and finite numeric values.
  2. Build a seven-entry day-owner array and reject missing or duplicate ownership.
  3. For each profile, sort ranges by start, validate integer bounds, and reject a range whose start is less than the previous end. Adjacent ranges are valid.
  4. Create a (7, 24) NumPy array, fill each assigned day from its baseline, apply slice assignments for its ranges, then flatten to one float32 array. Runtime is O(P + R + 168) for profiles P ≤ 7 and ranges R ≤ 168.

Client validation mirrors these rules for immediate inline feedback, but the library validation is authoritative.

Draft-preview contract
  • A common preview request carries the object/field identity, selected registry builder identifier, normalized unsaved form_inputs, and preview identity. The server resolves constraints such as negative-value support from the field metadata rather than trusting the browser. The request carries no model mutation instruction.
  • The adapter resolves the builder through the same registry used by the form, constructs it in memory, and lets library validation/computation remain authoritative. Expected validation failures return a field/preview error state, not the global exception modal.
  • A valid recurrent response contains one 168-point hourly series with Monday-through-Sunday labels.
  • A valid hourly response contains pre-aggregated monthly and yearly series so the existing granularity selector can switch without browser-side aggregation or another request. The full multi-year hourly array is never transferred.
  • Success updates both preview status and chart payload. Invalid responses update status only, preserving the last valid chart. Obvious client-invalid states suppress the request, but server validation still protects direct submissions.
  • Continuous hourly inputs and numeric baselines use a short debounce; range bounds refresh after commit, and profile add/remove/day-assignment actions refresh immediately when valid. One preview region allows only its newest request to win.

3. Cross-cutting concerns

  • Tests: keep numerical and schema rules in library unit tests; cover adapter shape and parsing in interface unit tests; cover dynamic browser behavior in Jest; use focused Playwright flows for weekly preview/save and the migrated hourly preview.
  • Migrations: no database migration. Keeping the constant builder and its current matcher means existing saved systems continue to load. If review adds a discriminator to existing JSON, the library schema version and upgrade handler become mandatory.
  • Metadata: source, confidence, comment, label, and can_be_negative behavior must remain at the composite field boundary and apply equally to either builder.
  • Unsaved changes: changes in hidden inactive builders must still mark the containing form modified; closing the panel discards both drafts through the existing panel lifecycle.
  • Preview performance: debounce continuous edits, cancel/replace stale in-flight requests, return only 168 recurrent points or compact pre-aggregated hourly series, and never persist or hydrate the full model for preview.
  • Preview errors: expected draft validation updates the preview status without replacing its last valid chart or opening a global error modal. Save remains independently protected by authoritative parsing and validation.
  • Accessibility: profile controls use fieldsets/legends and explicit labels; errors connect through aria-describedby; hidden inactive builders are not focusable or submitted.
  • Docs: if the registry/composite-field pattern ships, add a concise entry to e-footprint-interface/specs/architecture.md and the delegated-JavaScript convention if it gains a reusable rule. Document the new library builder, authored-state persistence, and human-readable comparison surface under the corresponding e-footprint layers/modeling, persistence, and comparison/display pages.

4. Risks

  • Two validators drift. Client and library checks could disagree. Keep pure, table-driven cases aligned; treat the library as authoritative and test boundary values in both suites.
  • Inactive inputs leak into submission. Duplicate form keys could select the wrong matcher. Disable every named control in inactive panels and assert the posted payload in parser and E2E tests.
  • Dynamic DOM misses HTMX swaps. Per-panel listeners can disappear. Use one document-level delegated listener and idempotent initialization, following current interface conventions.
  • Metadata or unsaved-change behavior regresses. The existing field wrapper owns these concerns. Keep one composite wrapper around all builders and explicitly test source/confidence/comment plus modified-form detection.
  • Profile JSON becomes an opaque client data layer. Limit JavaScript state to the visible editor, serialize only on changes/submission, and keep the normalized schema small and library-validated.
  • Preview responses arrive out of order. A slow older request could overwrite a newer draft. Scope request replacement to each preview instance and test rapid edits.
  • Preview accidentally mutates session state. Construct standalone explainable builders only; do not invoke create/edit use cases or repository save methods, and assert repository state is unchanged.
  • Saved and draft charts drift. Extract one raw-series preparation path consumed by both surfaces rather than adding preview-only aggregation rules.

5. Alternatives considered

  • Replace the constant builder. Rejected for V1: the simple path is valuable and replacement would expand schema and migration work without improving weekly-pattern authoring.
  • Painted 7 × 24 grid. Deferred: it is visually attractive but substantially raises interaction, accessibility, and testing cost.
  • Server round-trip for editor mutation. Rejected: profile/range state remains local and responsive. Only a debounced or commit-triggered, read-only preview request crosses the server boundary.
  • Compute draft previews in JavaScript. Rejected: the current hourly preview already duplicates library projection logic; extending that pattern to weekly composition would create a second domain implementation.
  • Render chart images or SVG entirely on the server. Rejected: server-prepared data plus the existing Chart.js dependency retains interaction and reuses current UI infrastructure without duplicating modeling logic.
  • Separate hourly and recurrent preview endpoints. Rejected: their construction and chart shapes vary, but request lifecycle, validation, bounded response, error state, and rendering contract are the same.
  • Infer UI builders from every ExplainableObject deserialization matcher. Rejected: those matchers are persistence concerns and do not carry safe UI labels, templates, defaults, or ordering.
  • Encode every nested value as bracketed form keys. Rejected: the chosen single normalized hidden JSON payload is leaner for dynamic profile and range lists. Structured server-error paths map failures back to visible inputs.

6. Constitutional notes

  • Library domain truth: weekly validation and composition live in e-footprint; the interface only renders, collects, and parses inputs.
  • Dependency direction: interface form concerns stay in adapters/templates/static assets. No Django or UI metadata enters the interface domain/application layers or the library.
  • HTMX-first, minimal JavaScript: JavaScript is limited to inherently local, unsaved editor interaction; persistence still uses the existing form submission and use-case flow. HTMX owns draft refreshes; generic JavaScript only manages Chart.js and selects among server-precomputed series.
  • No preview persistence: the adapter constructs temporary library values and never calls a repository or mutation use case, preserving the session as authoritative only for saved model state.
  • JSON quality gate: new authored builder state receives a complete library round-trip test. No constitutional amendment is required by this draft.

7. Resolved decisions

  • Use ExplainableRecurrentQuantitiesFromWeeklyPattern as the library class name and Weekly pattern as its interface label.
  • Keep editable-builder labels, templates, ordering, and defaults in an explicit interface registry rather than on library classes.
  • Submit the dynamic weekly profiles as one normalized hidden JSON value.
  • Return validation errors as a list of objects containing a normalized field path such as profiles[1].ranges[0].start, a stable error code, and a user-facing message. Preview and save map the same errors to visible controls. An invalid preview returns no replacement series, so the last valid chart remains visible.
