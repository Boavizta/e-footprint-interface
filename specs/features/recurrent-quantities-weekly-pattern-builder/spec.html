Weekly-pattern builder for recurrent quantities

Status: Spec — under review · 2026-08-31 · Reformatted from the 2026-04-21 legacy spec

1. Problem and audience

ExplainableRecurrentQuantities represents a canonical 168-hour week, but the interface currently lets people author only one value repeated across every hour. This makes ordinary rhythms—weekday office hours, quiet evenings, busier weekends, or scheduled edge workloads—impossible to express without leaving the interface.

  • Primary audience: non-technical product and sustainability practitioners who need a form-based way to describe a weekly workload without constructing an array or writing Python.
  • Secondary audience: technical and industrial users modeling recurrent web or edge demand.
  • Why now: recurrent workload inputs already exist throughout edge modeling; richer authoring removes a modeling limitation while preserving the simple constant-value path.

2. Success criteria

  • A user can choose between Constant value and Weekly pattern wherever a recurrent quantity is editable.
  • A weekly pattern can contain one to seven day profiles with non-empty, case-sensitive unique names, and every weekday is assigned to exactly one profile.
  • Each profile supports a baseline plus non-overlapping integer-hour ranges within [0, 24].
  • Saving a valid pattern produces exactly 168 hourly values ordered Monday 00:00 through Sunday 23:00, using the profile baseline outside explicit ranges.
  • Invalid profile counts, names, day coverage, numeric values, hour bounds, overlaps, or forbidden negative values block save and identify the offending profile or range inline.
  • A valid weekly-pattern draft displays a side preview of the generated 168-hour timeseries and refreshes after committed edits without saving the object.
  • An invalid draft does not produce an invented or ambiguous timeseries: the preview keeps its last valid chart and states that errors must be corrected before it can refresh.
  • Switching builders preserves the unsaved inputs of both builders until the panel is saved or closed, while only the selected builder is submitted. Closing a modified panel uses the existing unsaved-changes confirmation and discards both drafts when confirmed.
  • Existing recurrent values reopen with their stored builder selected; new values follow the builder of the attribute default and initialize a first-use weekly pattern from the current constant value.
  • The authored pattern, including unused profiles, survives system JSON download and upload without changing the computed week, unit, source, confidence, or comment.
  • Fields with only one available builder—currently hourly quantities—retain their existing appearance and behavior.
  • The existing hourly usage-journey-starts preview remains available and matches the timeseries that the library generates from the same unsaved form inputs.

3. Scope

Capability-level only. Implementation structure and wire-format choices live in plan.html.
In scope
  • A form-based weekly editor built around reusable day profiles and a total assignment of Monday through Sunday.
  • A field-level, read-only unit shared by every baseline and range value.
  • Profile creation, removal, naming, day assignment, baseline editing, and chronological range editing.
  • A newly added profile starts with baseline 0 and no ranges.
  • Single-assignment “stealing” semantics: assigning a day to one profile removes it from its previous profile.
  • New ranges start in the first free gap of at least one hour with value 0; adding is disabled when the day is fully covered. Valid edits move a range to its chronological position, while invalid edits remain in place with inline feedback.
  • New profiles append in creation order. Removing a profile leaves its days unassigned until the user assigns them elsewhere; unused profiles with no assigned days remain valid authored state.
  • Two first-use profiles: weekday for Monday–Friday and weekend for Saturday–Sunday, both using the current constant value or attribute default as their baseline.
  • A builder selector for polymorphic explainable-timeseries fields, hidden when only one builder is available.
  • Round-trip persistence and compatibility with existing calculated-attribute displays and downstream consumers.
  • Text summaries outside the editor continue to use the existing recurrent-quantity summary.
  • A live draft preview beside the editor on wide layouts, falling below it when horizontal space is constrained.
  • Migration of the existing hourly usage preview to the same authoritative preview behavior, without changing its user-facing projection controls.
  • English labels and desktop-first behavior, consistent with the rest of the application.
Out of scope (this iteration)
  • A painted or drag-and-drop 7 × 24 grid.
  • CSV import, sub-hour boundaries, formulas, profile templates, profile copying, and profile reordering.
  • Per-profile units or different units across ranges.
  • Replacing the constant builder with a degenerate weekly pattern.
  • Changing the user experience of single-builder hourly-quantity fields.

5. Constraints

  • The library remains the source of truth for weekly composition and validation; the interface must not own a competing interpretation of the 168-hour result.
  • The canonical week is local time with index 0 = Monday 00:00, matching the existing recurrent-quantity contract.
  • All values use the attribute's existing Pint unit. When the attribute disallows negatives, every baseline and range value must be zero or greater.
  • Range boundaries are integers satisfying 0 ≤ start < end ≤ 24; ranges within one profile are disjoint.
  • Interaction follows the interface's HTMX-first, minimal-JavaScript constitution. Local JavaScript is acceptable for lossless builder switching and dynamic profile/range editing.
  • Draft preview values are generated authoritatively on the server through the same library builders used on save; previewing must not persist or mutate the session model. Browser code only coordinates requests and renders the response.
  • Preview requests are bounded, debounced where inputs change continuously, and ensure an older response cannot replace a newer draft. The hourly preview is aggregated before transfer rather than sending its full multi-year hourly array.
  • The library JSON quality gate applies: authored state and its computed result must round-trip.
  • No backward-compatibility shim is required, but existing constant-builder JSON must continue to load in V1.
