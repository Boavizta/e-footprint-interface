Open a file: confirm before replacing the current modeling

Status: Spec — approved · 2026-10-21 · Source: GitHub issue #148

1. Problem and audience

  • Problem. "Open a file" replaces the current modeling without warning. A single-modeling file replaces the active modeling. A comparison file replaces both modelings. Every other action that discards a modeling asks first: loading an example from the picker ("This will replace your current modeling. Continue?"), "Reset to default modeling", and the ✕ that removes a modeling from a comparison. Users who rely on that warning elsewhere expect it here too. Modelings live only in the session, so work that was never downloaded is lost for good.
  • Who. Any user who opens a file while working on a modeling. The primary user is a non-technical product person, who is the least likely to download a backup first. Reported once by a tester on the deployed app (2026-09-30). Frequency unknown: no usage data exists for "Open a file" over a non-empty modeling.
  • Why now. The fix is cheap and closes the only gap among the actions that discard a modeling. Consistent warnings come before undo, which is tracked separately.
  • Tradeoff: one confirmation, decided before the upload. The interface only knows whether a file holds one modeling or a comparison after the file is uploaded. Two other approaches were considered. Reading the file in the browser first would need new client-side parsing. Uploading the file, holding it on the server and asking afterwards would store the interrupted action, which mission.md rules out ("Guards block; they do not suspend and replay"). Recommendation: ask once, before the upload, using what the page already knows: whether any modeling holds content and whether the session is a comparison. Cost: in a comparison where only the inactive modeling holds content, opening a single-modeling file would not discard it, yet the user is still asked. That case is rare and the extra prompt is harmless.

2. Success criteria

  • Single-modeling session, modeling with content: choosing a file and pressing Open asks "This will replace your current modeling. Continue?", the same wording the example picker uses.
  • Comparison session, at least one modeling with content: pressing Open asks for confirmation and says that the active modeling, or both modelings for a comparison file, will be replaced.
  • Cancel: nothing is uploaded. The modeling(s), the open "Open a file" panel and the chosen file stay as they were. Pressing Open again asks again. The cancelled action is not remembered or replayed.
  • Confirm: the file opens exactly as it does today, including the existing error message for an invalid file.
  • Nothing to discard: when every modeling in the session is empty, the file opens with no confirmation, matching the example picker and Reset.
  • Every entry point: the toolbar "Open a file" button and the picker's "Open a file" card behave the same, because both lead to the same Open action.
  • No new prompt for additions: "＋ Add a modeling to compare → Import" adds a modeling without discarding one, so it does not ask. Opening the "Open a file" panel itself does not ask either.
  • The existing confirmations (example picker, Reset, ✕ remove) are unchanged.

3. Scope

Capability-level only. File paths, class/method/parameter names, refactor instructions, internal hypotheses, and "mirror pattern X" code-level decisions belong in plan.html, not here.
In scope
  • A confirmation when Open is pressed in the "Open a file" panel while at least one modeling in the session holds content.
  • Wording that matches the session: "your current modeling" in a single-modeling session; the active modeling, or both modelings for a comparison file, in a comparison session.
  • The same behavior as the existing "replace" confirmations: the browser's native confirm dialog, decided from the page's content at the moment Open is pressed.
Out of scope (this iteration)
  • Undo or restore after a replacement (tracked separately, as the issue notes).
  • Wording that depends on the chosen file's content (single modeling vs comparison). See the tradeoff in §1.
  • Replacing the native confirm dialogs with a styled modal, for this action or the others.
  • Offering a download of the current modeling from the confirmation.
  • Any change to how a file is detected, validated or restored.

5. Constraints

  • mission.md, "Guards block; they do not suspend and replay": after Cancel the user simply presses Open again; the interrupted request is not stored.
  • constitution.md §1.4 (HTMX-first, minimal JS): reuse the existing conditional confirmation rather than adding new client logic or parsing the file in the browser.
  • Constitution §2.6: a CHANGELOG.md entry under ## [Unreleased].
  • The existing end-to-end tests that open a file over a non-empty modeling must keep passing and must handle the new confirmation explicitly.
