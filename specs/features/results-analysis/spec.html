Results analysis — configurable emission chart cards

Status: Spec — under review · 2026-07-03 · Normative UX: specs/design/journeys/analyse-results.html (prospective journey)

Thin spec by design. This feature is design-heavy, so the UX substance — screens, states, decisions — is authored as the prospective analyse-results journey (link above), which is normative for this feature. This file binds the feature into the spec-driven workflow at the capability level: problem, success criteria, scope, constraints. Same pattern as the pull-based-computation thin spec + rich companion.

1. Problem and audience

  • Problem. The Results panel's carbon charts are a read-only dead end: two fixed charts, one fixed breakdown (broad object categories), no way to see emissions over time for any other angle — per usage journey, per job, per country — even though the modeling engine attributes impact at exactly that granularity. Nor is there any way to keep an analysis: a user who finds an insight can only screenshot it; nothing of the reading survives in the model file.
  • Audience. The primary persona (non-technical product person) reads the default view unchanged and gains "one more chart from another angle" with a single control. Technical and methodology users (engineers, consultants, sustainability teams) compose multi-view, annotated analyses they can hand to stakeholders — the depth-on-demand posture of mission.md.
  • Why now. The library's pull-based results contract (and its companion attributed-footprints feature) makes per-object impact series cheap, persisted, and consistent with the Sankey by construction — the data this feature needs is about to exist natively. And the Sankey card stack has proven the interaction pattern (configurable analysis views as stackable cards with persisted settings); this feature generalizes it to the time dimension.

2. Success criteria

Each criterion is user-observable and testable.

  • Default parity. Opening Results on a computed model with no saved chart config shows the same information as today: per-period (yearly) and cumulative emissions by object category, with the split Fabrication / Usage legend — no configuration required.
  • Any angle. On a card, the user can choose any breakdown offered for the classes present in their model (object category, hardware, usage patterns, usage journeys, steps/functions, jobs/component needs, countries), switch between per-period and cumulative modes, change granularity (month/year) and lifecycle phase, and the chart re-renders without a page reload.
  • Conservation. Every stacked chart sums to the system total for the same period and phase selection (within display rounding) — including an explicit "Not attributable to …" remainder series when the chosen angle does not cover all flows. Chart values agree with the Sankey and the total footprint for equivalent selections.
  • Stack and order. The user can add chart cards, delete them, retitle them, and reorder them; the stack renders in the chosen order.
  • Commentary. The user can attach plain-text commentary to any card, edited in place; saving commentary or a title never recomputes the model and never reloads the chart.
  • Persistence. Cards — settings, titles, order, commentary — survive closing/reopening the panel, a session reload, and a model export → import round-trip.
  • No recompute on view. Opening Results on an already-computed model triggers no model recomputation; chart data is derived from persisted results.
  • Gate preserved. The Results entry points still gate on model computability with the live validation reason (behavior unchanged from today).

3. Scope

Capability-level only. File paths, class/method/parameter names, refactor instructions, and "mirror pattern X" decisions live in plan.html.
In scope
  • Replace the two fixed CO2 charts with a stack of configurable emission chart cards (one card type; per-period / cumulative modes; breakdown, granularity, phase, small-contributor aggregation settings).
  • Default card stack reproducing today's view for unconfigured models.
  • Add / delete / retitle / reorder cards; per-card plain-text commentary.
  • Persistence of the card stack in the model file's UI configuration (same posture as Sankey cards).
  • Series tooltips carrying object identity, value, and share of period total; object identity present in the chart data (the seam for future click-through to object panels and audit mode).
  • Retirement of the interface-side per-category emissions aggregation in favor of the library's results (single source of modeling truth).
Out of scope (this iteration)
  • Impact badges on object cards, side-panel impact header, and the audit-mode rebuild — separate features slicing off later prospective journeys.
  • Day-level granularity in the UI (the data contract already supports it; UI toggle deferred).
  • Report output (print / PDF / share rendering of the stack) and rich-text commentary.
  • Clicking a chart series to navigate anywhere (tooltip only in this iteration).
  • The Sankey section, Sources tab, and xlsx export — unchanged.
  • The companion library feature (serialized daily attributed footprints) — specified and driven from the e-footprint repository; this feature consumes its released contract.

5. Constraints

  • Constitution §1.3 — the library is the domain truth. All attribution and aggregation of impact values happens in the efootprint library; the interface renders. No interface-side re-implementation of emissions math survives this feature.
  • Constitution §1.4 — HTMX-first, minimize JS. Card management is partial-update driven; client JS is limited to chart rendering.
  • Dependency. Requires a released efootprint carrying the pull-based results contract and the companion attributed-footprints feature (serialized daily attributed footprints for non-impact-source objects). Quality gate §2.4 (PyPI pin) applies before merge.
  • Performance. Binding constraints are session-store weight and JSON round-trips, not CPU (specs/architecture.md): viewing results must not recompute the model; chart payloads are rolled up server-side to the requested granularity so they stay small on large models.
  • Prospective-journey discipline. Until this feature ships, view-results remains the faithful journey; analyse-results carries a prospective banner and supersedes view-results Phases B–C at ship time.

6. Open questions

  • Remainder semantics — the journey decides on an explicit "Not attributable to …" series so stacks always sum to the system total. Ratify or amend (alternative: partial stacks with a caption).
  • Phase handling on object-level breakdowns — the journey decides phases sum per object by default (category view keeps the split legend). Ratify or amend.
  • Default stack composition — two cards (per-period + cumulative, by category). Ratify or amend.
  • Card titles — auto-generated from settings with inline rename. Ratify or amend.
