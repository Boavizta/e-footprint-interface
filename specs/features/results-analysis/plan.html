Results analysis — Implementation plan

Status: DRAFT — produced by spec-specify because the kickoff conversation was design-rich; to be refined during the spec-plan stage · 2026-07-03 · Spec: spec.html · Normative UX: analyse-results journey (prospective)

1. Approach

Mirror the Sankey card architecture end to end — routes, views, templates, interface_config persistence — for a new chart-card family, and move all series math to the library. The interface's EmissionsCalculationService (daily-per-category aggregation feeding window.emissions) retires; chart series are folds over the library's persisted results: impact-source classes fold the serialized hourly footprint pairs (reduced to daily on read), all other classes read the serialized daily attributed-footprint projections delivered by the companion library feature. Chart.js remains the renderer; the existing result_charts bundle (rollups, split-capsule legend, tooltips) is refactored from two-hardcoded-charts to card-config-driven.

Data flow per card: HTMX POST chart-diagram/ with the card's settings → view builds the series payload via a thin adapter over library accessors (no attribution math interface-side) → template swaps the card's chart region → JS draws. Card CRUD, reorder and commentary are sibling endpoints persisting interface_config["result_charts"] via persist_to_cache(), exactly like sankey_views.py does for ["sankey_diagrams"].

2. Dependency — companion library feature (blocks implementation)

Driven from e-footprint/specs/features/ (library repo); contract settled in the 2026-07-03 discussion:

  • Per non-impact-source object and phase: hourly attributed_energy_footprint / attributed_fabrication_footprint as ordinary non-serialized @computed_attributes (lazy intermediates, full ancestry), plus a daily reduction projection slot per phase flagged @lazy_attribute(serialize=True) — computed on first read, persisted, invalidated by the ordinary deletion wave. Requires a uniform-step daily explainable-timeseries type (sibling of ExplainableHourlyQuantities).
  • Impact sources unchanged (serialized hourly pairs); impact_repartition_matrix unchanged (lazy period sums — Sankey only).
  • Remainder invariant: per breakdown class, system total − Σ(attributed daily of that class) = the "Not attributable" series; conservation guaranteed by attribution, asserted in tests.
  • Perf gates to measure there: added JSON weight (daily projections, est. ~1–2 MB compressed on the big fixture) and per-edit dirty-cone attribution cost (decides eager-vs-lazy pull policy for badges later; this feature only reads persisted values).

This interface feature starts when that contract is on a released efootprint (quality gate §2.4: PyPI pin before merge; local co-dev via editable install meanwhile).

4. Cross-cutting concerns

  • Tests: unit — chart_series_service (per-breakdown series, conservation incl. remainder, aggregation folding, granularity rollups, phase handling); integration — card CRUD/reorder/ commentary round-trip through interface_config incl. export→import; default-stack parity when key absent; Jest — drawChartCard config-driven rendering, legend behaviors; E2E (one critical flow) — open results → add card → change breakdown → commentary → reload → stack intact.
  • Migrations: no DB change. JSON: new interface_config key with absent-key default (no upgrade function needed); requires the companion library feature's serialization contract (efootprint version bump handles legacy files by lazy recompute — its concern, not ours).
  • Docs: specs/architecture.md — replace the emissions-service description with the chart-card pipeline + interface_config["result_charts"]; design hub — flip the prospective pill at ship; CHANGELOG.md entry (quality gate §2.6).

5. Risks

  • Series explosion on object breakdowns (e.g. 50 jobs): mitigated by the aggregation slider (default threshold folds the tail into "Other") and phase-summing default; palette must stay legible — cap distinct hues, ramp within groups.
  • Payload weight on big models: mitigated by server-side rollup (month/year points only; daily stays server-side until a Day toggle ships).
  • Default-view parity regressions: the old and new category series must match numerically; add a pinned-fixture comparison test before retiring the old service.
  • Comparison dashboard coupling: comparison_charts.js shares the bundle and may consume window.emissions — audit and migrate or isolate before retirement (spec-plan refinement item).
  • Library release timing: feature blocked on the companion contract; keep stages separable so template/JS work can proceed against a local editable install.
  • Commentary injection: plain text rendered escaped (Django autoescape); no HTML pass-through.

6. Alternatives considered

  • Time-bucketed repartition matrix as the chart data source — rejected: atom-resolution × time is over-resolution for chart consumers (they fold to object × phase × time immediately); would rework a just-ratified contract; per-object attributed slots are smaller, incrementally invalidated, and natively auditable. (2026-07-03 discussion.)
  • Monthly (or hourly) attributed projections — monthly rejected in favor of daily: daily is uniform-step (simpler type), matches the existing client daily contract, folds exactly to month/year, and keeps a future Day toggle data-free. Hourly rejected: tens of MB for symmetry no consumer reads; hourly stays a lazy pull.
  • Keep EmissionsCalculationService alongside the new path — rejected: two aggregation truths drift; constitution §1.3.
  • ECharts for the time charts (align with Sankey) — rejected for this feature: Chart.js is already bundled, tested, and sufficient; a renderer migration is orthogonal scope.
  • One mega-configurable chart instead of stackable cards — rejected: same rationale as the Sankey's stacked views; comparing angles side by side beats reconfiguring one artefact, and cards give the report its structure.
  • Drag-and-drop reorder — rejected: constitution §1.4; ↑↓ buttons are two HTMX posts.
