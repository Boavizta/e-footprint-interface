Public modeling sharing

Status: Spec — review decisions confirmed · 2026-09-30 · implementation pending

1. Problem and audience

A modeling currently lives in a temporary browser-session workspace. Keeping or exchanging it beyond that session requires a JSON file. There is no public address that a company can put on a transparency page, a writer can link in an article, or a researcher can cite for readers to inspect and reuse.

This feature makes a single modeling or a two-modeling comparison a long-lived, public publication with a stable URL, version history, explainable results and an anonymous fork action.

AudienceOutcome
Companies and ecodesign teamsPublish and update the footprint of a service and its alternatives.
Writers, journalists and researchersLink to explorable assumptions and results, with version-specific citations.
Readers and peersInspect, compare, download and fork without creating an account.

Explainability becomes publicly inspectable while the existing workspace remains the place where people read and edit modelings. Prioritize value relative to complexity: reuse its import, comparison, export, caching and size-limit behavior.

2. Success criteria

  • Publish: a user with a verified email-and-password account can publish the active modeling or both workspace modelings as one publication. It has a title, a public author/organization name, free-text tags and an optional article link. Every included modeling must pass the existing “Show results” readiness checks. A failed check or publication keeps the workspace and form intact.
  • Choose a URL: suggest a suffix from the title and allow editing before first publication, with a full URL preview. Suffixes use lowercase letters, numbers and single hyphens between words. Validate format and availability again when publishing; errors preserve the form. The chosen URL is fixed across title edits and updates. Retired addresses remain reserved.
  • Open like a JSON file: a single-model publication replaces only the active slot; a two-modeling publication replaces the whole workspace, retaining its reference/comparison roles and active selection. A sibling outside a single-model replacement stays untouched. The loaded publication occupies the normal session workspace as a read-only copy, with the existing shared size limit and cache lifecycle.
  • Protect work being replaced: JSON imports and opening shared publications warn before discarding existing editable modelings, identify the affected modeling(s), and offer Download, Cancel and Replace. Validate the incoming content and full replacement size before discarding existing work. Cancellation or loading failure leaves the workspace intact. Empty destinations need no data-loss warning. A version switch affecting only read-only shared slots needs no data-loss confirmation; if it would also replace an editable sibling, confirmation remains required.
  • Read without an account: shared slots protect modeling inputs and structure on the server as well as in the controls, including for their owner. Objects, hypotheses, results, charts, explainability and the existing comparison feature remain available. A read-only shared slot can sit beside an independently editable modeling. Clearly show the displayed version, its publication date and public author.
  • Keep viewing controls local: each visitor changes viewing settings on their own cached copy, as with an imported JSON file. Changes survive normal navigation and refresh within that workspace's lifetime. Explicitly loading another publication or version replaces the affected content and its viewing settings with the selected snapshot's defaults. There is no preference migration between versions or separate per-publication preference store. Other visitors and the stored publication are unaffected.
  • Fork in place: Fork into my session makes the loaded publication's slot(s) independently editable, keeps their current presentation, and records the source citation. It does not allocate another slot or replace an unrelated sibling. Publishing the fork creates a separate publication with its own URL. The source title, public author, exact version, URL and license survive JSON export/import and later publication. If the source disappears, keep the captured citation unchanged; its link leads to the unavailable page.
  • Update explicitly: an owner can make the loaded copy editable for an update while keeping its publication and base-version association. Editing never changes the public snapshot until Publish update. Each change beyond the four metadata fields below produces a new version. The canonical URL follows the latest version, while numbered version URLs continue to identify their snapshots and history is visible.
  • Correct current metadata: edits limited to title, public author name, tags and article link update the current version in place. Its number and URL stay the same, and no quota unit is consumed. Once superseded, a version's metadata remains as last saved. Ordinary editing never rewrites historical metadata; exceptional attribution-removal requests are handled manually.
  • Handle stale updates simply: if the public version has advanced since the working copy was opened, preserve that copy and show a warning. The owner can cancel or explicitly publish it as the next version. Intervening versions remain available. There is no automatic merge or dedicated conflict-diff viewer; the normal comparison feature is available if the user wants to compare.
  • Share and download: one Share control provides Copy latest link and Copy this version’s link. JSON download behaves exactly as in the ordinary workspace, including This modeling / Both modelings when two slots exist. Neither downloading nor forking requires sign-in.
  • Discover: list all available publications in a public index, searchable by title and filterable by free-text tag. Entries show title, author, tags, last-update date and the optional article link. Publication is self-service and does not imply endorsement by Boavizta.
  • Manage an account: provide sign-up, email verification, sign-in, password recovery, email change and deletion. For email change, confirm the user's password and verify the new address before replacing the old one; the old address remains active until then and receives a notification of the change. No approval from the old mailbox is required. Publications and their URLs stay with the account. Account emails are never public; author names are separate per-publication metadata.
  • Bound publication history: each account may retain 100 published versions in total across its publications. Initial versions, updates and moderator-unpublished versions all count; a two-modeling snapshot is one version and must fit the existing workspace size limit. Show the allowance only from 80/100, with advice to email the shared contact if more is needed. At 100, reject new publications/versions without changing existing history or the working copy. Whole-publication deletion frees its retained-version count. Do not prune versions automatically.
  • Delete: the owner can permanently delete a whole publication, or delete the account and all its publications, without maintainer intervention. Public access and discovery cease immediately. Latest and version URLs remain reserved and show “This modeling is no longer available.” Published forks remain independent. Live account/publication deletion is immediate; existing backup copies expire through the seven-day PostgreSQL backup rotation, as disclosed in the privacy notice.
  • Moderate: a discreet Report by email link includes the publication URL. A moderator can unpublish the entire publication, hiding all versions and removing it from discovery. Its URLs show the same neutral unavailable page. Retain the content for a moderator to restore at the same URLs, unless the owner permanently deletes it. Administrators can grant/revoke moderation privileges and promote other administrators; the maintainer is the initial administrator.

3. Scope

In scope
  • Verified accounts and their lifecycle; Brevo transactional emails.
  • Public single-modeling and two-modeling publications, stable addresses, history and editable current metadata.
  • Import-style workspace loading, per-slot read-only access, ordinary viewing/comparison/export and in-place forks.
  • Safer replacement confirmation and failure behavior for JSON imports as well as shared-publication loading.
  • Public discovery, owner management, the fixed version-count quota and lightweight reversible moderation.
  • Publication terms, privacy notice, account-creation consent and publish-time CC BY 4.0 acknowledgment.
  • Governance/documentation updates when the feature ships: mission, roadmap, persistence/workspace architecture, account and save/load journeys, and the existing Data & privacy surface.
Out of scope for V1
  • User-controlled private or unlisted long-lived storage. Moderator-hidden publications are the narrow retention exception.
  • Deleting individual versions; automatic history pruning; raising an individual account's allowance through code or UI. Revisit quota increases only if someone actually requests one.
  • An additional account byte quota or a publication-specific rate limiter. The fixed version count and existing size limit bound retained storage per account; they do not promise to bound all request load.
  • Renaming published URLs, redirects for renamed addresses, custom domains and account-based namespaces.
  • Concurrent collaborative editing, automatic merging or a conflict-specific diff viewer.
  • Preference migration across versions, a new saved-view indicator or a dedicated reset-to-published-view control.
  • Comments, likes, follows, user-profile pages, OAuth/SSO, embeddable widgets and formal DOI/citation tooling.
  • Searching inside modeling contents, semantic search, or a curated launch-time tag taxonomy.
  • Activity-notification subscriptions, moderation queues/dashboards, case tracking, acknowledgments and response-time commitments.
  • A dedicated attribution-removal interface or app wording. Existing Contact/Feedback routes support manual handling.
  • Historical-engine replay. Upgrade-related footprint differences belong to the separate prerequisite draft linked below.

4. UX / interface

The share-a-model journey is the single visual reference. It shows agreed future behavior inside the existing application, including mixed editable/read-only slots, replacement warnings, publishing, in-place forks, owner updates, metadata correction, quota states, email changes and unavailable links. It is a self-contained interactive storyboard, not the deployed feature.

ActionWorkspace effect
Open one shared modelingReplace active slot only, load published viewing defaults and mark that slot read-only.
Open a shared comparisonReplace both slots with the published pair; both are read-only.
Switch published versionLoad that snapshot with the same single/pair replacement rules and its defaults. Warn if editable work would be discarded.
Refresh the current viewKeep the cached copy and personal settings; a refresh is not a new import.
ForkMake the loaded publication's slot(s) editable with captured provenance and current presentation.
Edit and publish an updatePrepare an editable copy linked to the owned publication; publish explicitly later.

The publication URL and displayed version must remain consistent with the content on screen, including when another browser tab has changed the shared session workspace. Loading and confirmation must not silently discard edits from another slot or tab. Resolve the mechanics during planning using the existing workspace lifecycle.

5. Constraints and approved operating choices

  • Governance: the maintainer confirmed approval of Boavizta hosting, accounts, public storage, Brevo use, CC BY 4.0, deletion and moderation on 30 September 2026, following the Mattermost consultation posted on 3 September, with feedback requested through 14 September and no objections for more than two weeks. This records the confirmed consultation outcome, not a formal board vote. Production activation remains a deliberate release operation, not an unresolved request for another governance approval.
  • License: use CC BY 4.0. Preserve source/license notices and fork attribution. Verify compatibility of embedded third-party data during planning; publication does not relicense rights the publisher does not hold. Exceptional attribution requests use existing contact routes and manual intervention, including on historical citations.
  • Data and retention: collect only account email, password hash and technical verification/ authorization data. The privacy notice must describe sessions, public content, moderator-retained hidden content, Brevo processing, logs and backups. Daily PostgreSQL backups rotate after seven days. Terms must explain that independent copies/forks can survive source deletion.
  • Email: Boavizta's Brevo service is confirmed and a dedicated API credential is available. Sender configuration, delivery failures, expiry/resend behavior and provider retention are planning work.
  • Contact: use vincent.villet@publicissapient.com for publication reports and quota guidance. These and existing equivalent contact uses must share one contact configuration value rather than hardcoded copies.
  • Runtime: use the normal visitor workspace, session cache lifecycle and shared payload-size limit. Read-only enforcement protects source snapshots; viewing preferences write only to the visitor's copy. No separate long-lived private workspace is introduced.
  • Library upgrades: old JSON and old shared publications must use the same upgrade behavior. Stored publication snapshots remain the source record; loading may migrate inputs and recalculate under the running library. Do not imply that a fixed version URL freezes every numerical result across engine changes. Before implementation, refine the separate modeling upgrade comparison draft with spec-specify; the desired outcome is a summary of all objects with footprint divergences and a click-through overlay of historical and recalculated footprints.
  • Architecture: Clean Architecture and HTMX-first apply. Modeling truth and numerical comparison remain in the library. Existing construction, import, export and result-readiness mechanisms should be reused. No constitutional amendment is required; mission/architecture updates describe the feature when implemented.
