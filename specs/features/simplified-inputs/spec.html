Simplified inputs

Status: Spec — under review · 2026-09-14

1. Problem and audience

An ecodesign expert can build a faithful modeling, but that modeling may contain dozens of interdependent objects and assumptions. A colleague who only needs to adapt a few business variables must currently enter the same full editing experience, understand which inputs are safe to change, and avoid disturbing the expert's underlying structure.

This feature lets the expert turn a complete modeling into a simplified template: a self-contained JSON file that exposes a deliberately chosen subset of inputs. Opening the file leads with those inputs, so another person can adapt the modeling without first learning its full construction. The same JSON also retains the complete modeling and template definition. Every file holder can move between normal modeling, template construction, and template consumption; simplification guides the user but does not conceal, secure, or create ownership over the underlying data.

PersonaNeed
Ecodesign expert / consultantEncode a robust, explainable modeling once, decide which assumptions another person should adapt, and distribute the result as a file.
Product owner, engineer, or client consuming the templateAnswer a small, relevant set of questions and see the resulting footprint without navigating or accidentally restructuring the expert modeling.
Any file holder acting in either roleMove between the guided experience, normal modeling, and template construction without needing a different file or additional permission.

“Template maker” and “consumer” describe what someone is doing at a given moment, not different account roles. A consumer may inspect or revise the template; a maker may use the consumption view to test it. The only default is the opening mode.

Why now: e-footprint already supports deep modeling, explainable results, and portable JSON round-trips. A simplified-input layer makes that expert work reusable by the interface's primary non-technical audience and directly serves its principle of “no one left behind, depth available on demand.”

2. Success criteria

Each criterion is user-observable and testable.

  • Create from real work: from normal modeling mode, any user can enter template construction mode and choose a subset of the modeling's editable inputs to expose.
  • Portable handoff: the expert can export one self-contained JSON file carrying the complete modeling and its simplified-input definition. No account, server-side library, or separate companion file is required to use it.
  • Predictable opening mode: a normal modeling JSON opens in modeling mode. A JSON containing a simplified-template definition opens in template consumption mode by default, regardless of who created or opened it.
  • Only the intended choices: in template consumption mode, only the inputs selected in template construction mode are editable. Hidden inputs and structural actions cannot be changed accidentally through that mode.
  • Familiar input context: Simplified inputs identifies every exposed field using its existing field label together with the owning object's existing type and name; template makers do not need to invent a separate category or labeling system.
  • Adapt and calculate: a consumer can change the exposed inputs using their normal input types, receives the same validation guarantees as full editing, and can view results recalculated from the adapted values.
  • Focused timeseries editing: an exposed timeseries appears as a condensed field within the same owning-object container as ordinary inputs. Its Edit action opens a field-only side panel containing the compatible strategy selector, the selected strategy's complete editor, and its preview; only one timeseries is edited at a time.
  • Timeseries strategies remain available: a consumer can switch among the compatible timeseries strategies available in normal editing. Saving the panel persists the selected strategy and authored inputs, closes the panel, and refreshes the condensed summary.
  • No collateral mutation: saving a simplified input changes that input and its legitimate calculated consequences, but does not rewrite unrelated hidden assumptions or the simplified-input definition.
  • Three explicit modes: a visible, consistently placed control lets any file holder move among template consumption (“Simplified inputs”), normal modeling (“Modeling”), and template construction (“Template setup”) without exporting or reopening the JSON.
  • Depth remains available: switching to modeling mode makes every assumption and structural action available, with clear copy explaining that the simplified guardrails no longer apply. This is a usability boundary, not an access-control mechanism.
  • Resume template work: switching to template construction mode lets the same user edit which inputs the template exposes and export an updated templated JSON without needing the original pre-template file.
  • Faithful round-trip: repeated export and reopen cycles preserve the complete modeling, current adapted values, and simplified-input choices. A file that still contains a template continues to open in template consumption mode by default.
  • Safe failure: an invalid template definition or unreadable JSON is rejected with an actionable explanation and does not replace the modeling already open in the session.

3. Scope

Capability-level only. File paths, classes, schema shape, rendering strategy, and migration mechanics belong in plan.html.
In scope
  • Entering template construction mode from a normal modeling and creating a simplified template from it.
  • Selecting which existing modeling inputs are editable in template consumption mode.
  • A small template identity for orientation: a name and an explanation of what the consumer is adapting.
  • Three visibly distinct modes over the same in-session modeling: normal modeling, template construction, and template consumption.
  • A dedicated template consumption mode that groups exposed inputs into a focused editing surface, labels the current mode, validates changes, and keeps results available.
  • Organizing the focused surface with the existing modeling hierarchy: each input keeps its normal field label and is shown under its owning object's type and name.
  • Timeseries exposed as one composite field inside its normal owning-object group: a condensed summary on the main surface and a dedicated side panel for its strategy selector, full editor, validation, and preview.
  • Full control of the exposed timeseries, including changing to any compatible editable strategy, while keeping the complexity of only one timeseries open at a time.
  • A consistent mode control for moving among all three modes without changing files.
  • A JSON round-trip containing both the complete modeling and the simplified-input definition.
  • Opening normal JSON in modeling mode and templated JSON in template consumption mode by default.
  • Equal access to all three modes for every holder of a templated JSON; no maker/consumer permission distinction.
  • Preserving source, confidence, comment, unit, and explanatory context already associated with an exposed input wherever the normal editor supports them.
  • Non-destructive validation and recovery when an uploaded template cannot be used.
Out of scope (this iteration)
  • Using hidden inputs as secrets, locking full editing, passwords, roles, digital signatures, or author-only permissions.
  • Publishing templates to a hosted catalogue, stable public URLs, discovery, or server-side persistence. File exchange remains the sharing mechanism.
  • Multi-user collaborative editing of one modeling.
  • Changing or simplifying e-footprint's calculation semantics. The template controls which existing inputs are presented; it does not introduce a second modeling engine.
  • Automatically deciding which inputs are important or generating a template from heuristics.
  • Spreadsheet, YAML, XML, or other template formats.
  • Template version history, merging independently adapted copies, or syncing a consumer copy when the expert later changes the source template.
  • Multiple alternative simplified experiences inside one file.
  • A separate read-only full-model exploration mode. A user who wants to inspect the complete modeling switches to Modeling, where they are trusted to avoid unintended changes.
  • Selecting or locking individual nested parts of a timeseries, such as one profile baseline or one weekly time range. The timeseries is exposed as a whole.
  • Custom template categories, custom field labels, or a second naming hierarchy independent of the modeling's existing object types, object names, and field labels.

5. Constraints

  • Mission fit: the default experience serves a non-technical consumer, while the full depth remains available on demand as required by specs/mission.md.
  • The library remains the modeling truth: simplified inputs must update the same underlying e-footprint modeling and produce the same validations, calculations, derivations, and JSON-compatible values as full editing. No calculation logic may be reimplemented by the interface (specs/constitution.md §1.3).
  • JSON remains the only portable format: this feature extends the user-visible JSON round-trip rather than introducing an alternative serialization format, consistent with the e-footprint mission and constitution.
  • Existing file safety still applies: import must validate before replacing session state, calculated outputs must be verified or recomputed under the established rules, and a failed open must leave the current modeling intact.
  • File contents are transparent: because the complete modeling is needed for calculation, audit, and resuming full editing, every assumption is present in the JSON. The UI must not imply that unexposed inputs are confidential or tamper-proof.
  • Architecture and interaction: implementation must preserve Clean Architecture dependency direction and the HTMX-first, minimal-JavaScript principle (specs/constitution.md §1.1 and §1.4).
  • No backward-compatibility burden: the two repositories are co-developed; the plan should favor one clear format and migration path over parallel legacy behavior.
  • Desktop first and English only: existing constitutional product constraints continue to apply.

6. Open questions

  1. Other selectable input shapes: beyond scalar inputs, choices, and complete timeseries editors, must v1 also expose relationships and weighted collections?
  2. Comparison workspace: when a simplified-template file is opened or added in a two-model workspace, should its Simplified inputs view apply independently and still allow it to participate in comparison, or is the feature single-model only in v1?
  3. Template definition after modeling edits: if Modeling removes or replaces an input that the simplified definition exposes, should export be blocked until Template setup is repaired, or should stale selections be dropped with a warning?

7. Resuming from cold context

  1. Read this file end to end and resolve its open capability questions with the product owner.
  2. Read plan.html (when written) for the JSON contract, interaction architecture, ordered implementation steps, and test gates.
  3. Re-read specs/architecture.md, especially persistence, workspace files, normal input editing, and modeling templates.
  4. Read specs/design/journeys/save-and-load.html and specs/design/journeys/build-a-model.html for the current file and editing experiences.
  5. Read the companion library's specs/architecture/index.html and serialization pages before deciding whether the JSON contract belongs wholly to interface metadata or requires a coordinated library change.
