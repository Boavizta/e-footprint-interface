Simplified inputs

Status: Spec — under review · 2026-09-23

1. Problem and audience

An ecodesign expert can build a faithful modeling, but that modeling may contain dozens of interdependent objects and assumptions. A colleague who only needs to adapt a few business variables must currently enter the same full editing experience, understand which inputs are safe to change, and avoid disturbing the expert's underlying structure.

This feature adds a simplified-input definition to a complete modeling, exposing a deliberately chosen subset of inputs. The definition travels with the modeling in the same self-contained JSON file. Opening a file with selected inputs leads with those inputs, so another person can adapt the modeling without first learning its full construction. Every file holder can move between Modeling, Simplified inputs, and simplified-input configuration; simplification guides the user but does not conceal, secure, or create ownership over the underlying data.

Every modeling in the workspace has one simplified-input definition, initially empty. Experts can populate it while creating or editing objects and while reviewing individual inputs in Results → Sources, without interrupting their modeling workflow. Reference and comparison modelings each own their selection and guidance.

The definition stores field membership and presentation metadata only. Current values, source, confidence, and comment belong to the e-footprint modeling part of the JSON. Selecting an input never captures its initial value or creates a default to restore later. To preserve a baseline, save the JSON or use the comparison feature.

PersonaNeed
Ecodesign expert / consultantEncode a robust, explainable modeling once, decide which assumptions another person should adapt, and distribute the result as a file.
Product owner, engineer, or client using Simplified inputsAnswer a small, relevant set of questions and see the resulting footprint without navigating or accidentally restructuring the expert modeling.
Any file holder acting in either roleMove between the guided experience, normal modeling, and simplified-input configuration without needing a different file or additional permission.

“Modeling author” and “user” describe activities, not different account roles. Anyone can configure the simplified inputs or use them to adapt values. JSON-opening defaults depend on whether inputs are selected, not on who opens the file.

Terminology: Simplified inputs is a configurable view of an existing modeling, not a template used to create another one. Configure opens the Configure simplified inputs view, where the author selects fields and writes help; editing values happens in Simplified inputs or Modeling. A JSON file carries a modeling with simplified inputs, not a separate template.

Separately, the ready-made modelings currently called “templates” in the interface and library will be renamed examples in a dedicated ride-along refactor. An example is a complete modeling to learn from or start from; any modeling, including an example, can have simplified inputs.

Why now: e-footprint already supports deep modeling, explainable results, and portable JSON round-trips. A simplified-input layer makes that expert work reusable by the interface's primary non-technical audience and directly serves its principle of “no one left behind, depth available on demand.”

2. Success criteria

Each criterion is user-observable and testable.

  • Build the selection while modeling: every modeling always has a simplified-input definition, possibly empty. An expert can include inputs and write optional help in creation panels, editing panels, and individual rows in Results → Sources, or review the whole selection through Configure. Including the first input needs no separate creation or naming step.
  • Empty is a valid state: removing the last selected input or choosing Clear simplified inputs empties the selection; it does not delete a separate entity or change any modeling values. The empty Simplified inputs view offers Choose inputs. Retained guidance alone does not make the selection non-empty.
  • Confirm clearing simplified inputs: Clear simplified inputs opens a native browser confirmation warning that it removes all selected inputs and all custom per-field help, including help retained on previously deselected inputs. The modeling's values, sources, confidence, and comments remain unchanged. Confirming clears the draft selection and per-field help only; the view's title and general guidance remain. Save and return applies the change; cancelling the confirmation changes nothing, and cancelling configuration restores the saved selection and help.
  • Portable handoff: the expert can export one self-contained JSON file carrying the complete modeling and its simplified-input definition. No account, server-side library, or separate companion file is required to use it.
  • JSON-only opening defaults: when a modeling is loaded from JSON, at least one selected input opens Simplified inputs; zero selected inputs opens Modeling. This rule applies independently to each modeling in a workspace file, initially showing the active modeling. Adding or removing selected inputs never automatically navigates away from the current view.
  • Independent workspace context: reference and comparison modelings each retain their own selection, help text, values, and last base view (Modeling or Simplified inputs). Switching between them restores that base view instead of reapplying JSON-opening defaults. Configure is a temporary editing session: save or discard its changes before leaving, with no draft or layout restoration on return. Duplicating a modeling copies its selection and guidance, after which both copies evolve independently.
  • One source of values: Simplified inputs reads and edits the modeling's actual values. The simplified-input configuration has no initial-value snapshot, default values, or reset-to-defaults action. Removing and re-including an input preserves its current modeling value; JSON saves and comparison modelings provide baselines when needed.
  • Only the intended choices: in Simplified inputs, only the inputs included in its definition are editable. Hidden inputs and structural actions cannot be changed accidentally through that mode.
  • Bounded input scope: eligible fields are numerical inputs, whole editable timeseries, and selects that do not edit object relationships. Country, Network, and Device selectors are explicit exceptions: these familiar reference objects are not shown in the model builder. Their normal single- or multiple-selection behavior is preserved. Other structural relationships and weighted object collections cannot be exposed.
  • Complete conditional choices: including a controlling select also includes its dependent inputs, recursively, using the modeling's existing conditional-choice rules. For example, including Provider also includes Model; Model may be included alone with Provider fixed. Configuration and inline controls explain any automatically included fields and prevent removing a required dependent while its controller remains included. No separate dependency configuration is authored. If a required dependent cannot be exposed, its controller cannot be exposed either, with an explanation. Clear, undo, and selections reopened from normal exports respect the same invariant.
  • Valid conditional changes: changing a controlling value retains each dependent value when still valid; otherwise the first valid available option is selected and the automatic change is reported discreetly. This fallback is not a recommendation. The controller and all affected dependent values save together, never as an invalid intermediate combination. If there is no valid option, the entire change is rejected with an explanation and saved values stay intact.
  • Familiar input context: Simplified inputs identifies every exposed field using its existing field label together with the owning object's existing type and name; modeling authors do not need to invent a separate category or labeling system.
  • Scales to many objects: Simplified inputs provides a left-hand Navigation section grouped by existing object type and a single scrollable main pane with collapsible object-type and object levels. Selecting an object in Navigation expands its ancestors and brings it into view. Within each object only, exposed fields use up to three columns when space permits, falling back to two or one without mixing fields from different objects.
  • Efficient navigation: users can expand or collapse all modeled sections, see exposed-input counts on object headers, and retain their expansion state while working. The first object and any object containing a validation error open automatically.
  • Focus configuration on selected objects: Configure simplified inputs offers Only objects with selected inputs, off by default. Enabling it filters both Navigation and the main pane to objects with at least one selected input in the current draft; empty object types are hidden too. All eligible fields within a matching object remain available. Deselecting its last input removes that object from the filtered view, without deleting its help or other data. An empty result offers Show all objects to turn the filter off. Filtering never changes membership, help, or values. Every entry into Configure starts at the top with the filter off and the first object open; scroll position, expansion and filter choices are not remembered after leaving.
  • Per-field guidance: in configuration or any inline simplified-input disclosure, the author can optionally add custom help text. In Simplified inputs, non-empty help is displayed as authored, preserving capitalization, immediately below the field name; an empty help value leaves no placeholder or gap.
  • Editable source and comment: for every exposed input, a user can view and edit the source, confidence, and comment through the same compact disclosure below its value, including for timeseries inputs.
  • Adapt and calculate: a user can change the exposed inputs using their normal input types, receives the same validation guarantees as full editing, and can view results recalculated from the adapted values.
  • Autosave simple edits: numerical inputs and text metadata save on blur or Enter, not on every keystroke; selects save on change. Source, confidence, and comment follow the same rules. There is no Apply simple changes action. Discreet status distinguishes saving, saved, and failed changes. A rejected save shows the existing error modal and replaces the attempted field with its accepted repository value, marked Not saved; the rejected value is not retained. Native browser validation remains available; invalid fields open their object.
  • One save at a time: while a save is running, temporarily disable further edits, structural actions, view/model switching and export across the workspace. Re-enable them when the request finishes; a rejected edit leaves the accepted field visible and does not block navigation. Users can still read and scroll. Do not collect further edits for later submission. There is no form-wide commit button or automatic/manual saving preference in this iteration.
  • Focused timeseries editing: an exposed timeseries uses the same field layout as an ordinary input within its owning-object container. In place of a standard value control it shows a read-only string preview and a small Edit timeseries action. That action opens a field-only side panel containing the compatible strategy selector and the selected strategy's complete editor. On tablet and desktop, its visual preview appears immediately to the left of the side panel, over the workspace, as in the existing timeseries editor—not below the form. On phones the preview returns to the panel's form flow. Only one timeseries and its preview are active at a time; switching strategy replaces the preview, and closing the editor closes both.
  • Timeseries strategies remain available: a user can switch among the compatible timeseries strategies available in normal editing. Saving the panel persists the selected strategy and authored inputs together, closes the panel, and refreshes the string preview. These timeseries edits remain a draft until Save timeseries; Cancel discards them. A rejected save shows the existing error modal, closes the panel, and restores the accepted field value. Switching models reuses the ordinary side-panel unsaved-changes warning: stay to save first, or discard and switch. Returning does not reopen that editor or restore its draft. Ordinary modeling panels and Configure retain their explicit Save / Cancel boundaries.
  • No collateral mutation: saving a simplified input changes that input and its legitimate calculated consequences, but does not rewrite unrelated hidden assumptions or the simplified-input definition.
  • Clear navigation: in Modeling, a Simplified inputs button sits beside the edge-modeling toggle. Simplified inputs provides a Modeling button to return. The edge-modeling toggle appears only in Modeling, never in Simplified inputs or its configuration view. Within Simplified inputs, Configure opens Configure simplified inputs; Save and return or Cancel returns to Simplified inputs. These transitions use the same loaded JSON.
  • One familiar application shell: the global navbar, workspace tabs, active modeling's toolbar, and normal file controls remain available in Modeling, Simplified inputs, and configuration. The existing Export affordance exports this modeling or both modelings; there is no separate adapted-JSON download. Show results leads to the normal Results and Sources tabs without leaving the current modeling view. Compact layouts retain the usual model switcher and toolbar menu.
  • Footprint at a glance: the top-right Show results control and the existing bottom Results banner display the same total footprint for the active modeling. A tooltip explains that it covers manufacturing and use over the entire modeling period, not an annualized rate; units adapt to the magnitude. The bottom banner keeps Results on the left, its expansion chevron in the middle, and the total on the right. The top quick-result affordance stays visible outside the compact toolbar menu. Both are available in Modeling and Simplified inputs.
  • Trustworthy live totals: both displays refresh together after a successful simplified-input save, timeseries save, or modeling mutation, including side-panel saves, creation, and deletion. Switching reference/comparison shows the active modeling's total. While saving they indicate updating; after failure they identify the last saved result, not a result for unsaved edits. A non-computable modeling shows no numeric total and retains the existing disabled-results explanation. Opening the results panel is not required to refresh the total.
  • Export follows completed saves: the ordinary export actions cannot run while a relevant save is in flight, including a final field committed when focus leaves it. Exporting both modelings waits for both. Every export entry point is protected, including menu links, with no extra confirmation for this wait. A focused edit that fails or is invalid cancels that export activation; later exports use the accepted saved values. Configure uses its Save / Discard / Stay exit guard. Ordinary modeling panels retain their current export behavior, without a new unsaved-changes warning: exports contain saved values, not unfinished panel edits, including timeseries drafts.
  • Familiar configuration: configuration and Simplified inputs share Navigation, two disclosure levels, field order, and responsive grid of up to three columns per object. With the filter off, configuration reveals every object with eligible inputs in Navigation and the main pane, including objects with no fields currently exposed. Within each object, all eligible inputs appear with inclusion checkboxes and optional help-text controls. Objects and inputs added in Modeling are available on the next entry into configuration, unchecked unless included during creation or required by an already included controlling field. Current values are shown for context; Simplified inputs shows only the saved selection. Saving applies membership and help changes together; Cancel leaves the saved configuration intact. Leaving with unsaved changes offers Save / Discard / Stay, including model switching, Compare, Results/Sources, file opening and export. Save continues only after success; a failed Configure save keeps its draft and exit guard available. Opening Sources therefore cannot make inline configuration changes alongside a Configure draft.
  • Depth remains available: switching to Modeling makes every assumption and structural action available. Mode labels and navigation communicate the current view without permanent instructional or permission banners. Autosave explanations remain inside expanded simplified-input controls; contextual warnings appear only when relevant, such as on deletion. This is a usability boundary, not an access-control mechanism.
  • Discreet inline authoring: every eligible input in creation/editing panels and individual-input Sources rows has a small clickable bookmark: outlined when excluded, filled when included. Hover/focus explains its state. Clicking only opens a compact inline disclosure with Include in Simplified inputs and optional help text; it never toggles membership by itself. At most one disclosure is open per surface, keeping the form or table readable.
  • Immediate changes for existing inputs: inclusion changes save immediately; help text saves when leaving its field. Both are independent of the object's Save button and do not submit unsaved modeling values. A discreet status distinguishes saving, saved, and failed changes; a failed save shows the existing error modal without clearing the surrounding value draft, remains retryable and must not claim success. Cancelling value edits does not undo saved simplified-input settings. Individually deselecting an input, inline or in the configuration overview, retains its help for re-inclusion, unlike Clear simplified inputs. An Undo action makes an accidental inline membership change recoverable.
  • Creation is provisional: for an object not yet created, membership and help remain part of the creation draft, visibly labeled Included when this object is created. They are committed only on successful creation; cancellation or failed validation creates no simplified-input references. Server-side creation failures use the existing error modal and discard the creation form.
  • Required inputs are visible before creation: if a new object's input is required by an already included controlling field, it appears included and required in the creation panel. For example, creating a video job linked to an API whose Model is included automatically includes the job's Resolution. Its bookmark still opens the help-text editor, but removal is unavailable; hover or keyboard focus explains “Required because [API name] → Model is included in Simplified inputs.” Changing the chosen API recalculates the requirement. Removal becomes available once no included controller requires the field; the lock is not permanent. The required selection and its help save with successful creation, never before. No additional success notice is needed for inclusion already shown in the panel; any further automatic inclusion discovered on save is named discreetly.
  • Warn before removing exposed fields: when an object being deleted contains fields exposed through Simplified inputs, its existing deletion confirmation and unchanged actions are extended with a warning that identifies the affected fields and explains that they will be removed from Simplified inputs. Confirming removes the object and those simplified-input references together, leaving no stale selections.
  • Resume configuration: choosing Configure in Simplified inputs lets the same user change the selection and guidance, then export an updated modeling with simplified inputs without needing an earlier file.
  • Faithful round-trip: repeated export and reopen cycles preserve the complete modeling, current adapted values, simplified-input choices, per-field help text, and user edits to source and comment in the modeling itself. Each modeling with a non-empty selection opens in Simplified inputs when loaded from JSON; an empty selection opens in Modeling.
  • Safe failure: an invalid simplified-input configuration save is rejected with an actionable explanation and leaves the saved definition and modeling unchanged. An unreadable JSON file, or model data rejected by the existing import and size checks, does not replace the modeling already open in the session. File opening does not revalidate a saved simplified-input definition.
  • Consistent examples terminology: ready-made modelings are called Examples in the catalog, Open examples in navigation, and example modelings in documentation. Onboarding offers Start from an example or Start from scratch. Introductory examples and examples accompanying how-to guides remain loadable and editable with the same contents and guide associations in both the interface and library; the rename does not change their modeling behavior.

3. Scope

Capability-level only. File paths, classes, schema shape, rendering strategy, and migration mechanics belong in plan.html.
In scope
  • One always-associated, possibly empty simplified-input definition for each workspace modeling.
  • Inline membership and help-text authoring in creation/editing panels and Results → Sources, plus a dedicated overview editor. Sources already lists individual sourced inputs.
  • Selecting numerical inputs, whole editable timeseries, and non-relationship selects; Country, Network, and Device selectors are the only object-relationship exceptions.
  • Conditional selection completeness and atomic dependent-value fallbacks, derived from existing modeling rules rather than an additional author-maintained dependency configuration.
  • Autosaving simple values and provenance metadata, with visible save-failure status and export protection; explicit Save / Cancel for timeseries and configuration drafts.
  • A synchronized active-model total in the top-right Show results control and bottom Results banner, refreshed on successful modeling changes and unavailable when computation is impossible.
  • A title and general guidance for orientation: an explanation of what the user is adapting.
  • Two main destinations over the same in-session modeling: Modeling and Simplified inputs, with configuration entered from within Simplified inputs.
  • A dedicated Simplified inputs view that groups exposed inputs into a focused editing surface, labels the current mode, validates changes, and keeps results available.
  • Organizing the focused surface with the existing modeling hierarchy: each input keeps its normal field label and is shown under its owning object's type and name.
  • A shared configuration and Simplified inputs workspace with a left Navigation section, one main scrolling pane, two collapsible hierarchy levels, exposed-input counts, object navigation, and global expand/collapse controls. On narrower layouts Navigation provides a compact object selector.
  • An optional configuration-only filter, Only objects with selected inputs, driven by the draft selection. Navigation and the main pane stay synchronized; matching objects retain all their eligible fields. An empty filtered view offers Show all objects. Filtering is view state, not a mutation of simplified-input settings or modeling values.
  • A responsive grid of up to three field columns within each object. Width changes, including opening the timeseries side panel, may reflow fields inside that object but never interleave fields from different objects.
  • Inclusion controls and help-text editing alongside current-value previews in the same compact field layout. With its filter off, configuration shows all objects with eligible inputs and all their eligible fields, including objects and inputs absent from the selection or newly added in Modeling. These remain unselected unless included during creation or required by an included controller; Simplified inputs shows only saved exposed fields and hides objects with no exposed fields.
  • Optional custom help text for every exposed field, authored in the overview or inline and shown unchanged directly below that field's existing label in Simplified inputs.
  • Timeseries exposed as one composite field inside its normal owning-object group, using the same label, help, and Source and comment disclosure as ordinary inputs. A read-only string preview and Edit timeseries action replace the ordinary value control; a dedicated side panel contains the strategy selector, full editor, and validation. The active visual preview sits to the left of the side panel on tablet/desktop, matching the existing editor; on phones it sits in the form flow. This applies to hourly, weekly, and other compatible strategies.
  • Full control of the exposed timeseries, including changing to any compatible editable strategy, while keeping the complexity of only one timeseries open at a time.
  • A Simplified inputs button beside the edge-modeling toggle in Modeling, and a Modeling return button in Simplified inputs. No edge-modeling toggle in Simplified inputs; Configure and Save and return / Cancel manage configuration within that surface.
  • Clear simplified inputs removes the entire selection and all per-field help after browser confirmation, including help on deselected fields. The overview's Save and return / Cancel semantics still apply; modeling data, the title, and general guidance are unchanged.
  • A JSON round-trip containing both the complete modeling and the simplified-input definition.
  • Reusing the existing navbar, workspace tabs, modeling toolbar, normal Export menu, and Results/Sources navigation in the simplified experience; no special simplified-input download.
  • Choosing the initial view only on JSON load: empty selection → Modeling; non-empty selection → Simplified inputs. Workspace switching restores each modeling's last base view; Configure must first be saved or discarded and starts fresh on re-entry.
  • Independent reference/comparison definitions, duplication, and per-model or workspace JSON round-trips. Neither definition contains initial or current input values.
  • Equal access to Modeling, Simplified inputs, and configuration for every holder of a modeling JSON; no author/user permission distinction.
  • Discreet, keyboard-accessible outlined/filled bookmarks that disclose membership and help controls on demand, with immediate persistence for existing inputs and provisional creation settings.
  • An additional warning inside the existing object-deletion confirmation when the object contains exposed fields, followed by atomic removal of the object and its simplified-input references.
  • Showing the current source, confidence, and comment for every exposed input and letting the user edit them in Simplified inputs without separately exposing those metadata fields in configuration. Other context such as units remains available wherever the normal editor supports it.
  • Validate all uploaded models and their combined size before replacing the current workspace.
  • A dedicated ride-along refactor renames the existing ready-made modelings from templates to examples throughout both the interface and library, including developer-facing terminology and documentation. This must be its own task in the implementation run, not just a UI-label change; the draft plan records the coordinated scope and acceptance checks.
Out of scope (this iteration)
  • Using hidden inputs as secrets, locking full editing, passwords, roles, digital signatures, or author-only permissions.
  • Publishing user-authored modelings to a hosted catalogue, stable public URLs, discovery, or server-side persistence. File exchange remains the sharing mechanism.
  • Multi-user collaborative editing of one modeling.
  • Changing or simplifying e-footprint's calculation semantics. The simplified-input configuration controls which existing inputs are presented; it does not introduce a second modeling engine.
  • Automatically deciding which inputs are important or generating a selection from heuristics.
  • Spreadsheet, YAML, XML, or other simplified-input exchange formats.
  • Configuration version history, merging independently adapted copies, or syncing a user's copy when the expert later changes the source modeling.
  • Multiple alternative simplified-input definitions for the same modeling. A workspace file may contain two modelings, each with its own definition.
  • Configuration-owned initial values, defaults, snapshots, or a reset-to-defaults action.
  • Queued background autosaves, a form-wide batch commit for simple inputs, or a user-selectable automatic/manual saving mode. Timeseries, normal modeling panels and Configure keep Save / Cancel.
  • A separate read-only full-model exploration mode. A user who wants to inspect the complete modeling switches to Modeling, where they are trusted to avoid unintended changes.
  • Selecting or locking individual nested parts of a timeseries, such as one profile baseline or one weekly time range. The timeseries is exposed as a whole.
  • Editing structural object relationships or weighted object collections through Simplified inputs, except the existing Country, Network, and Device selectors.
  • Custom simplified-input categories, custom field labels, or a second naming hierarchy independent of the modeling's existing object types, object names, and field labels. Per-field help text supplements those labels but does not replace them.

5. Constraints

  • Mission fit: the default experience serves a non-technical user, while the full depth remains available on demand as required by specs/mission.md.
  • The library remains the modeling truth: simplified inputs must update the same underlying e-footprint modeling and produce the same validations, calculations, derivations, and JSON-compatible values as full editing. No calculation logic may be reimplemented by the interface (specs/constitution.md §1.3).
  • JSON remains the only portable format: this feature extends the user-visible JSON round-trip rather than introducing an alternative serialization format, consistent with the e-footprint mission and constitution.
  • Check imports before replacing: complete existing model-loading and combined-size checks before replacing session state. Calculated outputs are verified or recomputed under the established rules. Rejection at these checks leaves the current workspace intact.
  • File contents are transparent: because the complete modeling is needed for calculation, audit, and resuming full editing, every assumption is present in the JSON. The UI must not imply that unexposed inputs are confidential or tamper-proof.
  • Architecture and interaction: implementation must preserve Clean Architecture dependency direction and the HTMX-first, minimal-JavaScript principle (specs/constitution.md §1.1 and §1.4).
  • No backward-compatibility burden: the two repositories are co-developed; the plan should favor one clear format and migration path over parallel legacy behavior.
  • Desktop first and English only: existing constitutional product constraints continue to apply.

6. Open questions

No blocking capability questions remain. Input eligibility, conditional choices, autosave, accepted-field restoration after rejected saves, export protection, and the two quick-total displays are settled above. Ordinary modeling-panel and Configure draft handling remains distinct.

7. Resuming from cold context
