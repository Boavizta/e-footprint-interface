Simplified inputs — Draft implementation plan

Status: Draft — captured during specification · 2026-09-21 · Feature spec

This is not the complete or approved feature plan. It preserves the explicitly requested cross-repo ride-along refactor. The simplified-input persistence and interaction design still need the planning stage; no application or library implementation is authorized by this draft.

1. Approach

The feature is called Simplified inputs. Its settings select existing fields and attach guidance; they do not instantiate a modeling or own copies of its values. Use simplified-input configuration terminology throughout the eventual feature implementation, matching the spec and mockup.

Separately, rename the existing ready-made modeling catalog from templates to examples in depth across both repositories. These are complete editable modelings used as starting points and to accompany documentation, not simplified-input configurations. Keep their contents and behavior unchanged.

Required standalone task in this feature's implementation run: Rename ready-made modeling templates to examples across the library and interface. When tasks are generated, reserve one dedicated task in the driving interface repository's tasks.md, with explicit library and interface portions and its own review and verification. Do not bury this work inside a simplified-input UI task or create a separate feature run. Final ordering is settled during planning; complete the coordinated rename before wiring new code to catalog APIs so the feature does not introduce fresh references to the old terminology.

3. Cross-cutting concerns and task acceptance

  • Coordinated API cutover: both repositories and every in-repo caller use the new names. No legacy alias package, dual API, or deprecated compatibility layer is added.
  • Behavior preservation: every catalog entry still opens the same modeling, with editable input values and the same guide links. Scratch, file opening, replace confirmation, replaying the tour, and Help navigation still work.
  • Verification: run library and interface catalog/registry/authoring tests, import and JSON round-trip checks, and critical picker/deep-link browser tests. Check package resource inclusion and run strict documentation builds to catch stale links and imports. Complete the normal constitutional test gates in both repositories before declaring the task done.
  • Terminology audit: search source, file paths, routes, fixtures, scripts, and live documentation in both repositories for the retired ready-made-modeling terminology. Resolve each remaining occurrence deliberately. Django/Jinja templates, native HTML templates, generic document/code templates, and historical mentions explaining this rename are not rename targets.
  • Migrations: this catalog rename is not a modeling-schema change. Preserve example identifiers and serialized modeling contents. Audit any persisted catalog-specific keys; if a necessary rename changes a serialized contract, specify its migration before implementing it rather than silently breaking JSON imports.
  • Independent review: keep the rename identifiable as its own task, with its cross-repo changes and test evidence reviewed independently of simplified-input functionality.

4. Risks

  • Renaming only the UI leaves two competing vocabularies. Audit developer-facing names and documentation as well as displayed labels.
  • Moving packages can break resource loading or authoring commands despite successful imports. Verify packaged JSON resources, regeneration, and the interface's shared-library examples.
  • Route and selector changes can break navigation, guide deep links, or the tour. Update producers and consumers together and exercise the complete flows.
  • A blind text replacement would damage unrelated rendering templates. Limit the rename to the ready-made modeling concept and review every remaining match in context.

5. Alternatives considered

  • UI-only relabeling: rejected; the user requested an in-depth rename across both repositories.
  • Archetypes or scenarios: examples is clearer for editable learning material and avoids implying authoritative reference architectures or conflating examples with comparison alternatives.
  • Calling the new feature a template: rejected; simplified inputs are a view and configuration attached to any modeling, including an example.

6. Constitutional notes

Preserve Clean Architecture, library ownership of modeling logic, and the interface's HTMX-first rendering. Both repositories are co-developed without a backward-compatibility burden. No constitutional amendment or calculation change is required by this rename. The normal dependency, test, documentation, and release gates still apply when implementation runs.

7. Open planning work

The main feature still needs its JSON/configuration contract, validation and eligibility rules, per-model persistence, view restoration, inline versus overview save boundaries, UI integration, and test strategy. Resolve the spec's input-shape question before emitting the full task list. Preserve the dedicated examples-rename task while completing that plan.
