Simplified inputs — Draft implementation plan

Status: Draft — captured during specification · 2026-09-23 · Feature spec

This is not the complete or approved feature plan. It preserves the explicitly requested cross-repo ride-along refactor and the technical decisions agreed during specification. Persistence, request coordination, and the complete implementation sequence still need the planning stage; no application or library implementation is authorized by this draft.

1. Approach

The feature is called Simplified inputs. Its settings select existing fields and attach guidance; they do not instantiate a modeling or own copies of its values. Use simplified-input configuration terminology throughout the eventual feature implementation, matching the spec and mockup.

Separately, rename the existing ready-made modeling catalog from templates to examples in depth across both repositories. These are complete editable modelings used as starting points and to accompany documentation, not simplified-input configurations. Keep their contents and behavior unchanged.

Required standalone task in this feature's implementation run: Rename ready-made modeling templates to examples across the library and interface. When tasks are generated, reserve one dedicated task in the driving interface repository's tasks.md, with explicit library and interface portions and its own review and verification. Do not bury this work inside a simplified-input UI task or create a separate feature run. Final ordering is settled during planning; complete the coordinated rename before wiring new code to catalog APIs so the feature does not introduce fresh references to the old terminology.

Accepted technical decisions to carry into planning

  • Derive conditional dependencies: use the existing library objects' conditional_list_values metadata, including depends_on, for membership closure and value reconciliation. Do not add a Provider → Model special case or a second simplified-input dependency schema. The Ecologits external API is only one example; audit multi-hop chains and cross-object dotted dependencies as well. A controller is not safely exposable unless its complete affected dependent closure can also be exposed.
  • One atomic modeling edit: compute the valid option lists in dependency order, retain valid dependent values, otherwise choose the first valid option, and validate/persist the whole affected set once. Reject the whole edit if any required list is empty. Server-side domain validation is authoritative. Existing dynamic_forms.js clears stale choices; it does not currently implement this first-valid fallback, so reuse/adapt deliberately rather than assuming current form behavior already meets the spec.
  • Eligibility and metadata: allow numerical inputs, supported editable timeseries builders, and non-relationship selects, plus Country, Network, and Device references. Preserve collection cardinality for the existing multiple-Device selector; do not turn that exception into support for arbitrary relationship collections. Reuse source/confidence/comment editing semantics, including confidence invalidation on value changes.
  • Save boundaries: simple values and provenance commit on blur/Enter or select change; a timeseries strategy and its payload commit together through the existing explicit panel Save. Configuration overview is still an explicit draft; existing-input inline membership and help remain independent autosaves. Serialize/coalesce requests per modeling and prevent late responses from overwriting newer state. Keep failed drafts recoverable and never reserialize modeling data just to save membership/help.
  • Reuse the eagerly materialized total: ModelWeb.persist_to_cache() already pulls System.total_footprint. Obtain its sum and existing display-quantity formatting from the library; do not build charts or the Sankey matrix for the quick display. Render both total-bearing Results controls from one presentation value in the same response.
  • Extend existing OOB results updates: results_buttons already renders both toolbar and bottom Results controls. Currently the mutation helper emits this region when creation/computability constraints change. Also refresh it after every successful relevant modeling mutation even when computability is unchanged; retain the disabled-results reason when computation is unavailable. Workspace switches must render the active slot's total.
  • Explicit export protection: do not assume HTMX disables all export actions. Single-model download and the two-model dropdown items are ordinary links; disabling a dropdown button is insufficient. Guard every export path while relevant commits are queued or in flight, including blur-before-click ordering, and cover both slots for workspace export. Failed autosaves need an explicit recover/discard path before they can be mistaken for exported values. Reuse existing save/discard semantics for explicit panel/configuration drafts; no new in-flight modal.

3. Cross-cutting concerns and task acceptance

Feature verification to expand during planning: test allowed/rejected input shapes, multiple devices, transitive and cross-object conditional closure, dependent-only selection, valid-value retention, first-valid fallback, empty-list rollback, and selection undo/clear/import validation. Cover blur/Enter/change saves, field metadata, failure/retry, rapid edits and late responses, final-blur export, both-model export, explicit drafts, and per-model restoration. Assert synchronized totals after successful edits/create/delete and workspace switches, unchanged saved totals on failure, and no numeric result when non-computable. Browser tests should cover keyboard access and compact-screen results visibility. Update the owning architecture and testing documentation for the eventual autosave/OOB patterns, and flag relevant AGENTS.md / CLAUDE.md guidance.

The dedicated examples-rename task retains its own acceptance gates:

  • Coordinated API cutover: both repositories and every in-repo caller use the new names. No legacy alias package, dual API, or deprecated compatibility layer is added.
  • Behavior preservation: every catalog entry still opens the same modeling, with editable input values and the same guide links. Scratch, file opening, replace confirmation, replaying the tour, and Help navigation still work.
  • Verification: run library and interface catalog/registry/authoring tests, import and JSON round-trip checks, and critical picker/deep-link browser tests. Check package resource inclusion and run strict documentation builds to catch stale links and imports. Complete the normal constitutional test gates in both repositories before declaring the task done.
  • Terminology audit: search source, file paths, routes, fixtures, scripts, and live documentation in both repositories for the retired ready-made-modeling terminology. Resolve each remaining occurrence deliberately. Django/Jinja templates, native HTML templates, generic document/code templates, and historical mentions explaining this rename are not rename targets.
  • Migrations: this catalog rename is not a modeling-schema change. Preserve example identifiers and serialized modeling contents. Audit any persisted catalog-specific keys; if a necessary rename changes a serialized contract, specify its migration before implementing it rather than silently breaking JSON imports.
  • Independent review: keep the rename identifiable as its own task, with its cross-repo changes and test evidence reviewed independently of simplified-input functionality.

4. Risks

  • Renaming only the UI leaves two competing vocabularies. Audit developer-facing names and documentation as well as displayed labels.
  • Moving packages can break resource loading or authoring commands despite successful imports. Verify packaged JSON resources, regeneration, and the interface's shared-library examples.
  • Route and selector changes can break navigation, guide deep links, or the tour. Update producers and consumers together and exercise the complete flows.
  • A blind text replacement would damage unrelated rendering templates. Limit the rename to the ready-made modeling concept and review every remaining match in context.
  • Concurrent field autosaves or metadata updates can lose edits when whole-model persistence races. Define per-model request coordination, atomicity, and stale-response rejection before tasks.
  • Conditional metadata can cross object boundaries or reach an ineligible input. Inventory these cases; do not silently change a hidden dependent. Reject an unsafe configuration with an actionable explanation rather than inventing a second dependency declaration.
  • Results controls may stay stale if their existing constraint-diff trigger is reused unchanged. Cover successful mutations where computability stays true, and failure paths where old totals must not appear to represent unsaved inputs.

5. Alternatives considered

  • UI-only relabeling: rejected; the user requested an in-depth rename across both repositories.
  • Archetypes or scenarios: examples is clearer for editable learning material and avoids implying authoritative reference architectures or conflating examples with comparison alternatives.
  • Calling the new feature a template: rejected; simplified inputs are a view and configuration attached to any modeling, including an example.
  • Hardcoding Provider → Model or storing duplicate dependency metadata: rejected; derive the general rule from existing conditional lists.
  • A global Apply action or saving every keystroke: rejected for simple inputs; save on a completed field edit. Keep explicit Save for the composite timeseries editor and configuration overview.

6. Constitutional notes

Preserve Clean Architecture, library ownership of modeling logic, and the interface's HTMX-first rendering. Both repositories are co-developed without a backward-compatibility burden. No constitutional amendment or calculation change is required by this rename. The normal dependency, test, documentation, and release gates still apply when implementation runs.

7. Open planning work

The main feature still needs its JSON/configuration contract, implementation of the now-settled eligibility and dependency rules, per-model persistence, request ordering and failure recovery, view/draft restoration, save/export coordination, complete UI integration, and test strategy. Decide how shared-source edits and confidence invalidation reuse existing provenance behavior, how cross-object dependency closure is resolved, and where unsupported/cyclic configurations are rejected. These are planning work, not new capability questions. Preserve the dedicated examples-rename task while completing that plan.
