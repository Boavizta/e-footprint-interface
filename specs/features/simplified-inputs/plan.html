1.1 · Define field identity and stored configuration Proposed

Files domain/services/simplified_inputs.py

Extend the existing per-model interface_config with simplified_inputs. Identify a field by owner object ID + constructor attribute name, scoped to its modeling. Never use display names, DOM IDs, or the replaceable explainable value's ID.

domain/services/simplified_inputs.pyNew · proposed data structures; imports omitted

@dataclass(frozen=True)
class FieldAddress:
    object_id: str
    attribute: str

class FieldSetting(TypedDict):
    included: bool
    help: str

class SimplifiedInputsDefinition(TypedDict):
    title: str
    guidance: str
    fields: dict[str, dict[str, FieldSetting]]
    # owner ID → attribute name → setting

Design choice: use a typed JSON-shaped definition, not a new library entity. FieldAddress is the hashable key used within a request; persisted keys remain ordinary strings. The repository owns the definition. ModelWeb continues to own only modeling data.

Serialized example, normalization and validation

  • Values and provenance stay in the modeling. Labels and ordering come from existing form contexts; view state stays in the browser. Render authored help as escaped text, preserving capitalization.

1.2 · Resolve those addresses into an eligible-field catalog Proposed

Files adapters/forms/form_field_generator.py · domain/conditional_inputs.py · adapters/forms/timeseries_builder_registry.py · domain/services/simplified_inputs.py

Reuse constructor signatures and class metadata directly. Extract only dotted-path resolution and the timeseries builder-support lookup; add simplified-input eligibility and selection rules on top.

Today · discovery and rendering are mixed together

  • adapters/forms/form_field_generator.py: generate_dynamic_form() reads constructor signatures, unwraps optional annotations, reads list_values/conditional_list_values, then creates field dictionaries containing labels, widgets, values and provenance. It also applies form-specific exclusions and ordering.
  • The same function resolves dotted depends_on paths, but turns them into dynamic_lists for one form: DOM controller IDs and option lists. On edit, a skipped relationship is treated as fixed. That output cannot tell us which fields on other objects must also be exposed.
  • adapters/forms/timeseries_builder_registry.py already owns editable strategies. build_timeseries_form_config() matches the current value to a registered builder before generating its editor context; an unfamiliar value stays read-only.

Refactor · share two helpers, leave metadata access alone

Forms and the new service both use the existing get_init_signature_params(), domain/type_annotation_utils.py and class choice dictionaries. No new metadata wrapper is needed.

Conditional paths: extract the traversal currently embedded in generate_dynamic_form() into a small domain helper. Return the final owner and attribute so forms can read its value and simplified inputs can identify its address.

domain/conditional_inputs.pyNew file · proposed extraction from form traversal

def resolve_input_path(root, path: str) -> tuple[ModelingObject, str]:
    *relationships, attribute = path.split(".")
    owner = root
    for name in relationships:
        owner = getattr(owner, name)
    return owner, attribute

Normal forms retain labels, widgets, provenance, exclusions, ordering and one-hop dynamic_lists. On creation, resolve the remaining path from each candidate reference; on edit, start from the existing object. No change to form output or browser behavior.

Timeseries support: in adapters/forms/timeseries_builder_registry.py, extract find_editable_builder(annotation, value) from build_timeseries_form_config(). Rendering and eligibility use that same lookup, but only rendering initializes strategy drafts. The existing registry stays the single source of editor support.

adapters/forms/timeseries_builder_registry.pyModified · proposed extracted lookup and boolean helper

def find_editable_builder(annotation, value) -> TimeseriesBuilderDefinition | None:
    return next(
        (builder for builder in editable_builders_for(annotation)
         if isinstance(value, builder.builder_class)),
        None,
    )

def can_edit_timeseries(annotation, value) -> bool:
    return find_editable_builder(annotation, value) is not None

Sources' constructor-input checks and the stateless preview endpoint already use the existing helpers; neither needs a metadata-lookup refactor for this feature.

Extend · add eligibility and a model-wide dependent index

domain/services/simplified_inputs.py adds feature-specific work: identify constructor inputs by owner address, apply the allowed-input policy, and index conditional dependents across the model. A widget name alone is insufficient: Country and Server references can both render as select_object, but only Country is eligible here.

domain/services/simplified_inputs.pyNew · eligibility results, not a copy of class metadata

@dataclass(frozen=True)
class FieldDescriptor:
    address: FieldAddress
    eligible: bool
    reason: str | None
    controller: FieldAddress | None

@dataclass
class FieldCatalog:
    fields: dict[FieldAddress, FieldDescriptor]
    dependents: dict[FieldAddress, list[FieldAddress]]
    # controller address → directly dependent field addresses
    # complete_selection() follows these links recursively

def build_catalog(model_web, *, can_edit_timeseries) -> FieldCatalog: ...
def complete_selection(catalog, selected) -> set[FieldAddress]: ...
def validate_definition(definition, catalog) -> None: ...

can_edit_timeseries is the ordinary Python function defined above in adapters/forms/timeseries_builder_registry.py. Pass the function itself, not its result:

  1. adapters/views/views_simplified_inputs.py imports it and supplies it when constructing the simplified-input use case.
  2. The use case in application/use_cases/simplified_inputs.py passes that function to build_catalog(model_web, can_edit_timeseries=...).
  3. build_catalog() calls it with a field's annotation and current value to check whether the field has an editor.

FieldCatalog answers two questions:

  • Can this field be included in simplified inputs?
  • If included, which other fields must accompany it?

For example, including an API's Model also requires including Resolution for every video job linked to that API.

Configuration, saving and JSON import use this same catalog to enforce consistent selections. Existing forms still provide the labels and editors.

Validation · separate existing rules from new selection checks

Reuse the library's check_belonging_to_authorized_values() for value validation. The new validator checks saved field addresses, eligibility and required companion fields. Selection traversal tracks visited addresses; it does not introduce blanket cycle rejection.

Confirmed library bug: attributes_with_depending_values() overwrites earlier dependents sharing a controller. SI-1 records the reproduction and focused library fix; do not work around it in the interface.

Agreed · required fields during creation

An API's Model is selected; a new linked video job's Resolution appears included and required before saving. Its help remains editable; removal is locked only while required. Creation saves the object and required selection together. Preview and save boundaries →

Existing video dependency. No concrete ineligible-dependent case has been found; no silent-pruning policy is proposed.

domain/object_factory.py owns prepare_input_changes(). Both the existing normal-edit function and the new use case call it; only the new use case gathers changes across owners. First-valid fallback remains specific to simplified editing.

Save order

  1. Check the addressed field is selected and eligible; reuse normal value/unit/builder conversion.
  2. Prepare dependent changes using the candidate controller values. Keep valid values; otherwise choose the first allowed value. A missing conditional branch adds no restriction; an empty allowed list rejects the change. The library remains the final validator.
  3. Apply the whole value batch with ModelingUpdate, then its prepared provenance changes, and persist once. Any failure discards the candidate model and preserves the browser draft.

Important refactor: some metadata edits currently mutate inputs immediately. Defer them too, so failed dependent validation cannot leave a changed source/comment behind. Keep existing source identity and confidence behavior, preserve omitted metadata, and do not edit shared Source records through this patch.

Request handling

  1. Simple editors enqueue on completion; normal/timeseries panels enqueue on Save. Bookmark requests contain settings only. Coalesce unsent edits to the same property, but never cancel a sent mutation.
  2. Queue saves, structural edits and model switches together. Each request carries slot/System ID and a response-generation token. Reject replaced-model targets; never overwrite a newer draft with an older response.
  3. A failed save keeps its draft and pauses dependent edits for retry/discard. Apply shared toolbar updates only for the active model; preserve ordinary save/discard safeguards on destructive navigation.
  4. Every export entry first completes the focused field and waits for the relevant models' saves. Direct links and menus use the same guard. Failed saves require retry/discard; explicit panel/configuration drafts retain their normal warning.

Configure draft versus inline saves

Store Configure edits as changed properties, not a full copied definition. A later inline save updates that property's draft/base value without wiping other edits; Save applies only the remaining changes. Cancel does not undo successful inline saves. Metadata patches likewise preserve omitted properties.

Clear sends an explicit clear-all-fields instruction after confirmation and Configure Save. Undo applies an inverse membership change and validates it against the current model.

4. Risks · where review matters

  • Partial saves: dependent values and provenance must be accepted together.
  • Import failure: old workspace data must remain reachable until the replacement succeeds.
  • Wrong-model or stale responses: queued requests and restored drafts must retain their owning model.

These are the highest-risk integration boundaries; the verification map targets them directly.

5. Alternatives considered

  • New metadata/editor registries: unnecessary; existing signatures, class metadata and the timeseries registry already supply them.
  • Separate saves for dependents: creates invalid intermediate combinations; use the library's multi-owner update instead.
  • Independent per-model queues: misses shared session state. Disabled buttons alone also miss direct download links and the final focused-field edit.
  • Full-page refreshes: discard drafts and focus; use targeted updates and retained view containers.

6. Constitutional and architectural notes

No constitutional amendment or new dependency. Eligibility belongs in the interface domain, orchestration in use cases, rendering in adapters, and modeling validation in the library. Pass the registry's editor-support function into the domain rather than importing adapters there.
