Home-page starting-point drawer — Implementation plan

Status: Draft — captured during spec-specify from the kickoff conversation; refined in the spec-plan stage · 2026-10-08 · Spec: spec.html

1. Approach

The catalog machinery already exists and is sound: domain/services/template_catalog_service.py builds the ordered groups, adapters/presenters/template_picker_presenter.py::build_picker_groups() turns them into a view model with chips and mkdocs guide URLs, and views_onboarding.py::load_template loads a chosen id into the session. None of that changes. What changes is who renders that view model and where.

Three moves:

  1. Extract the card markup from onboarding/template_picker.html into a reusable partial, so the home-page band, the home-page drawer and the existing in-builder overlay all render the same cards from the same build_picker_groups() output. The three differ only in chrome (a section heading, a drawer shell, an overlay shell) and in whether chips/guides are shown.
  2. Assemble the home-page view model in a new presenter (adapters/presenters/starting_point_presenter.py, beside the existing template_picker_presenter) and have both views.home and a new drawer endpoint import it. The presenter imports neither view module, which is what keeps e_footprint_interface.views → views_onboarding → model_builder…views from closing into a cycle. The drawer is fetched on click rather than rendered hidden at page load, so its resume state and emptiness flag are as fresh as the click.
  3. Stop auto-showing the overlay. model_builder_main passes show_template_picker=False unconditionally; is_empty_model keeps its other two jobs (the model_is_empty context flag and the blank-flavoured tour). The overlay lives on for open_template_picker (Help ▸ Open templates) and reset_model.

3. Cross-cutting concerns

  • Unit tests. tests/unit_tests/adapters/presenters/test_template_picker_presenter.py still covers build_picker_groups() unchanged. Add Jest coverage for starting_point_drawer.js (open/close, Esc, focus restore) alongside the existing onboarding_first_run.js Jest suite.
  • Integration tests. New: GET / carries the catalog context and the band renders every introductory template by name; the drawer endpoint returns the resume block only when the session model is non-empty; GET /model_builder/ on an empty session renders no #template-picker; open-template-picker still does. test_template_deeplink_view.py and test_template_catalog_service.py should keep passing untouched — a good signal the catalog layer really is unchanged.
  • E2E. tests/e2e/test_onboarding.py is the main rewrite: it currently asserts the picker appears over the canvas. New coverage — templates readable on the home page without clicking; CTA opens the drawer without changing the URL; Esc/backdrop dismisses to an untouched home page; a template click lands a filled canvas; a returning session sees Continue first. Check tests/e2e/pages/model_builder_page.py and tests/e2e/conftest.py for picker helpers other suites lean on (test_forms.py touches them) before changing their signatures. Constitution §2.1 puts this flow squarely in "critical flows" territory.
  • Migrations. None. No Django models, no serialized-model schema change.
  • Docs. specs/architecture.md and the onboarding journey (above), plus a CHANGELOG.md entry under ## [Unreleased] per constitution §2.6 — consolidated by the supervisor if this runs as a feature-implement loop.
  • Docs site. If mkdocs pages tell readers "click Start modeling, then pick a template", they now describe a drawer. Worth a grep of the docs repo before closing the feature.

4. Risks

  1. The replace-confirmation silently stops working from the home page. The existing guard reads emptiness from canvas cards in the DOM, which the home page doesn't have — so a returning visitor could lose their model with no prompt. This is the sharpest correctness risk in the feature, and the prototype shipped it wrong (a server-rendered hx-confirm, which conventions.md explicitly forbids). Decision: extend the delegated listener's emptiness resolution instead — cards when a canvas is present, otherwise a server-set flag. One mechanism, convention intact.
    Named residual: on the home page that flag is only as fresh as the page render, so a visitor who loads a model in a second tab and then clicks a band card in the first will not be prompted. Accepted, because the home page cannot mutate the session in place (the only way to change it is to leave), and the drawer's per-click refetch narrows the window to a single page view. Do not claim the flag is live — document it where it is set.
  2. The home view starts touching the session. If it accidentally seeds the scratch baseline (as model_builder_main deliberately does), every home-page visit mints a session model, is_empty_model stays true but a session is written for every anonymous visitor, and the resume logic gets muddier. Mitigation: read-only access, explicit test that GET / creates no session model.
  3. "Continue where you left off" promising work that has expired. Slot payloads live in a short-TTL cache while the workspace index lives in the long session — model_builder_main calls workspace.drop_expired_slots() for exactly this reason. The home view must reconcile the same way, or it will offer to resume a model that 500s on load.
  4. The guided tour stops auto-running, or runs at the wrong moment. Its once-ever trigger is entangled with the picker's presence (onboarding_first_run.js defers while #template-picker exists). Removing the auto-overlay changes that timing. Mitigation: explicit e2e assertion that the tour appears once on a template-loaded canvas reached from the home page.
  5. Two entry points diverging anyway. The mitigation is the shared card partial; the risk is that "the home page needs a slightly different card" erodes it. Mitigation: parameterise the partial, never fork it, and assert in an integration test that the names rendered on the home page match build_picker_groups().
  6. Home-page bloat — the thing the user explicitly wants to avoid. All five cards plus a drawer is more page than exists today, and trimming the count is no longer an available escape hatch (that decision is made). Five also does not fit one row, so the band wraps three-then-two and the tallest card sets each row's height — today that is the GenAI marketing video description, which was written for a roomy overlay. Observed in the prototype: chips stack one-per-line in a narrow column and become most of a card's visual weight. Both levers are now decided — chips stay (they are the clearest signal of what a template demonstrates, which is the band's whole purpose), and the one oversized description is shortened instead. That is the entire budget: if the band still reads as a catalogue rather than an invitation, fix it in card design — not by hiding templates or stripping chips.
  7. Losing the "just get me in" path. Today the CTA lands you somewhere; now it asks a question. Mitigation is copy, not code — "Start from scratch" must read as an obvious first-class option, not a consolation prize.

5. Alternatives considered

  • Render the drawer hidden in the home page and toggle it purely client-side. Rejected: the resume state and the replace-confirmation would be baked in at page-load time and could go stale, and it pushes state into JS against constitution §1.4. Fetching the fragment on click is both more HTMX-idiomatic and more correct.
  • Keep the auto-overlay as a safety net alongside the drawer. Rejected by the spec — a user who chose on the home page would be asked again on the canvas.
  • Delete the overlay entirely and route Help ▸ Open templates back to the home page. Rejected: switching template mid-session is a legitimate in-app action and bouncing to the home page to do it is worse than keeping a working chooser.
  • A separate /start page instead of a drawer. Rejected: an extra navigation is exactly the abruptness the feature is removing.
  • A second hand-written template list on the home page. Rejected outright — the duplication hazard is the whole reason for the shared partial.
  • Server-rendered hx-confirm on home-page cards, with a conventions.md amendment carving out freshly-fetched fragments. Rejected: it splits one guarantee across two mechanisms, and the band (rendered at page load, not fetched per click) would not even satisfy the carve-out it asked for.
  • Band cards open the drawer instead of loading directly. Rejected: it would make every confirmation decision fresh, but at the cost of the one-click template load that is the band's entire reason to exist.

6. Constitutional notes

  • §1.4 HTMX-first, minimize JS. Respected: the drawer's content is a server fragment; JS covers dismissal and focus only. The new JS module must follow conventions.md → JavaScript (IIFE, no window globals, Jest-testable export tail like onboarding_first_run.js).
  • §1.1 dependency direction. Nothing new in domain/ or application/. The catalog service stays Django-free; the presenter stays the only place that knows about CLASS_UI_CONFIG and MKDOCS_BASE_URL.
  • §2 quality gates. Critical first-run flow → e2e required; full pytest + Jest green; CHANGELOG.md entry; pyproject.toml back on the PyPI efootprint before anything reaches main.
  • §4 desktop-first. The drawer must not break narrow viewports, but is designed for desktop. No amendment needed anywhere.
  • conventions.md → JavaScript. Two rules bind this feature directly: conditional confirmation is decided at click time from live state (never a server-rendered hx-confirm), and new modules dispatch via data-action. Both are honoured rather than excepted, so no convention amendment is needed. The prototype broke both; do not copy it verbatim.
  • §3.1 never paper over a bug. Specifically relevant to risk 1: if the confirmation gap is found mid-implementation, fix it rather than dropping the assertion.

7. Open questions

Settled during the spec-plan pass (2026-10-07)
  • Where the shared context is assembled — a new adapters/presenters/starting_point_presenter.py, not views_onboarding. Breaks the import cycle the prototype worked around with a function-level import.
  • How the replace-confirmation works — extend the delegated htmx:confirm listener; see §4 risk 1 and §5.
  • Where the band sits — directly under the hero, per the spec.
  • Which namespace the drawer route lives in — model_builder, beside load-template. Confirmed workable in the prototype.
  • Whether a fetch per open is fast enough — yes; the fragment is small and the catalog build is already on the home-page path.
  • Whether the band renders how-to templates — yes, the whole templates group, no category filtering.
  • Whether band cards show concept chips — yes, the same chips the in-app chooser shows (decided 2026-10-08).
  • Whether the catalog copy is shortened for the band — yes, for the one oversized entry; the spec widens scope by that single line (decided 2026-10-08).

Still open, to resolve before or during spec-tasks:

  • What exactly carries the server-set emptiness flag — an attribute on <body>, on the band container, or a dedicated element the listener looks up. Needs to be reachable identically from the band (page render) and the drawer (per-click fetch).
  • Does the upload hand-off reuse the existing side-panel open route, or warrant its own endpoint? Depends on whether HX-Trigger-After-Settle can carry the panel URL cleanly.
