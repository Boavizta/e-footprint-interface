Home-page starting-point drawer

Status: Spec — under review · 2026-09-24

1. Problem and audience

What is wrong today. e-footprint ships four starter templates — a classical e-commerce journey, an AI chatbot, an industrial IoT fleet, a machine-learning workflow — plus the library's how-to scenarios. They are the fastest route from "I have never modeled anything" to "I am looking at a realistic model I can poke at". The home page never mentions that any of them exist. A visitor sees one call to action, Start modeling →, and has no way to know whether it leads to a blank page or a worked example.

The templates are offered, but only after the visitor has already committed: clicking the call to action swaps the whole page to the builder, and only then does a welcome overlay appear asking them to pick a starting point. Two things go wrong at that moment:

  • The choice arrives after the decision. The visitor asked to start modeling and was answered with a question. The information that would have made the call to action attractive — "there is a ready-made e-commerce model waiting" — is revealed only to people who were already willing to click into the unknown.
  • The context switch is abrupt. The overlay lands on a page the visitor has never seen, over a canvas they cannot yet read. Dismissing it leaves them on an empty canvas with no route back to the explanation they were reading a second ago.

Who experiences it. The primary audience of the whole product: a non-technical product person arriving cold, usually from a link or a talk, with no modeling background and a few minutes of curiosity. This is their very first interaction, so the severity is high — a newcomer who bounces here never sees anything else the tool does. Frequency is every single first visit.

Why now. The template catalog has just reached the point where it carries real pedagogical weight — showcased-concept chips, how-to guides attached to cards, a growing library-side set of scenarios. That investment is currently gated behind a click that gives no reason to be made. Making the catalog visible is the cheapest available improvement to first-run conversion, and it needs no new modeling capability.

2. Success criteria

Each criterion is phrased as something an observer can check in a browser or an automated test.

  1. A first-time visitor who loads the home page and scrolls, without clicking anything, can read the name and a one-line description of every starter template.
  2. Clicking a named template on the home page loads that model and lands the visitor on the canvas with it already filled in — no intermediate picker, no second confirmation for an empty session.
  3. Clicking Start modeling opens a starting-point chooser in place on the home page: the page beneath stays visible and the address bar does not change until a choice is made.
  4. The chooser offers, in one view: every starter template, start from scratch, and load an existing .e-f.json file.
  5. Dismissing the chooser (close control, backdrop click, or Esc) returns the visitor to the home page exactly as it was, with nothing loaded and no model replaced.
  6. A returning visitor whose session still holds work sees Continue where you left off as the first and visually primary option in the chooser, naming their model.
  7. Choosing a template or scratch while a non-empty model is in session asks for confirmation before replacing it; cancelling leaves the existing model untouched.
  8. After this feature ships, a visitor who reaches the canvas through the home page is never shown the welcome overlay on top of it — the starting-point question is asked exactly once, on the home page.
  9. The starting points available on the home page are always the same set, with the same names, descriptions and concept chips, as those available from the in-app template chooser. Adding a template to the catalog makes it appear in both places with no further work.
  10. Every starting point in the chooser is reachable and operable by keyboard alone, and the chooser traps focus while open.
  11. The home page's existing narrative sections — what e-footprint is, who it is for, how it works, about us — remain present and in their current order.

3. Scope

Capability-level only. File paths, class/method/parameter names, refactor instructions, internal hypotheses, and "mirror pattern X" code-level decisions belong in plan.html, not here.
In scope
  • A named-template section on the home page. A visible band presenting all four starter templates by name and description — none held back behind the drawer — positioned so a visitor meets it while reading the page rather than having to hunt for it. Each entry is itself a way in: selecting it loads that model.
  • An in-page starting-point drawer behind the main call to action. Start modeling no longer navigates; it opens a chooser over the home page containing the full set of starting points — templates, start from scratch, load a JSON file — with the home page still visible behind it.
  • A continue affordance for returning visitors. When the session already holds a model, the drawer leads with an option to resume it, named after the model, ahead of everything that would replace it.
  • Retiring the automatic welcome overlay. The canvas no longer greets an empty model with the picker. The same chooser stays reachable on demand from inside the app (help menu, and after a model reset) so a user can switch starting point mid-session.
  • A single catalog behind both surfaces, so home page and in-app chooser cannot drift apart in content or ordering.
  • Dismissal and replace-protection semantics as described in §2.
  • Keyboard and screen-reader operability of the drawer and the template band.
  • Updating the onboarding journey documentation to describe the new first ninety seconds.
Out of scope (this iteration)
  • Changing the template catalog itself — no new templates, no renamed or re-described ones, no re-grouping. This feature changes where the catalog is shown, not what is in it.
  • Previews of a template's contents before loading it — a thumbnail of the canvas, an impact figure, a sample result. Worth considering later; not needed to make the names visible.
  • Search, filtering or tag-based browsing of templates. The catalog is small enough to read at a glance; adding navigation to it would be the overwhelm the feature is trying to avoid.
  • Changing the guided tour that runs once the canvas loads.
  • Changing the JSON import experience itself. The drawer routes to the existing import flow; that flow is unchanged.
  • Anything about the rest of the home page's copy or layout beyond inserting the template band.
  • Mobile-first treatment. Desktop-first per the constitution; the drawer must remain usable on a narrow viewport but is not designed for it.
  • Persisting which template a user chose, or personalising the home page on repeat visits beyond the continue affordance.

5. Constraints

  • Constitution §1.4 — HTMX-first, minimize JS. The drawer is a partial update over the home page, not a client-side route. Any JavaScript is vanilla and confined to opening, closing and focus management.
  • Constitution §4 — no SPA framework. "In-page drawer" means an overlay served and dismissed within the existing page, not client-side routing.
  • Constitution §4 — desktop-first. The drawer must not break on a narrow viewport, but mobile is best-effort.
  • Mission — "no one left behind, depth available on demand." The band must read as an invitation, not a wall of options. All four starter templates are shown inline (decided), so the burden of keeping the page calm falls on layout and copy density rather than on hiding options — compact cards, short descriptions, one row if the width allows.
  • Session model, not user accounts. "Continue where you left off" can only mean the current session's model. A visitor returning after their session expired sees the ordinary drawer; the continue option must never promise work that is gone.
  • One catalog, two surfaces. Templates, descriptions, concept chips and how-to links come from the catalog the app already owns. Neither surface may carry its own hand-written list.
  • The existing deep link into a named scenario stays working — documentation links that load a scenario directly are unaffected by this change.
  • Quality gates (constitution §2) apply: this is a critical first-run flow, so it warrants end-to-end coverage alongside unit and integration tests.

6. Open questions

  • How many templates go in the home-page band? Decided (2026-09-24): all four introductory templates, inline. Discoverability wins over page calm here — a template the visitor cannot see is a template that does not exist to them. Keeping the page calm is now a layout and copy-density problem (see §5), not a reason to hide options.
  • Where does the band sit? Directly under the hero (maximum visibility, but pushes the explanatory sections down) or after "How does it work?" (read in context, but below the fold). Leaning toward directly under the hero, since a visitor who already knows they want to try should not have to scroll past the pitch.
  • Do the library's how-to scenarios appear on the home page at all, or only in the drawer and the in-app chooser? They are more pedagogical than exemplary and there will be more of them over time, which argues for drawer-only.
  • Does the main call to action keep its current label? "Start modeling →" now opens a question rather than starting anything. A label naming the choice may set expectations better, at the cost of sounding less decisive.
  • Should the drawer be dismissible into a "just start" path — i.e. does closing it ever mean "go to a blank canvas"? Current answer is no: closing returns to the home page and scratch is an explicit option. Confirm this is not frustrating in practice.
