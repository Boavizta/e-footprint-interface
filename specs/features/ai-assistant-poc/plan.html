1. Follow the interactions through the code

1.1 · Shared: the sandbox becomes a package

An empty ai_sandbox/__init__.py lets the view import build_system(), complete() and resolve_genai() directly. The sandbox's own scripts keep their sys.path trick, so nothing changes for the CLI. parse_json() and validate_tolerating_extras() move to dsl.py because both paths of the view need them.

The assistant model comes from settings.AI_ASSISTANT_MODEL, default claude-haiku-5-5, which must be a key of MODELS. The provider key is read from the environment by the adapter as today; load_dotenv is not called from Django.

1.2 · Empty model → generate

The view mirrors load_example(). Emptiness is not model_web.usage_patterns and not model_web.edge_usage_patterns on the active slot (ModelWeb.usage_patterns). Sequence:

  1. complete(model, system_prompt, description) with the sandbox system prompt.
  2. parse_json → validate_tolerating_extras → build_system. The catalog resolutions are kept for the feedback line.
  3. system_to_json(system, save_computed_state=False) to a dict, then load_system_into_session() on the active repository, exactly as the example loader does. Reloading through the import service is what validates the payload; no second json_to_system round trip.
  4. render_model_builder() with show_example_picker=False and an ai_feedback context dict.

Any exception in steps 1 to 3 is caught in one place, formatted as "stage: message", and rendered in the same builder response with the model untouched. No retry, no JSON repair beyond what parse_json already does.

1.3 · Non-empty model → edit

system_to_dsl(model_web.system) produces the DSL dict the LLM reads, one object per library object the DSL covers, each with its library id and the field values the builder would have set, read back through the same unit conversions in reverse. Comments on those values come back into comments. Objects or attributes outside the vocabulary are not represented; the feedback copy says that hand-set values on such fields may be reset.

The edit prompt gives the DSL and the request and asks for:

{"edits": [
   {"op": "set", "section": "usage_patterns", "id": "...", "field": "volume", "value": {"value": 5200000, "per": "month"}},
   {"op": "add", "section": "jobs", "object": {"name": "Push notification", "server": "API server"}},
   {"op": "remove", "section": "jobs", "id": "..."}],
 "note": "one sentence on what was changed and what was assumed"}

apply_edits checks each edit: known section, known id for set and remove, a field of that section's spec for set, and raises with the offending edit otherwise. References inside objects stay by name, as in the DSL today; a removed object that is still referenced fails at build_system with its existing error. The patched dict goes through validate_tolerating_extras and build_system, then the same load and render as the generate path. Ids are not preserved across the rebuild: the canvas re-renders fully anyway.

Edit operations instead of RFC 6902 JSON Patch

Three named operations addressed by section and id are easier for the model to get right than index-based paths over a list, and easier to validate and to echo in the feedback. The cost is a 30-line applier instead of a dependency.

1.4 · Feedback line

From the Completion: latency, cost_usd(model), token counts. The footprint uses ecologits.tracers.utils.llm_impacts(provider, model_name, output_token_count, request_latency) with the EcoLogits provider and model resolved by resolve_genai from the entry in MODELS; its gwp.value is in kg and is shown in mg. Only one call per request, so the line is computed in the view, no new persistence. The generate path lists the DSL's open_questions; the edit path shows the note and the applied edits.

1.5 · The box

Included from model_builder_main.html right under the toolbar include, guarded by settings.AI_ASSISTANT_ENABLED exposed through the existing context. A plain form with hx-post, hx-target="#main-content-block", hx-disabled-elt="this" and hx-indicator on the button. The hint, placeholder and button label are chosen server-side from the emptiness flag. The feedback block renders from ai_feedback when present.

2. Delivery and verification

Implementation sequence

  1. Package the sandbox, move the two helpers, add the settings flags and the dependency change.
  2. Generate path: view, route, template, feedback line. Deployable after this step.
  3. to_dsl.py with a round-trip check on the handwritten smart-building case: build → to_dsl → build gives the same total footprint.
  4. Edit path: prompt, patching.py, the branch in the view.
  5. Changelog, flag on in the dev app's environment with the key, smoke in a browser.

Gates: poetry run pytest tests --ignore=tests/e2e and the dependency test on pyproject.toml. No E2E test: the flow is a form POST already covered by the integration tests and the feature lives one day.

3. Decisions for review

  • Code stays under ai_sandbox/ rather than model_builder/, so deleting the experiment is deleting a folder and one view. The view is the only Django-aware piece.
  • The whole builder re-renders on every assistant response, success or failure, so there is a single HTMX target and no out-of-band swap to maintain.
  • Edits rebuild the system from the patched DSL instead of applying attribute writes through the use cases. Simpler, and matches the generate path; the price is lost ids and lost non-DSL values, both accepted in the spec.
  • Default model claude-haiku-5-5, the sandbox winner on quality per dollar. The three open-weight models were added to the sandbox after the comparison and are untested at the time of writing; switching is one environment variable.
