1.4 · Submit on a non-empty model: edit

Implemented with IMPL-DECISION-01 to 04; the rename rule needs supervisor resolution

Files ai_sandbox/edit.py · ai_sandbox/prompts/edit_prompt.md · ai_sandbox/dsl.py · views_ai_assistant.py

The non-empty branch of the view reads the current model back into the DSL, sends it with the request, applies the answer to the live model and persists once:

model_builder/adapters/views/views_ai_assistant.py Implemented, abridged: the else branch of 1.3

current = json.dumps(system_to_dsl(model_web), indent=1)
completion = complete(model, EDIT_PROMPT, f"Current model:\n{current}\n\nRequest: {prompt}")
data, _, error = parse_json(completion.text)
if data is None:
    raise AssistantError(f"The answer is not JSON: {error}")
feedback["applied"] = apply_edits(data, model_web)   # mutates the in-memory model, raises on the first problem
persist_structural_change(model_web, input_catalog)  # the only write of this path (IMPL-DECISION-03)
feedback["note"] = data.get("note", "")

Reading the model back. system_to_dsl(model_web) in edit.py is the mirror of the builders: servers from ModelWeb.servers (cloud_provider/instance_type for a Boavizta server, kind: "gpu" and gpus for a GPU server, storage_gb from the storage), GenAI APIs from ModelWeb.external_apis, jobs, steps and journeys by walking ModelWeb.usage_patterns. Numeric fields are the tables of 1.1 in reverse, read as value.value.to(unit).magnitude on the underlying pint quantity (see IMPL-DECISION-01), with each value's comment back under comments. A usage pattern's volume and growth_pct_per_year are read from the form_inputs of its ExplainableHourlyQuantitiesFromFormInputs when the series is one, otherwise as the yearly total; the device archetype comes from the default device names ("Default smartphone" → smartphone), anything else is passed as the device's name. Steps and jobs are weighted dicts in the library (a job called twice has weight 2); the DSL lists the name as many times as its weight, the way the handwritten case already does. The read-back is lossy on purpose: what the DSL cannot say, the assistant cannot see or change, and it stays in the model untouched.

[IMPL-DECISION-01] — APPLIED · newly discovered pre-existing library behavior, task 2 review

The plan and the task 2 brief prescribed value.to(unit).magnitude for the read-back. In efootprint 27.0.0 ExplainableQuantity.to() converts in place (self.value = self.value.to(...), returns self), so reading the model back changed the live objects' units: the handwritten case's API server storage went from TB to GB, the chatbot and IoT examples' request_duration from ms to s, the video and IoT examples' data_transferred from MB to kB. Footprints were unchanged, but task 3 reads the model back before every edit and persists at the end, so each successful assistant edit would have silently saved the user's display units converted.

_read_fields() now converts the underlying pint quantity (value.value.to(unit).magnitude) and leaves the ExplainableQuantity alone. The round-trip test test_reading_a_built_model_back_rebuilds_the_same_footprint asserts the exported model is identical before and after system_to_dsl; it failed before the fix. Rule carried into task 3: never read a live value through ExplainableQuantity.to().

The answer. The addendum edit_prompt.md is appended to the generation prompt, so the vocabulary is taught once. It asks for the objects that change, each reduced to its name and the fields that change, and for removals by name:

ai_sandbox/prompts/edit_prompt.md Payload the model writes and apply_edits consumes, illustrative

{"changed": {
   "usage_patterns": [{"name": "Browsing", "volume": {"value": 5200000, "per": "month"},
                       "comments": {"volume": "Doubled as asked"}}],
   "jobs": [{"name": "Push notification", "server": "API server", "data_transferred_kb": 2}],
   "journeys": [{"name": "Browse recipes",
                 "steps": [{"name": "Open feed", "jobs": ["Recipe list", "Recipe query", "Recipe thumbnails", "Push notification"]}]}]},
 "removed": {"jobs": ["Photo upload"]},
 "note": "one sentence on what was changed and what was assumed"}

Rules the prompt states and apply_edits enforces: matched by name within its section (two objects with the same name in a section fail the request, naming them); a known name with fields is a set of those fields, an omitted field is unchanged; an unknown name is a new object and must be complete, it is validated with the section's existing pydantic class (JobSpec.model_validate and so on); a journey's steps and a step's jobs re-list all their children, new steps as full objects, jobs by name only since jobs are top level. No ids: names are what the DSL already uses for every reference and what the sandbox showed small models copy reliably, and dropping the id keeps the pydantic specs unchanged. No null-reset and no tolerance comparison: a present field is set, except that a field echoed with its read-back value and no new comment is ignored, and a child left out of a re-list is deleted once nothing uses it (IMPL-DECISION-04).

Applying. apply_edits(answer, model_web) builds the name lookups from the same walk as system_to_dsl, then works in order: the changed sections in dependency order (servers, APIs, jobs, journeys with their steps, usage patterns; each entry is added or set in place), the dropped-children cleanup, then the removals in reverse order. Everything mutates the hydrated library model behind model_web; the library recomputes and validates on each assignment through ModelingObject.__setattr__.

  • Set a table field: setattr(obj, attr, SourceValue(value * unit, comment=comments.get(field))). Verified today on the handwritten case: setting a job's data transferred recomputed the total.
  • Set volume or growth: pattern.hourly_occurrences = _volume_timeseries(volume_spec, growth, comment, horizon=...) with _volume_timeseries(); the half the answer omits is read from the current form_inputs, or growth 0 when the current series is not a form one. The horizon keeps the current start date and duration (_horizon()). Verified today.
  • Set server sizing or GenAI model: merge the given fields with the current ones, call resolve_cloud_instance or resolve_genai, and set provider and instance_type (or provider and model_name) in one ModelingUpdate batch so the conditional pair changes together. Only on a Boavizta cloud server or an EcoLogits API; a plain Server fails the request with that reason. Confirmed in the final code at _set_servers(); a change of cloud_provider alone keeps the current instance name, snapped to the new catalog.
  • Add: the builder of that kind from 1.1 with the current lookups and a _Shared seeded from the model; each created object, and the storage, devices, network and country it carries, is registered with ModelWeb.add_new_efootprint_object_to_system(), which already follows one level of attributes. A new usage pattern is appended to system.usage_patterns as pre_add_to_system() does. Verified today.
  • Re-list children: step.jobs = to_weighted_explainable_object_dict([objects by name], weight_label=...) with the library's to_weighted_explainable_object_dict(), the same constructor sugar the step's __init__ uses; repetition gives the weight. A plain list assignment is refused by the library (verified today), hence the helper.
  • Remove: DeleteObjectUseCase(model_web, input_catalog), its check_can_delete() then _delete() rather than execute(), because execute persists to the session through persist_structural_change and the request must persist only once it has fully succeeded. A blocked delete fails the request with the use case's reason.
  • Not expressible: device, network, country, kind, renames and null values fail the request with "not supported by the assistant in this experiment; change it by hand". A rename cannot be detected: without ids, a renamed object is an unknown name and is added as a new object by add() while the old one stays, so the prompt forbids renames and the model is never damaged by one (the duplicate is visible and removable). Resolved by the supervisor on 2026-10-29: a refusal is not possible with name-only matching and the no-ids choice above stands.

Atomicity costs nothing: the model is mutated in memory and persist_structural_change() (which ends in persist_to_cache(), see IMPL-DECISION-03) runs after the last operation, so a failure anywhere leaves the session's model as it was and the handler of 1.3 re-hydrates a fresh ModelWeb for the render. Because the live model is edited, every id, every value outside the DSL vocabulary and every source, confidence and comment the user set survive, which is success criterion 2.

[PLAN-UPDATE-01] — ACCEPTED · Edits are applied to the library model through the sandbox builders, not through the form use cases

Decision (2026-10-29): sets and adds mutate the hydrated library objects through the per-object builders and field tables of 1.1; only removals use the delete use case's internals (_delete()). The spec's §1 and §3 clauses about "the interface's own create, edit and delete paths" are edited accordingly.

Rationale: the use-case route would be a second DSL-to-library mapping written in the parsed-form shapes create_efootprint_obj_from_parsed_data() expects, and every use case persists immediately through persist_structural_change(), so "nothing half-applied" would need a session snapshot. Hand-set values, ids, sources, confidence and comments still survive (success criterion 2); what is lost is the form path's conditional-choice repair, replaced by setting a provider and its resolved instance type together and failing visibly if the library refuses the pair.

[IMPL-DECISION-02] — APPLIED · newly discovered pre-existing defect, task 3 review (commit 0ac6b40c)

An answer removing a job and then its server (or API) failed with AttributeError: 'NoneType' object has no attribute 'efootprint_class'. Deleting the job leaves a detached contextual wrapper on the server whose modeling_obj_container is None; the library's own modeling_obj_containers skips such entries, but the interface's ModelingObjectWeb.efootprint_contextual_modeling_obj_containers did not, so the list and dict container properties built on it crashed, and with them DeleteObjectUseCase.check_can_delete() on the server. The same crash is the bug-fixes-2026-10 task 4 report (GitHub #151, a recurrent need's delete re-render); that task is now marked shipped by this commit and its reproduction's expected-failure marker is removed.

Fix: the property filters out detached entries, matching the library's rule in the one place both derived properties read. Regression: test_check_can_delete_ignores_a_referrer_deleted_in_the_same_model. List-held referrers (a pattern holding a journey) never had the problem. The CHANGELOG carries the fix line the bug batch called for.

[IMPL-DECISION-03] — APPLIED · material plan difference, task 3 review

The plan's single write was ModelWeb.persist_to_cache(). Every form create and delete in the app writes through persist_structural_change(), which reconciles the simplified-input bookmarks in interface_config before the same persist_to_cache(); DeleteObjectUseCase.execute() is _delete() plus that call. Persisting with the bare method left a removed object's bookmarked simplified inputs dangling in the session config. The view now calls persist_structural_change(model_web, input_catalog) at views_ai_assistant.py: still the single write of the path, after the last mutation, and it restores the config when the write fails. Row 2 bookmarks a field of the removed job and asserts the bookmark is dropped (test_edit_changes_only_what_is_asked).

[IMPL-DECISION-04] — APPLIED · material plan difference and lasting complexity in apply_edits(), task 3 implementation and review

Orphans from a re-list. The plan let a re-list simply replace a step's jobs or a journey's steps. Two defects followed: a job left out of a step stayed in the saved model as an orphan that neither the canvas nor the read-back can show, and a step left out of a journey was deleted at once even when another journey still used it. The form path's edit_with_cascade_cleanup deletes orphaned children, so the assistant now does the same: each re-list in _Edits._set_journeys() and _Edits._set_step() records the children it drops; after all changed entries, and before the explicit removals, every dropped child that nothing uses any more is deleted through the same _Edits.remove(). A job moved to another step survives. remove() tracks deleted ids and lists the steps and jobs a delete cascaded to, so an answer removing a pattern, its journey and the journey's job in one go works and the feedback names every deletion once. The prompt addendum states the rule.

Weights the DSL cannot say. A surviving step keeps its own weight object in a journey re-list and a job whose count is unchanged keeps its weight object in a step re-list, so hand-set sources and comments on weights survive; a step re-list where a surviving job's weight is fractional is refused with the plan's "change it by hand" message rather than rounded.

Echoes. The plan said "a present field is set, full stop". Small models repeat whole objects, and the read-back rounds to six significant figures and converts units, so an echoed value is not always equal to the live one: echoing it replaced the value, its source and its comment, an echoed volume rebuilt the series (flattening an uploaded, non-form series to a constant) and every echo produced a misleading "set …" line. _Edits.change() now compares each entry with its system_to_dsl read-back through _changed_fields() and drops a field with the same value and no new comment before dispatch; describing-only fields (kind, a job's server/genai_api, a pattern's journey, device, network, country) are accepted when echoed and refused when different, under that one rule. Known limit: a describing-only field echoed with a new comment counts as changed and is refused. Tests: test_an_echoed_field_keeps_its_hand_set_source_and_comment and test_a_re_list_deletes_only_the_children_nothing_else_uses.

Cost accepted. apply_edits carries a dropped-children list, a removed-id set and a read-back comparison that future maintainers must keep aligned with system_to_dsl; this is the price of editing the live model without a second mapping and without silently destroying what the assistant could not see.

Considered and kept out: edit as a regeneration

Sending the DSL of the current model plus the request and rebuilding from the full answer would delete apply_edits and the builder refactor, about half of this step. It was rejected at kickoff and the code confirms why: the builder turns every CPU server into a Boavizta cloud instance (build_system(), 30 to 40x the footprint of a plain Server per the README), flattens any non-form timeseries to a constant, and resets every value outside the DSL. A tester starting from an example and asking for one change would watch the total move for unrelated reasons. The implementation sequence keeps it as the cut line instead: after step B the generate path ships alone.

3. Decisions for review

  • Three plan updates accepted at the tasks stage, PLAN-UPDATE-01, PLAN-UPDATE-02 and PLAN-UPDATE-03; the spec was edited to match. The task breakdown is in tasks.md: task 1 is step A (plus the two moved helpers and the changelog line), task 2 is steps B and C, task 3 is step D and the README paragraph; the dev-app part of step E is a deployment gate.

  • Route always registered, view 404s when off (1.3). Observationally the same as the spec's "route exists only when the flag is set"; the tests set the flag with the settings fixture.
  • Vocabulary of edits is deliberately partial (1.4): device, network, country, kind, renames and resets fail visibly. The spec already allows "an edit the assistant cannot express fails the whole request with the reason shown"; this lists what that is for the hackathon. Renames are not refused by a check yet (see the open point in 1.4).
  • Whole-builder re-render on every answer, one HTMX target, no OOB regions.
  • Cut line: step A alone is a demoable generate-only assistant; D is the only step that can be dropped without touching the others.
