1. Follow the interactions through the code

1.1 · Shared: the sandbox becomes a package, web vocabulary only

The interface uses the web subset of the DSL: servers, genai_apis, jobs, journeys and usage_patterns. The generation prompt the view sends is a copy of the sandbox prompt without its edge content; system_to_dsl and the edit prompt cover the same five sections. The pydantic specs and build_system are unchanged, the edge sections simply stay empty. The sandbox CLI keeps the full prompt so case 3 still runs there.

An empty ai_sandbox/__init__.py lets the view import build_system(), complete() and resolve_genai() directly. The sandbox's own scripts keep their sys.path trick, so nothing changes for the CLI. parse_json() and validate_tolerating_extras() move to dsl.py because both paths of the view need them.

The selectable models are DEFAULT_MODELS, posted with the form as model and remembered in the session under one key so the select reopens on the last choice; the first choice defaults to the first entry. A posted model outside the list is rejected. A model whose provider key is absent from the environment is rendered disabled, using the key check from list_models(). The price table is MODELS. The provider keys are read from the environment by the adapters as today; load_dotenv is not called from Django.

1.2 · Empty model → generate

The view mirrors load_example(). The view first refuses a model where ModelWeb.has_edge_objects is true, rendering the builder with the refusal as feedback. Emptiness is then not model_web.usage_patterns on the active slot (ModelWeb.usage_patterns). Sequence:

  1. complete(model, system_prompt, description) with the sandbox system prompt.
  2. parse_json → validate_tolerating_extras → build_system. The catalog resolutions are kept for the feedback line.
  3. system_to_json(system, save_computed_state=False) to a dict, then load_system_into_session() on the active repository, exactly as the example loader does. Reloading through the import service is what validates the payload; no second json_to_system round trip.
  4. render_model_builder() with show_example_picker=False and an ai_feedback context dict.

Any exception in steps 1 to 3 is caught in one place, formatted as "stage: message", and rendered in the same builder response with the model untouched. No retry, no JSON repair beyond what parse_json already does.

1.3 · Non-empty model → edit

system_to_dsl(model_web.system) produces the DSL dict the LLM reads, one object per library object the DSL covers, each with its library id and the field values the builder would have set, read back through the same unit conversions in reverse. Comments on those values come back into comments. The LLM answers with the objects it changes, each reduced to its id and the fields that change, plus the ids it removes:

{"changed": {
   "usage_patterns": [{"id": "...", "volume": {"value": 5200000, "per": "month"},
                       "comments": {"volume": "Doubled as asked"}}],
   "jobs": [{"name": "Push notification", "server": "API server", "data_transferred_kb": 2}]},
 "removed": ["..."],
 "note": "one sentence on what was changed and what was assumed"}

In a changed object an omitted field means unchanged, a present field is compared with the current DSL value after normalization and with a tolerance and becomes a set only when it differs, and an explicit null resets the field to the library default taken from the class's default_values. An object without an id is an add and is a normal DSL object, references by name. The format is the DSL the model already writes reliably, with no operation names or paths; a one-field edit costs a three-line object, and the model cannot alter a field it does not mention, which removes the drift of re-emitting whole objects.

Each resulting operation is translated into the input of the interface's own use case and applied to the live model, never by rebuilding it, so ids, sources, confidence, comments and every value outside the DSL vocabulary survive:

  • set → EditObjectUseCase with pre-parsed form data for the one attribute: the DSL field table gives the library attribute name and unit, the same table build_system uses through _opt. Composite fields map to their form shape: volume and growth_pct_per_year to the form-inputs timeseries, cloud_provider and instance_type through resolve_cloud_instance, GenAI provider and model_name through resolve_genai, device, network and country to the id of the matching existing object or a new archetype.
  • add → CreateObjectUseCase with the object type and the form data derived from the DSL fragment, references resolved by name to existing ids, plus the parent the DSL implies (a job's step, a step's journey, a journey's usage pattern).
  • remove → DeleteObjectUseCase after check_can_delete; a blocked delete fails the request with the use case's reason.

Operations are validated up front (known section, known id, known field, a step for a new job) and then applied in order on the session model; the first failure raises, the model is reloaded from the repository, and the error is rendered. The exact form-data shape per object type is read from the use cases' integration tests during spec-plan; that is the main unknown of this path.

Edits through the use cases, not a rebuild from the patched DSL

A rebuild was the 30-line option but reset every value outside the DSL vocabulary that the user had set by hand, and every id. Going through the use cases costs the field table and the three translations, about a day, and keeps the library and the interface as the only writers of the model. The model returns changed objects rather than JSON Patch operations or a full re-output: the first asks for a second grammar that small models get wrong, the second costs 10 to 15x the output tokens and 20 to 30 s per edit, against a product target of a cent per session.

1.4 · Feedback line

From the Completion: latency, cost_usd(model), token counts. The footprint uses ecologits.tracers.utils.llm_impacts(provider, model_name, output_token_count, request_latency) with the EcoLogits provider and model resolved by resolve_genai from the entry in MODELS; its gwp.value is in kg and is shown in mg. Only one call per request, so the line is computed in the view, no new persistence. The generate path lists the DSL's open_questions; the edit path shows the note and the applied operations. The raw answer text goes under a closed details block. The view also writes one logger.info line per call with the prompt, the model, the answer, token counts and cost; the dev app's log retention is the only storage.

1.5 · The box

Included from model_builder_main.html next to the results bar button include, positioned fixed at the lower right above the results band with its own small style block. That style block also hides the box under body.edge-modeling-on, the class edge_modeling_toggle.js drives from the toggle and the latch, so switching edge modeling on hides it without a request. The include itself is skipped when model_web.has_edge_objects, and guarded by settings.AI_ASSISTANT_ENABLED exposed through the existing context. A plain form with hx-post, hx-target="#main-content-block", the page's existing hx-disabled-elt selector so every enabled button is disabled for the duration, as the canvas container already does at model_builder_main.html, hx-indicator on the button, and a select of the models next to it. The hint, placeholder and button label are chosen server-side from the emptiness flag. The feedback block renders from ai_feedback when present.

2. Delivery and verification

Implementation sequence

  1. Package the sandbox, move the two helpers, add the settings flags and the dependency change.
  2. Generate path: view, route, template, feedback line. Deployable after this step.
  3. to_dsl.py with a round-trip check on the handwritten smart-building case: build → to_dsl → build gives the same total footprint.
  4. Edit path: prompt, the field table and edits.py, the branch in the view.
  5. Changelog, flag on in the dev app's environment with the key, smoke in a browser.

3. Decisions for review

  • Code stays under ai_sandbox/ rather than model_builder/, so deleting the experiment is deleting a folder and one view. The view is the only Django-aware piece.
  • The whole builder re-renders on every assistant response, success or failure, so there is a single HTMX target and no out-of-band swap to maintain.
  • Edits are applied through the create, edit and delete use cases; only the generate path builds a system from scratch. See the callout in 1.3.
  • The model list is the sandbox's DEFAULT_MODELS, so the interface and the sandbox compare the same set and a change in one place updates both. The first entry is the default.
