1.1 · Shared: DSL field tables and per-object builders

Files ai_sandbox/dsl.py · ai_sandbox/run.py · ai_sandbox/README.md

Today the DSL-to-library mapping is written once, inline in build_system(): each section loop calls _opt() once per numeric field with the library attribute name and unit. The edit path of 1.4 needs the same mapping twice more, to read a model back and to set one field, so the _opt arguments become tables and the loop bodies become functions. This is a pure refactor of the builder; the sandbox CLI and its --dry-run check keep working unchanged.

The cloud sizing fields (cores, ram_gb, cloud_provider, instance_type) and the GenAI provider/model_name are not in a table: they go through resolve_cloud_instance() and resolve_genai() as today, and 1.4 reuses those calls. Each builder takes name-to-object lookups (servers, apis, jobs, journeys) instead of reading the dicts build_system accumulates, which is what lets 1.4 hand them the current model's objects. _Shared gains the possibility to be seeded with existing devices, networks and countries so an edit does not add a second "Default smartphone".

parse_json() and validate_tolerating_extras() move to dsl.py because the view needs them and should not import the CLI module; run.py imports them back. The sandbox stays a folder of top-level modules: the view inserts the folder on sys.path exactly as run.py does and imports dsl, providers, catalogs and edit by those names. Turning the folder into a package would change its five internal imports and the README commands for a module that is deleted after the hackathon.

1.3 · Submit on an empty model: generate

Files views_ai_assistant.py · model_builder/urls.py · views.py · ai_sandbox/dsl.py

The form posts to ai-assistant/, registered in urls.py next to load-example. The route is always present; the view raises Http404 when the flag is off, which is what a client observes either way and spares the tests the URLconf reload that debug_urls needs for the DEBUG-only route. The view is shaped on load_example():

model_builder/adapters/views/views_ai_assistant.py Proposed

sys.path.insert(0, str(settings.BASE_DIR / "ai_sandbox"))   # same trick as ai_sandbox/run.py
from dsl import build_system, parse_json, validate_tolerating_extras
from providers import DEFAULT_MODELS, MODELS, complete
from edit import apply_edits, system_to_dsl

SYSTEM_PROMPT = (settings.BASE_DIR / "ai_sandbox/prompts/system_prompt.md").read_text()
EDIT_PROMPT = SYSTEM_PROMPT + "\n\n" + (settings.BASE_DIR / "ai_sandbox/prompts/edit_prompt.md").read_text()


class AssistantError(Exception):
    """A refusal or a failed stage; its message is shown as is."""


@require_POST
def ai_assistant(request):
    if not settings.AI_ASSISTANT_ENABLED:
        raise Http404
    workspace = SessionWorkspaceRepository(request.session)
    repository = workspace.active_repository()
    model_web = ModelWeb(repository)
    model = request.POST["model"]
    if model not in DEFAULT_MODELS:
        raise Http404
    request.session["ai_assistant_model"] = model
    prompt = request.POST["prompt"].strip()
    feedback, completion, started = {"model": model}, None, perf_counter()
    try:
        if model_web.has_edge_objects:
            raise AssistantError("This model contains edge objects, which the assistant does not handle yet.")
        if is_empty_model(model_web.system_data):
            completion = complete(model, SYSTEM_PROMPT, prompt)
            data, _, error = parse_json(completion.text)
            if data is None:
                raise AssistantError(f"The answer is not JSON: {error}")
            spec, _ = validate_tolerating_extras(data)
            system, _ = build_system(spec)
            system_data = system_to_json(system, save_computed_state=False)
            model_web = load_system_into_session(repository, system_data, workspace=workspace)
            feedback["note"] = ("Values set from the description carry a comment; values the description "
                                "does not state use library defaults.")
        else:
            ...  # 1.4
    except Exception as error:  # provider error, invalid JSON, schema, build, refusal: all shown as is
        feedback["error"] = f"{type(error).__name__}: {error}" if not isinstance(error, AssistantError) else str(error)
        model_web = ModelWeb(repository)   # the session was never written on this path
    if completion is not None:
        feedback.update(call_metrics(model, completion))   # 1.5
        feedback["raw"] = completion.text
    logger.info(...)                                        # 1.5
    return render_model_builder(request, model_web, show_example_picker=False, workspace=workspace,

Server processing follows the sandbox stages: complete (providers.complete(), one call, no retry), parse_json, validate_tolerating_extras, build_system, then system_to_json() and load_system_into_session(), the same persistence step the example loader takes. Reloading through the import service is the validation of the payload; nothing else is checked. The system prompt is the sandbox's system_prompt.md read as is: it has been web-only since the sandbox dropped edge modeling, so the kickoff draft's separate web prompt is not needed. Emptiness is is_empty_model(), the app's own definition, which render_model_builder also uses for the copy of 1.2.

Rendering: the whole builder re-renders into #main-content-block, success or failure, through render_model_builder(), which gains extra_context=None merged into its context dict (two lines). One HTMX target, no out-of-band swap, the box re-renders with the feedback because it is part of the page.

1.4 · Submit on a non-empty model: edit

Files ai_sandbox/edit.py · ai_sandbox/prompts/edit_prompt.md · ai_sandbox/dsl.py · views_ai_assistant.py

The non-empty branch of the view reads the current model back into the DSL, sends it with the request, applies the answer to the live model and persists once:

model_builder/adapters/views/views_ai_assistant.py Proposed, the else branch of 1.3

current = system_to_dsl(model_web)
completion = complete(model, EDIT_PROMPT, f"Current model:\n{json.dumps(current, indent=1)}\n\nRequest: {prompt}")
answer, _, error = parse_json(completion.text)
if answer is None:
    raise AssistantError(f"The answer is not JSON: {error}")
feedback["applied"] = apply_edits(answer, model_web)   # mutates the in-memory model, raises on the first problem
model_web.persist_to_cache()                            # the only write of this path
feedback["note"] = answer.get("note", "")

Reading the model back. system_to_dsl(model_web) in edit.py is the mirror of the builders: servers from ModelWeb.servers (cloud_provider/instance_type for a Boavizta server, kind: "gpu" and gpus for a GPU server, storage_gb from the storage), GenAI APIs from ModelWeb.external_apis, jobs, steps and journeys by walking ModelWeb.usage_patterns. Numeric fields are the tables of 1.1 in reverse, value.to(unit).magnitude, with each value's comment back under comments. A usage pattern's volume and growth_pct_per_year are read from the form_inputs of its ExplainableHourlyQuantitiesFromFormInputs when the series is one, otherwise as the yearly total; the device archetype comes from the default device names ("Default smartphone" → smartphone), anything else is passed as the device's name. Steps and jobs are weighted dicts in the library (a job called twice has weight 2); the DSL lists the name as many times as its weight, the way the handwritten case already does. The read-back is lossy on purpose: what the DSL cannot say, the assistant cannot see or change, and it stays in the model untouched.

The answer. The addendum edit_prompt.md is appended to the generation prompt, so the vocabulary is taught once. It asks for the objects that change, each reduced to its name and the fields that change, and for removals by name:

ai_sandbox/prompts/edit_prompt.md Payload the model writes and apply_edits consumes, illustrative

{"changed": {
   "usage_patterns": [{"name": "Browsing", "volume": {"value": 5200000, "per": "month"},
                       "comments": {"volume": "Doubled as asked"}}],
   "jobs": [{"name": "Push notification", "server": "API server", "data_transferred_kb": 2}],
   "journeys": [{"name": "Browse recipes",
                 "steps": [{"name": "Open feed", "jobs": ["Recipe list", "Recipe query", "Recipe thumbnails", "Push notification"]}]}]},
 "removed": {"jobs": ["Photo upload"]},
 "note": "one sentence on what was changed and what was assumed"}

Rules the prompt states and apply_edits enforces: an object is matched by name within its section (two objects with the same name in a section fail the request, naming them); a known name with fields is a set of those fields, an omitted field is unchanged; an unknown name is a new object and must be complete, it is validated with the section's existing pydantic class (JobSpec.model_validate and so on); a journey's steps and a step's jobs re-list all their children, new steps as full objects, jobs by name only since jobs are top level. No ids: names are what the DSL already uses for every reference and what the sandbox showed small models copy reliably, and dropping the id keeps the pydantic specs unchanged. No null-reset and no tolerance comparison either: a present field is set, full stop.

Applying. apply_edits(answer, model_web) builds the name lookups from the same walk as system_to_dsl, then works in order: new servers and APIs, new jobs, changed and new journeys and steps, new usage patterns, sets, removals. Everything mutates the hydrated library model behind model_web; the library recomputes and validates on each assignment through ModelingObject.__setattr__.

  • Set a table field: setattr(obj, attr, SourceValue(value * unit, comment=comments.get(field))). Verified today on the handwritten case: setting a job's data transferred recomputed the total.
  • Set volume or growth: up.hourly_occurrences = _volume_timeseries(VolumeSpec, growth, comment) with _volume_timeseries(); the half the answer omits is read from the current form_inputs, or growth 0 when the current series is not a form one. Verified today.
  • Set server sizing or GenAI model: merge the given fields with the current ones, call resolve_cloud_instance or resolve_genai, and set provider and instance_type (or provider and model_name) in one ModelingUpdate batch so the conditional pair changes together. Only on a Boavizta cloud server or an EcoLogits API; a plain Server fails the request with that reason. To confirm in implementation.
  • Add: the builder of that kind from 1.1 with the current lookups and a _Shared seeded from the model; each created object, and the storage, devices, network and country it carries, is registered with ModelWeb.add_new_efootprint_object_to_system(), which already follows one level of attributes. A new usage pattern is appended to system.usage_patterns as pre_add_to_system() does. Verified today.
  • Re-list children: step.jobs = to_weighted_explainable_object_dict([objects by name], weight_label=...) with the library's to_weighted_explainable_object_dict(), the same constructor sugar the step's __init__ uses; repetition gives the weight. A plain list assignment is refused by the library (verified today), hence the helper.
  • Remove: DeleteObjectUseCase(model_web, input_catalog), its check_can_delete() then _delete() rather than execute(), because execute persists to the session through persist_structural_change and the request must persist only once it has fully succeeded. A blocked delete fails the request with the use case's reason.
  • Not expressible: device, network, country, kind, renames and null values fail the request with "not supported by the assistant in this experiment; change it by hand".

Atomicity costs nothing: the model is mutated in memory and ModelWeb.persist_to_cache() runs after the last operation, so a failure anywhere leaves the session's model as it was and the handler of 1.3 re-hydrates a fresh ModelWeb for the render. Because the live model is edited, every id, every value outside the DSL vocabulary and every source, confidence and comment the user set survive, which is success criterion 2.

[PLAN-UPDATE-01] — PROPOSED · Edits are applied to the library model through the sandbox builders, not through the form use cases

Spec clauses: §1 "Edits go through the interface's own create, edit and delete paths, so hand-set values survive an assistant edit" and §3 "applied as a set of edits to the current model through the same paths a user's form submissions take". This is a spec change, not an implementation choice within scope.

Current: each operation is translated into CreateObjectUseCase or EditObjectUseCase input with pre-parsed form data. Proposed: sets and adds go to the hydrated library objects through the per-object builders and field tables of 1.1; only removals use the delete use case's internals.

Complexity removed: the use-case route is a second DSL-to-library mapping next to the one build_system() already is, written in the parsed-form shapes create_efootprint_obj_from_parsed_data() expects: {"value", "unit"} dicts for quantities, {id: count} dicts for weighted relationships, the form-inputs dict for a timeseries, ids of default devices and countries for references, plus the server's nested storage form data its pre_create hook reads. Each is a shape to learn and test, with no sandbox precedent. And every use case persists immediately (execute → persist_structural_change() → persist_to_cache), so "nothing half-applied" would need a snapshot of the session payload restored on failure.

User tradeoffs: hand-set values, ids, sources, confidence and comments still survive, so success criterion 2 holds. What is lost is the form path's metadata and conditional-choice repair in apply_input_edits(): a provider change is set together with the resolved instance type, and if the library refuses the pair the request fails visibly. Assistant-set values carry the library's hypothesis source and the DSL comment, as generated values do today. Architecturally an adapter mutates library objects directly, bypassing the application layer; the code is confined to the deletable experiment and the library remains the only validator.

Recommendation: accept. Uncertainties: the weighted-dict rebuild and the paired catalog update are confirmed in implementation; quantity sets, volume replacement, usage pattern append, job unlink plus self_delete and the export round trip were exercised today on the handwritten case.

Considered and kept out: edit as a regeneration

Sending the DSL of the current model plus the request and rebuilding from the full answer would delete apply_edits and the builder refactor, about half of this step. It was rejected at kickoff and the code confirms why: the builder turns every CPU server into a Boavizta cloud instance (build_system(), 30 to 40x the footprint of a plain Server per the README), flattens any non-form timeseries to a constant, and resets every value outside the DSL. A tester starting from an example and asking for one change would watch the total move for unrelated reasons. The implementation sequence keeps it as the cut line instead: after step B the generate path ships alone.

1.5 · Feedback line, log line, failures

Files views_ai_assistant.py · components/ai_assistant.html · CHANGELOG.md

call_metrics(model, completion) in the view module reads the Completion: latency_s, token counts, cost_usd(). The call's own footprint comes from EcoLogits, already installed with the library: llm_impacts(provider, model_name, output_tokens, latency_s) from ecologits.tracers.utils (site-packages, EcoLogits 0.11.3), with the provider alias from GENAI_PROVIDER_ALIASES and the catalog name from resolve_genai, so the open-weight models served by Mistral snap to their nearest Mistral catalog entry as the spec allows. Its gwp.value is a RangeValue(min, max) in kg; the line shows the midpoint in mg with "(EcoLogits)" after it.

The feedback block of the component renders, in order: model · 24.3 s · USD 0.0031 · 410 mg CO2-eq (EcoLogits); then the error in red when present, otherwise the note and, for an edit, the applied list ("set Browsing.volume to 5,200,000 per month", "added job Push notification on API server", "removed job Photo upload"); then <details>Raw answer</details> with the answer text when a call was made. A refusal before the call shows only the message.

One logger.info line per call, using the library logger the views already import: model, latency, input and output tokens, cost, then the prompt and the answer text. Nothing is stored anywhere else. The dev app's log retention is the day's record and the box says so.

[PLAN-UPDATE-02] — PROPOSED · No open questions in the generation feedback

Spec clauses: §2 first criterion "and the assistant's open questions appear under the prompt box"; §3 in scope "the assistant's open questions or its note about what it did"; the §4 mockup's fb-questions line.

Evidence: the sandbox working tree of 2026-10-29 (uncommitted) removes open_questions from ModelSpec, from the prompt and from the handwritten case, and the README records why: clarification is a separate step before generation, and the questions produced rarely targeted the dominant driver. Keeping the spec clause would mean re-adding the field against that direction.

Proposed: the generation feedback shows the metrics line, the fixed sentence about comments and defaults, and the raw answer; nothing else. Tradeoff: testers get no prompt about what to refine after a generation; the comments on values carry the assumptions instead. Recommendation: accept; on acceptance the three spec passages are edited and the mockup line removed.

CHANGELOG.md gets one line under Unreleased · Added: "Experimental, dev-only AI assistant that builds or edits the model from a description, behind AI_ASSISTANT_ENABLED."

3. Decisions for review

  • Two spec changes are proposed, PLAN-UPDATE-01 and PLAN-UPDATE-02; the rest of the plan does not depend on them except the edit mechanics of 1.4, which are provisional on 01.
  • No dependency change. The three SDKs stay in the dev group of pyproject.toml: the image runs plain poetry install, which includes that group, and pydantic and EcoLogits are already locked. Step E verifies the dev deployment does the same before relying on it.
  • Sandbox stays a folder, not a package (1.1). One sys.path line in the view module mirrors run.py; deletion is simple and the CLI is untouched. The cost is three top-level module names (dsl, providers, catalogs, edit) in the Django process.
  • Route always registered, view 404s when off (1.3). Observationally the same as the spec's "route exists only when the flag is set"; the tests set the flag with the settings fixture.
  • Vocabulary of edits is deliberately partial (1.4): device, network, country, kind, renames and resets fail visibly. The spec already allows "an edit the assistant cannot express fails the whole request with the reason shown"; this lists what that is for the hackathon.
  • Whole-builder re-render on every answer, one HTMX target, no OOB regions.
  • Cut line: step A alone is a demoable generate-only assistant; D is the only step that can be dropped without touching the others.
