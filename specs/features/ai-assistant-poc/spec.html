AI assistant proof of concept

Status: Spec — under review · 2026-10-29

1. Problem and audience

  • Problem. Building a first e-footprint model takes a product person an hour of clicking through forms they do not yet understand. The AI sandbox showed that a 2,000-token prompt turns a product description into a computable model for well under a cent, with the structure right on every case. Nobody has yet tried that from inside the interface, on their own description, and then asked for changes.
  • Audience. The five Boavizta hackathon participants, for one day on the dev deployment, plus the maintainer reading what they typed and what it cost. Not a production feature: it is removed or re-specified after the hackathon.
  • Why now. The hackathon is the one occasion with real users and real descriptions. The sandbox harness (DSL, builder, provider adapters, catalog resolvers) already exists, so the marginal work is the interface wiring and the edit path.
  • Scope tradeoffs. Web modeling only: the assistant knows nothing about edge devices, functions and deployments, which removes the hardest third of the vocabulary and the problems the sandbox found there, and cuts the prompt by about a third. No clarification questions before generation: the user is assumed to write a good description, and the assistant's open questions are shown afterwards instead. No spending guardrails: five people for a day is a couple of dollars at most. Edits go through the interface's own create, edit and delete paths, so hand-set values survive an assistant edit; the assistant's vocabulary is a subset of the library's, so some requests cannot be expressed yet and fail visibly rather than silently. Usage frequency is unverified by construction, which is what the day is for.

2. Success criteria

  • With the active model empty, submitting a product description replaces it with a computed model whose canvas renders, and the assistant's open questions appear under the prompt box.
  • With a non-empty active model, submitting a request changes the model as asked and nothing else: after "double the volume of the browsing usage pattern" that one value is doubled, and every other value, including values the user set by hand on fields the assistant does not know about, is still there with its source, confidence and comment.
  • The user can pick the assistant model among the sandbox's default models before each call; the feedback line names the model used, with latency in seconds, cost in USD and the call's own footprint in mg CO2-eq computed with EcoLogits.
  • A failed call (provider error, unparseable answer, model that does not build) leaves the current model untouched and shows the error text where the feedback line goes. Nothing is retried or hidden.
  • The prompt box and its route exist only when the deployment sets the AI_ASSISTANT_ENABLED environment variable, as the dev app does; main and production are unchanged by the merge.
  • The box is hidden while edge modeling is switched on, and absent when the active model contains edge objects; a request on such a model is refused with a message rather than applied.
  • Each path has one automated test that runs without calling a provider.

3. Scope

Capability-level only. File paths, class/method/parameter names, refactor instructions, internal hypotheses, and "mirror pattern X" code-level decisions belong in plan.html, not here.
In scope
  • A prompt box on the model builder page, visible when the feature is enabled, edge modeling is off and the active model has no edge objects.
  • Web modeling only: servers, GenAI APIs, jobs, journeys, steps and usage patterns. The assistant's vocabulary and prompts do not mention edge modeling.
  • Empty model: the description becomes a full model, built with the sandbox vocabulary and the library's defaults for what the description does not state. Numbers the description implies are estimated and carry the assistant's one-line derivation as the value's comment.
  • Non-empty model: the request is applied as a set of edits to the current model through the same paths a user's form submissions take, not a regeneration. Adding, changing and removing objects and values are all allowed in one request. An edit the assistant cannot express, or that the model rejects, fails the whole request with the reason shown; nothing is half-applied.
  • Technical feedback after each call: model, latency, cost, CO2-eq, and the assistant's open questions or its note about what it did, with the raw answer in a collapsed block underneath.
  • One server log line per call with the prompt, the model, the answer, tokens and cost, so the maintainer can read what was asked during the day; the box says so.
  • A model selector in the box, listing the sandbox's default models; the choice is kept for the session and shown in the feedback line, so testers can compare models on the same request.
  • A changelog entry marking the capability experimental and dev-only.
Out of scope (this iteration)
  • Clarification questions before generation, and any scripted or interactive question round.
  • Spending caps, rate limits, per-session quotas, abuse protection.
  • Conversation memory: each prompt is independent, the model on the canvas is the only state.
  • Streaming, progress indication beyond a disabled box while the request runs, cancellation.
  • Edge modeling: the sandbox keeps its edge vocabulary and case for a later iteration.
  • Any change to the examples, the guided tour, the simplified workspace or the comparison slot.

4. UX / interface

One box anchored at the lower right of the screen, just above the results band, present on every builder page when the flag is on. A cold visitor meets the example picker first and finds the box after it; that is poor discoverability by design, accepted because the maintainer guides the testers and it is the simplest thing to build. 5. Constraints

  • Constitution. The library stays the modeling truth: the assistant produces the sandbox vocabulary and the existing builder turns it into library objects; nothing is computed outside the library. HTMX-first, no client-side state; server failures shown as rendered.
  • Deployment. The dev app runs one web worker with a 120 s request timeout behind a 240 s proxy. A generation call takes 5 to 30 s depending on the model and the case; during that time every other request to the dev app waits. Acceptable for five testers, stated here so nobody debugs it.
  • Providers. The selectable models span three providers, so three API keys as environment variables of the dev app and the three SDKs become runtime dependencies instead of dev ones. A model whose key is missing is listed disabled. Each model must resolve to an EcoLogits catalog entry for the footprint line; the open-weight ones resolve to their nearest catalog name.
  • Lifetime. One day of testing, then AI_ASSISTANT_ENABLED is unset on the dev app and the feature is removed or re-specified with questions and guardrails. The spec folder is archived either way.
  • Changelog gate. Runtime code lands behind a flag, so it still gets its CHANGELOG.md entry, marked experimental.
