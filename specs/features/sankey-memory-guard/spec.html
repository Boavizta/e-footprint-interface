Reactive computation memory guard

Status: Approved spec · 2026-08-28

1. Problem and audience

Large e-footprint models can require several gigabytes of transient and retained memory while reactive attributes are calculated from a cold cache. Sankey attribution is by far the heaviest known path, but any operation that pulls a sufficiently large invalidated dependency cone—including a model edit, result view, import, or export—can in principle exceed the container's memory. Model complexity can grow much faster than serialized JSON size, especially with long durations and shared usage patterns, so the existing upload-size limit no longer predicts RAM demand.

  • Modelers can lose a Sankey request to a worker OOM kill, receive a generic gateway error, and experience an extended service interruption when the deployment has one instance and one worker.
  • Operators cannot currently reconstruct the worker and container memory progression that preceded the kill.
  • The problem is most severe for industrial edge models and cold Sankeys, but protection should follow reactive computations rather than be coupled to one result type.

This is worth solving now because a five-pattern model caused a real worker OOM in the 4 GiB development deployment, while a controlled clean-container reproduction peaked at only 2.76 GiB. Production progression data is needed both to explain that gap and to enforce a safe boundary.

2. Success criteria

  • In observation mode, model operations produce correlated start, bounded-progress, completion, and post-request memory evidence sufficient to distinguish worker growth, cgroup working set, reclaimable file cache, and an actual cgroup OOM kill.
  • Observation identifies whether the attribution matrix was already cached and records non-sensitive topology dimensions needed to compare runs.
  • Ordinary calculations and cache hits retain their current behavior; monitoring does not materially regress interactive latency.
  • After calibration, enforcement mode interrupts any monitored reactive operation before the container OOM-kills the worker and returns a clear generic recoverable-error explanation without corrupting the user's model.
  • A Sankey interruption replaces the graph space with guidance, the percentage of required attribution slots already cached, and the container capacity. The percentage is explicitly completion coverage, not an estimate of elapsed time, remaining work, or remaining memory.
  • An interruption during a transactional edit follows the existing ModelingUpdate error path: inputs and relationships roll back, invalidated guards are recomputed, and persistence is not reached. An interruption while computing a later result preserves the already-valid persisted edit and makes only that result unavailable.
  • The maximum unobserved memory growth near the enforcement threshold is bounded by one completed elementary reactive calculation, subject to an explicit reserve for native allocations inside that calculation.
  • The first capacity exception latches the monitor for that request so normal rollback computations cannot raise the same capacity exception repeatedly while RSS remains high.
  • Following an aborted calculation, the existing post-request full collection and controlled worker recycling restore capacity without turning the triggering response into a gateway error.
  • The extension used to observe calculations propagates through nested reactive computations within its explicit scope, is reliably restored on exit, and is inert when no observer is installed.

3. Scope

Capability-level scope only; concrete modules, callback contracts, sampling intervals, thresholds, and rollout settings belong in the accompanying implementation plan.
In scope
  • A library-level capability to observe the completion of every elementary reactive calculation, including nested calculations, within an explicitly scoped operation.
  • Low-volume, correlated memory diagnostics for model operations and worker lifecycle events.
  • A staged operating mode: disabled, observation-only, then enforced interruption after evidence-based calibration.
  • The existing generic recoverable-error experience when any computation exceeds the safe memory budget, plus specialized Sankey coverage and guidance in the graph space.
  • Repeatable Docker profiling that measures monitor overhead and validates the safety reserve.
Out of scope for this iteration
  • Predicting exact Sankey memory from model topology before calculation.
  • Preventing users from increasing model duration or adding usage patterns.
  • Changing JSON size limits or treating serialized size as a memory proxy.
  • Persisting the attribution matrix in recovery storage.
  • Evicting hourly reactive values, redesigning explainability retention, or reducing NumPy array count.
  • Adding instances, workers, or changing the hosting autoscaling policy.
  • A mathematical guarantee against an allocation spike occurring entirely inside one elementary calculation.
  • A special lightweight rollback path, rollback-time garbage collection, or removal of guard recomputation from ModelingUpdate.rollback().

4. UX / interface

Normal and cached calculations remain visually unchanged. Only the unsafe path introduces a new user-facing outcome:

The Sankey interruption is rendered in the graph space rather than as a generic error. Its wording is:

This model is too large to compute its impact repartition within the available memory. X% of the required attribution data was prepared before the memory safety limit was reached.

Reduce the model complexity—especially the number of usage patterns—or shorten the modeling timespan, then try again. You can also run the interface on an instance with more memory. This instance has Y GiB available.

X is the peek-only ratio of cached attribution slots required by this Sankey to the total required attribution slots; no value may be computed merely to produce the explanation. Y is the cgroup container capacity, not host RAM. Graph-space guidance applies once ModelWeb hydration has produced the complete system required by the coverage query. If capacity is reached earlier during hydration, the request uses the existing generic recoverable-error modal rather than fabricating a coverage percentage. Every non-Sankey operation uses that same modal carrying the capacity exception's safe message. A transactional edit rejected by the guard has already rolled back before that modal is rendered, and its persistence step is not reached.

5. Constraints

  • The primary deployment may have one 4 GiB container and one worker; protection cannot assume another instance is immediately available.
  • The monitoring path must distinguish process RSS, raw cgroup usage, inactive file cache, and cgroup working set. Container capacity must come from the cgroup rather than host RAM.
  • Logs must contain numerical topology and correlation identifiers only, never model names, serialized content, or other potentially sensitive input.
  • Heavy allocation profilers and repeated PSS/USS reads are restricted to controlled experiments, not continuous production monitoring.
  • The interface remains a consumer of e-footprint modeling behavior. The library owns the generic calculation observation capability; hosting policy and user messaging remain in the interface.
  • The current deployment uses one synchronous Gunicorn worker, so the scoped observer need not solve concurrent requests within one interpreter. Its public scope must nevertheless restore the previous observer in a finally block so exceptions and nested observer scopes cannot leak state.
  • The interface constitution's Clean Architecture direction and the library's framework/core/API dependency direction must remain intact.

6. Open questions

  • What measured reserve and transition point should enforcement use after observation-mode runs on the production architecture?
  • Should enforcement initially be limited to pre-production for one release before becoming the production default?
