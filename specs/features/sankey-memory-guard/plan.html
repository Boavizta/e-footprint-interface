Reactive computation memory guard — Implementation plan

Status: Approved plan · 2026-08-28 · Spec: spec.html

1. Approach

Add one process-local, explicitly scoped observation seam to the reactive engine. A caller-provided callback runs after each previously void ReactiveSlot completes, including slots recursively pulled by another slot. Cached reads do not emit events. The context manager restores the previous observer in finally; with no callback installed, the engine preserves current behavior with only a cheap cache-miss check. The current synchronous Gunicorn worker handles one request at a time, so ContextVar-based concurrent-request isolation is not a requirement.

A Django middleware opens that scope before any model-builder view constructs ModelWeb, so hydration, imports, edits, results, and exports are covered without a per-view opt-in list. The first rollout is observation-only: it counts every completed slot, samples memory adaptively, emits bounded structured logs, and records cgroup OOM events without raising. After calibration, the same observer's enforcement mode raises one recoverable capacity exception per request before the hard container limit. Sankey adds attribution-source cache coverage and a dedicated graph-space explanation; every other operation uses the existing generic recoverable-error presentation. Existing post-request collection and the 60% retained-working-set recycling threshold clean up or replace the worker after the response.

3. Detailed behavior and rollout

  1. Reactive notification: introduce observe_computations(callback). Its process-local scope propagates the callback to every nested cache-miss computation and restores the previous observer in finally. The callback receives the completed slot and must not mutate the model or pull reactive values. Cached reads do not notify.
  2. Callback failure: notification follows dependency replacement and cache attachment so the callback observes the completed unit's memory. If it raises, the engine drops and unlinks that just-produced value, restores the slot's previous dependency edges, unwinds the computation stack, and re-raises. Earlier successfully computed child slots may remain valid caches, as with ordinary nested computation.
  3. Operation scope: add middleware around every /model_builder/ request and enter observe_computations(monitor) before calling the inner Django handler. This covers computations made during ModelWeb construction as well as imports, edits, results, and exports without maintaining a brittle view allowlist. Emit compact summaries even when every requested value was cached; callbacks occur only for actual computations. The middleware exits the scope in finally and does no monitoring work for unrelated routes.
  4. Adaptive sampling: count every callback. Far from the tentative limit, read RSS/cgroup metrics every 16 slots. Within an initial 256 MiB warning window, sample every slot. Emit progress only after another 128 MiB high-water band, an unusually large between-sample jump, completion, or abort. In the near-limit mode, where every slot is sampled, that delta is also a single-slot jump. These are starting values for observation, not acceptance constants.
  5. Correlated evidence: structured records carry a request correlation token, privacy-safe route, HTTP method, PID, elapsed and CPU time, completed-slot count, usage-pattern count and modeled hours when available, RSS, raw cgroup current, inactive file, working set, capacity, and sampled peak. Sankey records additionally carry attribution-cache state and coverage. Slot identity is logged only for exceptional jumps and must not include user-authored names.
  6. Operating modes: COMPUTATION_MEMORY_GUARD_MODE=off|observe|enforce, defaulting to off in code. Pre-production explicitly selects observe. Enforcement is enabled only after the profiling report records architecture-specific evidence and accepted headroom.
  7. Initial enforcement hypothesis: support an absolute override and a ratio default independent of worker recycling. The candidate abort point is 80% of cgroup capacity, with no additional fixed reserve. The configured ratio and cgroup capacity resolve to one numeric threshold when the runtime-memory module initializes; every request in that worker uses the same value. Enforcement compares cgroup working set to this threshold; logs retain raw cgroup current, inactive file, and process RSS so reclaimability assumptions remain auditable. Observation must confirm that the largest between-sample increase remains comfortably below the proportional headroom on the smallest supported container.
  8. Two-threshold hysteresis: retain the existing 60% post-request recycling threshold separately from the 80% in-flight abort threshold. A worker retained above 60% would begin its next request too close to the breaker; recycling it after the response restores headroom. Both thresholds are resolved once from the same cgroup capacity, but remain independently configurable because they express different policies.
  9. Single-trip failure: enforcement raises ComputationMemoryLimitExceeded once, then latches into observation-only behavior for the remainder of that request. Existing ModelingUpdate.rollback() semantics remain unchanged: restored guards are recomputed without a second capacity exception, while the interface persists only successful edits. No rollback-time GC or special lightweight rollback path is added. The exception itself carries a privacy-safe generic explanation suitable for the existing recoverable-error modal.
  10. Sankey recovery: sankey_diagram() catches the capacity exception inside the existing generic exception decorator and returns the dedicated template in the graph space. The library helper computes X as cached impact_repartition_rows slots divided by all attribution sources required to build System.impact_repartition_matrix; it unwraps contextual relationship proxies and uses descriptor peek, never private registries or reactive pulls. Report cgroup capacity as Y GiB and describe X as attribution-source coverage, not linear progress: source slots can differ greatly in work and retained memory.
  11. Generic recovery: no change is required to render_exception_modal_if_error; decorated views render the capacity exception's generic message exactly like other recoverable failures. The middleware catches the exception only as a fallback for an undecorated model-builder route and reuses the existing modal renderer. Edits interrupted inside ModelingUpdate have already rolled back and skip persistence. Results and exports leave the valid persisted model intact. Post-request full GC runs, and the existing 60% retained-working-set rule recycles the worker when needed.
  12. OOM evidence: Gunicorn records cgroup oom/oom_kill counters at worker lifecycle boundaries so a SIGKILL can be attributed even when no request-completion log exists.

4. Cross-cutting concerns

  • Tests: library unit tests prove observer semantics and graph consistency; interface unit tests prove cgroup parsing, adaptive sampling, modes, thresholds, privacy-safe fields, and exception behavior; integration tests prove rejected edits are not persisted and guarded result failures leave session state intact. Focused E2E coverage verifies the Sankey graph-space explanation; existing generic-modal coverage serves other routes.
  • Performance gates: benchmark cache-miss computation with no observer, a no-op observer, observation mode, and enforcement-near-limit mode. The no-observer cost must be within measurement noise; observation should target at most 3% added cold-computation time, with cache-hit overhead measured separately and kept to compact milestone logging. During the initial observation rollout only, accumulate callback count, sample count, total/max callback duration, RSS/cgroup-read time, and logging time, then emit one overhead summary at request completion. Compare those figures with controlled local monitor-off/observe A/B runs. Remove the detailed timing counters after representative production runs confirm the overhead.
  • Migrations: no database, session, or JSON schema changes.
  • Docs: update the library reactive architecture/conventions and interface request-lifecycle architecture. Append calibrated runs and the final threshold rationale to performance/memory/.
  • Deployment: first deploy observe only to pre-production; preserve logs for known five-pattern, fresh-worker, result-primed, and allocator-history scenarios before approving enforcement.

5. Risks

  • Observer overhead: cgroup file reads after every slot could add seconds. Adaptive sampling keeps the callback cheap away from the limit; the profiling gate measures rather than assumes the result.
  • False safety: a getter can allocate native temporaries before returning, so the hook cannot see its internal peak. Preserve a calibrated reserve and treat the hook as a circuit breaker, not a mathematical memory bound.
  • False aborts or false safety: raw cgroup usage includes reclaimable cache, while inactive file is not guaranteed to disappear instantaneously. Decisions initially use working set; logs retain both raw current and inactive file, and observation must confirm that the proportional headroom covers observed reclaim latency and between-sample growth.
  • Graph corruption on callback failure: the observer runs after graph commit, so its exception path must explicitly drop the new value and restore previous dependency edges. Tests exercise scalar, structure, computed-dict, nested-parent, and transactional rollback cases.
  • Rollback headroom: cyclic GC remains disabled during the request, but reference counting still releases ordinary values when their references reach zero. A conservative enforcement threshold and single-trip latch leave room for the normally light guard recomputations; post-request full GC handles remaining cycles.
  • Logging pressure or data leakage: memory-band logging bounds volume; records exclude model names, values, JSON, and user-authored labels.
  • Single-worker interruption: an enforcement abort may be followed by controlled recycling. The response is produced first, but subsequent requests can briefly wait while the only worker restarts; this is preferable to an OOM and must be measured in pre-production.

6. Alternatives considered

  • Check only after each attribution source: simpler, but a single source can materialize many pattern-keyed arrays and exceed the available gap before the next checkpoint.
  • Estimate entirely from model topology: useful later for proactive UX, but current evidence is calibrated on one topology and cannot safely cover every calculation family.
  • Log every reactive completion: produces high overhead and unusable volume; count every event but log bounded memory bands.
  • Read RSS only: misses other processes and cgroup pressure. Combine cheap RSS sampling with periodic cgroup measurements.
  • Worker recycling alone: releases retained allocator memory only after a completed request and cannot stop an in-flight OOM.
  • Special resource-abort rollback: unnecessary initially. The existing rollback recomputes only guards plus explicitly configured eager outputs; the interface configures no eager outputs. Preserve its graph invariants and collect evidence before changing it.
  • Persist or evict calculation state first: potentially larger optimizations, but materially more invasive than establishing observability and a safety boundary.

7. Constitutional notes

The library remains the owner of generic reactive-engine behavior, satisfying interface constitution §1.3. The interface owns cgroup policy, deployment configuration, logging, and presentation. Infrastructure code stays in the adapter/project layers and does not introduce Django imports into domain or application layers, satisfying §1.1. The library framework layer does not import core or API modules. No constitutional amendment is required.

8. Approved calibration decisions

  • Initial adaptive sampling uses 16-slot sampling away from the limit, per-slot sampling within 256 MiB, and 128 MiB high-water logging bands.
  • Cgroup OOM and OOM-kill counter monitoring ships in the first implementation because it provides kernel evidence when a killed worker cannot emit a completion log.
