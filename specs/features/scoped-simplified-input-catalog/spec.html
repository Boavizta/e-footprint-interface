Scoped simplified-input catalog

REFACTO · Planning kickoff · 8 October 2026 · Interface-owned

This working set captures an authorized planning handoff. The implementation scope and API are proposals for review, not an approved plan. Read the self-contained context and audit before running spec-plan. No application implementation is authorized by this document.

Problem

Narrow interactions such as opening one bookmark or refreshing one selected field currently evaluate every constructor field in the model to build a simplified-input catalog. Ordinary structural changes also build a catalog when no saved or pending field settings require reconciliation. This adds measurable server work on large models.

Catalog construction accounted for about 18% of a 5,002-object edit-panel view in a local in-memory benchmark. A scoped prototype reduced catalog-only work substantially, but hydration and other request costs remain. These results establish an opportunity, not a guaranteed browser speedup.

Desired outcome

Reduce unnecessary catalog work where justified while preserving simplified-input eligibility, required selections, cross-object dependencies, bookmark state, rendering, validation, and persistence behavior. The same model and request must retain the same accepted result and error behavior.

Candidate scope to decide in planning

  • Avoid catalog construction during structural reconciliation with no retained or pending field settings.
  • Share scoped catalog construction for narrow readers, including required dependent closure.
  • Keep complete discovery for Configure and initially retain existing write-path catalog behavior, except for an independently justified empty-settings shortcut.

The context brief audits each caller and distinguishes low-cost opportunities from changes with a larger validation burden. Planning should select the smallest useful delivery rather than assume all candidates are required.

Constraints and non-goals

  • Reuse one domain eligibility/dependency contract. Preserve transitive ineligibility and cross-owner links.
  • Retain strategy-provided field owners; do not restore Storage-specific logic in generic builders.
  • Preserve fresh accepted-state error restoration and validation of retained help-only settings.
  • No UI behavior, JSON schema, model calculations, or library API changes are intended.
  • Partial model hydration, persistent catalog caches, and stored metadata indexes are outside this kickoff.

Success criteria for the eventual approved scope

  • Scoped readers produce the same field/bookmark contexts and errors as the complete-catalog path.
  • Cross-object chains and unsupported required descendants retain current eligibility and selection behavior.
  • If included, the empty-settings shortcut preserves structural persistence and rollback while avoiding catalog work.
  • Bounded benchmarks demonstrate savings on large models and report catalog-only and request-level costs separately.
  • Configure and broad selections retain their complete behavior without a material unexplained performance regression.

Use context.md for source entry points, existing tests, measured evidence, complexity estimates, and open planning decisions.
