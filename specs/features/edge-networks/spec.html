Edge wireless networks — interface

Status: Spec — under review · 2026-11-02 · Spec 2 of 2 in the edge-networks feature roadmap.

Dependency. This feature cannot start until the library feature (e-footprint/specs/features/edge-networks/spec.html) has been implemented: the three object types, their technology defaults, docstrings and parameter descriptions all come from the library. Plan against the implemented library, not against its spec.

1. Problem and audience

Once the library models wireless IoT links, interface users still cannot reach them: there is no way to give an edge device a radio, to say how often it sends and how much, to declare the gateway on site, or to see the gateway and the operator network in the results. The primary audience is the non-technical product person who models an IoT fleet by clicking, and the industrial user who wants the technology comparison without writing Python.

AudienceOutcome
Non-technical product person Picks a technology from a short list, sets how many messages per hour and how big they are, and gets a footprint. Never sees a transmit power unless they open the advanced values.
Industrial user, edge mode Adds the on-site gateway to the fleet group with a count, compares LoRaWAN against NB-IoT, sees the gateway as its own line in the results.
Hardware-aware engineer Overrides any default with a measured value and its source, as for every other input.

Why now. The library spec ships the objects; the interface is where most users meet them. The interface already has every mechanic needed: component accordions on edge devices, component-need accordions on device needs, group membership with counts, weekly-pattern builders, sources on every value, and per-object results lines. This feature adds object types to those mechanics, not new mechanics.

Scope tradeoffs taken.

  • Defaults materialize on save, not live in the form. Creating a network interface asks for a name and a technology only. The technology's sourced defaults appear in the card and edit panel once the component is created, where any of them can be overridden. This avoids client-side prefill machinery for a form that is filled once per device, and matches how the rest of the interface edits defaults.
  • Advanced values collapsed. The edit panel shows technology, gateway and the fabrication footprint up front; the radio physics (powers, bitrate, frame sizes, sync period, hops, error rate, operator shares) sit in a collapsed "Advanced" group so the primary audience is not confronted with them.
  • Gateway control follows the technology. For NB-IoT and SIGFOX the gateway control is hidden with a one-line explanation, the disabled-instead-of-error rule; the library guard remains the backstop for hand-crafted submissions.
  • No new column, no new widget. The gateway is an "Add edge gateway" button in the Infrastructure column next to edge devices and groups; it joins groups through the existing membership controls and shows up in the existing results surfaces.
  • No starter example in this iteration (open question 2).

Unverified frequency assumptions. IoT fleet modeling is a stated mission audience but there is no usage measurement; the design keeps the per-model effort at three objects (interface, messaging need, gateway) and assumes one technology per device.

2. Success criteria

  1. Add a network interface. From an edge device's components, the user adds a "Network interface", gives it a name and picks one of the six technologies. After saving, the component card shows the technology, and its edit panel shows every default with its source, grouped with the physics collapsed. Overriding a value keeps the existing source and confidence conventions.
  2. Choose a gateway. The interface's edit panel offers existing edge gateways in a select (none required). For NB-IoT and SIGFOX the control is hidden and a short line explains that the operator network is charged automatically. Changing the technology on edit shows or hides the control accordingly.
  3. Add a messaging need. From a recurrent edge device need whose device has a network interface, the user adds a "Messaging need" targeting that interface with a weekly messages-per-hour pattern (existing weekly pattern builder) and a payload size. Saving recalculates and patches the canvas in place like any component need.
  4. Add an edge gateway. In edge mode, the Infrastructure column has "Add edge gateway". The form asks for a name, power, fabrication footprint and lifespan with defaults and sources, and offers the existing group membership controls with counts. The gateway card lists the interfaces that use it and the groups it belongs to; a group panel lists gateways beside devices with editable counts.
  5. Results. The gateway is its own node in the Sankey and its own line in the system breakdown and source table, never folded into devices. The interface appears in its device's component breakdown. The audit drill-down explains the operator share and the three energy terms through the library's existing explainability.
  6. Guards. Deleting a gateway that interfaces still link to, or a gateway referenced by a group, is refused with the existing explanation pattern. Library errors (lifespan shorter than usage span, an operator-side link) are shown as the server renders them.
  7. Persistence. Download and upload round-trip models with the three new object types. Models saved before this feature load unchanged.
  8. Onboarding copy. Canvas help and tooltips describe the three new object types in the interface's writing style; the edge section of the build-a-model journey mentions them.
  9. Gates. Unit, integration and Jest suites pass; one E2E flow covers add interface, add messaging need, add gateway, see results; the PyPI dependency is restored before merge; changelog entry.

3. Scope

Capability-level only. Wrapper classes, form configuration keys, templates and endpoints belong in plan.html, written in the spec-plan stage.
In scope
  • Network interface as a selectable component type on edge devices built from components, with a technology choice and collapsed advanced values.
  • Gateway select on the interface, hidden for operator-side technologies.
  • Messaging need as a selectable component-need type, with weekly messages-per-hour and payload size.
  • Edge gateway as an Infrastructure object in edge mode, with group membership and counts.
  • Gateway and interface in the Sankey, breakdown, source table and audit drill-down through existing mechanisms.
  • Delete guards and server-rendered library errors.
  • Save/load round trip and the one-line canvas help, tooltips and journey mention.
  • One E2E flow, plus unit and integration coverage of the new wrappers and forms.
Out of scope (this iteration)
  • Network interfaces on edge computers and edge appliances (component-less device types). Their component lists are internal; adding a radio to them is a follow-up once the component-built device path has shipped.
  • Live prefill of defaults when the technology changes in an open form (defaults appear after save).
  • A starter example and guided-tour step for IoT fleets (open question 2).
  • Simplified-workspace fields for the new objects (open question 3).
  • A gateway-by-device breakdown view beyond the Sankey split.
  • A LoRaWAN spreading-factor selector (library open question 2).

5. Constraints

  • Constitution. The library is the domain truth: no modeling logic in the interface, including the technology defaults (read from the library). HTMX-first: hiding the gateway control on technology change reuses the existing dynamic-form dependency mechanism or a server re-render, not a client data layer. PyPI dependency restored before merge; changelog entry; no Django model change expected.
  • Dict relationships. Gateways join groups through the existing weighted-dict membership mechanism; the dict-relationship registry must resolve a gateway to the group's device-counts attribute through the library's widened parent type (see dict-based relationships).
  • Object descriptions come from the library's docstrings and parameter descriptions; the interface adds only labels, category placement and constraint messages.
  • Persistence. Saved-state export and import follow the existing JSON round trip; a model saved before this feature must load unchanged (see architecture/persistence.html).
  • Design docs. The build-a-model journey's edge section and the writing-style guide govern copy.
  • Owning pages: architecture/forms-and-relationships.html, architecture/rendering.html, architecture/persistence.html, design/journeys/build-a-model.html.

6. Open questions

  1. Where the gateway lives in the canvas. Recommendation: a fourth purple button in the Infrastructure column, cards listed with edge devices (the library lists the gateway under the existing "Edge devices" category). Alternative: its own list header. Decide at plan time if the column gets crowded.
  2. Starter example. A "LoRaWAN sensor fleet" example would make the feature discoverable to the primary audience at low cost (one JSON file in the example picker). Include in this iteration, or follow up?
  3. Simplified workspace. Should messages per hour and payload size be exposed as simplified inputs for the focused editor, or stay in the full panel only? Recommendation: full panel only in this iteration.
  4. Edge computer and edge appliance. Confirm that giving those device types a radio is a follow-up (their components are internal today).
