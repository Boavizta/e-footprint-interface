Plan · approved scope · 2026-10-06

Derived optional quantity controls

This plan is the approved scope for the follow-up feature; task review precedes implementation. The existing simplified-inputs plan documents the shipped behavior.

1. Follow the interactions

File links above identify existing code. e-footprint-interface owns this feature; the library owns the parameter contract and its description.

1.1 · Model contract

Annotation lookup · Shared count type · Core constructors · Builder constructors

fixed_nb_of_instances permits a quantity or EmptyExplainableObject; an empty value has no usable unit. Define a small InputUnit metadata value and one shared annotated quantity alias, then use that quantity member in ServerBase, Server, GPUServer, Storage, and the two builder constructors that redeclare the parameter. The builders retain their existing | None; the metadata attaches only to the quantity, without repeating the unit in each declaration. The server's conditional_list_values still restricts autoscaling and serverless to empty.

Proposed annotation in efootprint/core/hardware/hardware_base.py and its constructor consumers:

InstanceCountQuantity = Annotated[ExplainableQuantity, InputUnit(u.concurrent)]
# ServerBase, Server, GPUServer, Storage:
fixed_nb_of_instances: InstanceCountQuantity | EmptyExplainableObject = None
# Builder overrides also retain: | None

Keep get_init_signature_params() returning ordinary resolved types for existing callers. A focused expected-unit lookup in efootprint/utils/tools.py uses a unit-bearing class.default_values[param] first; otherwise it reads get_type_hints(..., include_extras=True) and finds InputUnit on the quantity member of the union. An EmptyExplainableObject class default is not a unit source, despite its neutral unit property. Existing parameter descriptions remain the contextual tooltip source under doc-as-code; this feature adds no instance-specific help text.

1.2 · Open a normal or simplified form

Generator · UI config · plain normal template · optional normal template · simplified dispatcher · plain simplified partial · optional simplified partial

generate_dynamic_form() already detects allows_empty from the constructor union and derives empty-only controller values from conditional_list_values. Set input_type to optional_explainable_quantity for those quantities and keep explainable_quantity for ordinary ones. The existing normal-form dynamic_form_field.html router selects the matching template by input type, so it needs no new branch. Rename the derived controller keys for the empty state rather than automatic sizing. When touching the controller derivation, add a short code comment explaining that empty-only locking currently handles direct depends_on paths; dotted paths need separate handling.

Keep explainable_quantity.html focused on the numeric input and its initial required state. Its new optional sibling wraps and includes that input with a generic “Leave unset” switch. In simplified editing, editor.html selects a plain numeric partial or an optional wrapper that includes the same numeric partial. Switch markup and controller data live only in the optional templates. The existing field tooltip beside the label explains what unset means for that parameter. A saved number opens with the switch off; an empty value opens with it on. Non-optional quantities keep a required numeric input.

Remove auto_sizing, empty_unit, and “Leave blank for automatic sizing” from field_ui_config.json. The generator and test form-data builder use the expected-unit lookup for every optional quantity: a quantity in the class default supplies the unit even when the saved value is empty; otherwise InputUnit supplies it. If neither exists, fail instead of silently using dimensionless. A nonempty saved value still displays its actual unit. step and hide_unit remain ordinary presentation choices, unrelated to optionality.

1.3 · Switch between unset and specified values

normal optional template · simplified optional template · optional quantity script · simplified save script · ModelingObject validation

The shared optional_quantity.js handler already clears the number when the switch is on, requires a number when it is off, and forces the empty state for controller values restricted to empty. Keep that behavior, rename its auto_* data attributes and switch action to empty-state terms, and remove the instance-specific help-text branch. Its existing change event carries empty rather than automatic; simplified_inputs.js saves when the user switches to empty. The existing form_data_parser.py distinguishes blank from 0 using the same union type. Do not add a second tag, parser branch, or persistence format.

ModelingObject currently checks dimensionality against a quantity in default_values, but returns before unit and sign checks for a union annotation. For an optional quantity, resolve the expected unit from the class's quantity default or InputUnit before returning for an empty input. If neither source exists, raise a descriptive TypeError naming the class and parameter, whether the input is empty or nonempty. An empty value then bypasses numerical checks; a nonempty quantity receives the existing dimensionality and sign checks. Ordinary quantity parameters continue to use default_values, without unit annotations added to them. The normal and simplified edit paths continue to save an EmptyExplainableObject for blank and a quantity for a fixed number.

3. Review decision

Unit metadata is a fallback only where no quantity class default supplies a unit; annotating every quantity would duplicate the existing default-based contract and complicate parameters whose units vary by concrete class. Resolve the unit before accepting an empty optional value so missing declarations fail at validation rather than surfacing later in rendering or computation. Keep EmptyExplainableObject unit-neutral: its current to(), copy, and JSON paths do not carry a unit. The optional-value control uses only generic wording and behavior; the existing field tooltip supplies parameter-specific meaning. A future empty-capable quantity therefore needs no new switch copy or field UI tag.
