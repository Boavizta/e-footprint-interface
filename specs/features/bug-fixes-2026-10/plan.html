1 · How the interface reads a modeling object's containers

Every wrapper derives its containers from the library's raw efootprint_contextual_modeling_obj_containers. list_containers_and_attr_name_in_list_container classifies an entry as a list membership by indexing the container's constructor signature, and dict_containers_and_attr_name_in_dict_container reads dict_container. Three consumers trust the answer: mirrored_cards places cards; check_can_delete chooses between "Yes, delete" and the blocking modal; _delete chooses between unlinking from containers and self_delete(). The properties miss three library facts: detached wrappers stay in the raw list (Task 4); builders create some relationships in after_init, outside the constructor (Tasks 6, 8); a pattern references its journeys without owning them (Task 11). Each mismatch surfaces as a crash, a false removal target or a delete that only unlinks. Owning page: forms and relationships.

Task 4 · Deleting a recurrent need: ignore detached contextual containers

CONFIRMEDe-footprint-interfaceeasy diagnostic · GitHub #151

Files modeling_object_web.py · test_views_deletion.py · test_modeling_object_web.py · CHANGELOG.md

Symptom
Deleting a RecurrentServerNeed or RecurrentEdgeProcess shows 'NoneType' object has no attribute 'efootprint_class'; the need is deleted but its card stays until reload.
Root cause, followed on the Industrial IoT example

The data structure. In the library, a link "object A's attribute points to object B" is a ContextualModelingObjectAttribute wrapper. A stores the wrapper as its attribute value, and the wrapper's constructor also appends itself to B's contextual_modeling_obj_containers list (constructor → add_to_contextual_modeling_obj_containers). That list is B's reverse index: "who points at me, and through which attribute". Each wrapper records the pointing object in modeling_obj_container and the attribute name in attr_name_in_mod_obj_container.

Unlinking never removes a wrapper from that list. set_modeling_obj_container(None, None) only sets both fields to None (:80-81). The wrapper stays in B's list, detached. Library readers filter detached wrappers out, for example modeling_obj_containers keeps only entries whose container is not None. The interface reads the raw list through efootprint_contextual_modeling_obj_containers, because it needs each entry's attribute name, and does not filter.

The example. In iot_industrial.json, the edge function Sensor-records-and-uploads-readings lists two recurrent edge processes in recurrent_edge_device_needs: Measure-temperature-and-vibration (the one the user deletes) and its sibling Keep-recent-readings-on-the-sensor. Both, and the server need Upload-sensor-readings, have edge_device = Factory-sensor (:196, :230). After loading, the two reverse lists that matter hold only live wrappers (probe output, wrapper ids shortened):

Probe output before the delete; container is the wrapper's modeling_obj_container

Factory-sensor.contextual_modeling_obj_containers
  w1  container=Measure-temperature-and-vibration    attr=edge_device
  w2  container=Keep-recent-readings-on-the-sensor   attr=edge_device
  w3  container=Upload-sensor-readings               attr=edge_device

Keep-recent-readings-on-the-sensor.contextual_modeling_obj_containers
  w4  container=Sensor-records-and-uploads-readings  attr=recurrent_edge_device_needs

What "Yes, delete" does to them.

  1. The view runs DeleteObjectUseCase.execute. The need is held in a list (its edge function's), so _delete takes the list branch: it builds {"recurrent_edge_device_needs": ["Keep-recent-readings-on-the-sensor"]} (:200-205) and calls edit_with_cascade_cleanup on the edge function.
  2. The library replaces the whole list. ModelingUpdate.apply_changes calls replace_in_mod_obj_container_without_recomputation on the old list, which detaches it and attaches the new one. Detaching a list detaches every entry, so w4 on the sibling becomes detached. The new list holds a fresh wrapper w5 for the sibling, appended to the sibling's list by the wrapper constructor.
  3. EditService sees that the deleted need left the function's accordion children and has no live container left, so it calls self_delete(). The library's self_delete detaches every link the deleted need owns, including its edge_device wrapper w1, which still sits in Factory-sensor's list.

Probe output after _delete, same in-memory model

Factory-sensor.contextual_modeling_obj_containers
  w1  container=None                                 attr=None      <- detached in step 3
  w2  container=Keep-recent-readings-on-the-sensor   attr=edge_device
  w3  container=Upload-sensor-readings               attr=edge_device
Factory-sensor.modeling_obj_containers (library, filtered)
  [Keep-recent-readings-on-the-sensor, Upload-sensor-readings]

Keep-recent-readings-on-the-sensor.contextual_modeling_obj_containers
  w4  container=None                                 attr=None      <- detached in step 2
  w5  container=Sensor-records-and-uploads-readings  attr=recurrent_edge_device_needs

The library's own view is correct: the deleted need no longer points at Factory-sensor. Only the raw lists carry the leftovers.

Where it crashes: the response render, on the same model.

  1. The view hands the output to present_deleted_object, which takes the list-deletion branch and renders the top-parent card of the edited function, the edge usage journey, without reloading the model.
  2. That card renders the surviving sibling need. Its links_to (used to draw the leader line) walks its direct object attributes, here only edge_device, and asks Factory-sensor's mirrored_cards.
  3. mirrored_cards reads list_containers_and_attr_name_in_list_container, which loops over the raw list. Its first entry is w1; container is None, and container.efootprint_class raises AttributeError: 'NoneType' object has no attribute 'efootprint_class' (reproduced by the probe).
  4. @render_exception_modal_if_error turns that into the reported modal. The deletion itself is already persisted, but no card swap is sent, and the modal's hyperscript cannot remove a nested card (Task 3), so the stale card stays.

Why it looks intermittent. A reload deserializes the saved model, which creates only live wrappers, so the canvas is right again. Job and step deletions never reach this path: JobWeb.links_to returns a web_id without calling mirrored_cards. A need without a sibling sharing its edge device renders nothing that asks the device for its cards. Any other mutation that detaches a wrapper and then re-renders cards in the same request hits the same line, such as relinking a need's edge_device. The sibling's own detached w4 would crash any caller of the sibling's mirrored_cards the same way.

The reporter located the error in the presenter. The presenter is only the caller; the fault is the unfiltered read in the domain wrapper.

Fix
efootprint_contextual_modeling_obj_containers returns only entries whose modeling_obj_container is not None. Both container properties read through it, so w1 and w4 are skipped and the dict property's implicit guard becomes explicit too. This also fixes the latent same crash after an edge_device relink.
Tests
View: iot Upload-sensor-readings and Measure-temperature-and-vibration deletions return 200, no exception modal, top-parent OOB swap present, deleted id absent, sibling present, session updated. This introduces the iot loader that Tasks 8, 11 and 3 reuse. Domain unit: both container properties ignore a detached entry; mirrored_cards does not raise.
Flags
Once shipped, nested-child deletions surface Task 3's hyperscript "is null" console error, which the crash masked today.

Task 5 · Round daily chart emissions to significant figures

CONFIRMEDe-footprint-interfaceeasy diagnostic · GitHub #146, helps #106

Files model_web_utils.py · unit tests · test_modeling_integration.py · layers-and-wrappers.html (optional)

Symptom
The cumulative chart ends at 9.54 kt while the Sankey shows 9.55 kt; small categories show 0 in tooltips.
Root cause
np.round(daily, rounding_depth) is a fixed step of 1e-5 display units (10 kg at kt). Since 479e9a7f converts to the display unit before rounding, the step grows with the model total. Sub-step categories vanish and periodic daily values repeat the same signed error every day, so the drift grows linearly (+16.6 t simulated at the reporter's scale). Reporter's hypothesis held; the drift can go either way.
Fix
Per-value 6-significant-figure rounding, vectorized; unit, payload shape and JS unchanged. Rename rounding_depth to sig_figs and update the docstring.

model_builder/domain/entities/web_core/model_web_utils.py Proposed tail of to_rounded_daily_values (illustrative)

magnitude = np.floor(np.log10(np.abs(daily), where=daily != 0, out=np.zeros_like(daily)))
scale = 10.0 ** (sig_figs - 1 - magnitude)
return (np.round(daily * scale) / scale).tolist()
Tests

Beside test_system_emissions: ≈4,748-day kt regression sums to total_footprint within 1e-5, small category > 0. Settled · flags
