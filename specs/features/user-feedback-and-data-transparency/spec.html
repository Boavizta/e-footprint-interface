User feedback and data transparency

Status: Spec — approved · 2026-09-07

1. Problem and audience

  • People using the public e-footprint interface lack an easy, contextual way to report a bug or share feedback, especially when the current modeling file would help reproduce a problem.
  • Users cannot currently see how long their modeling data remains available, what the browser cookie contains, or how close their workspace is to the server's JSON storage limit. The resulting uncertainty can reduce trust and make size-limit failures feel abrupt.
  • This affects all users, with greater impact on non-technical users who should not need to understand Django sessions, Redis, PostgreSQL, or GitHub workflows.
  • The feature is worth solving now because the application already has layered, time-limited persistence and computes the saved payload size; exposing those facts turns existing safeguards into understandable user assurances.

2. Success criteria

  • From the main modeling experience, a user can choose to report a bug or send general feedback without searching for contact information.
  • A bug report can be opened as a prefilled issue in the e-footprint-interface GitHub repository, with an optional, explicit workflow to download and manually attach the current modeling JSON.
  • A user who cannot or does not want to attach the file on GitHub can open a prefilled email to vincent.villet@publicissapient.com and is reminded to attach the downloaded file manually.
  • No modeling data, traceback, user-authored text, or JSON content is placed in a public issue URL, email URL, application log, or third-party service automatically.
  • Before sharing a modeling file, the user is told that it may contain their entered data and that GitHub issues and their attachments are normally public.
  • A user can open a concise data-and-privacy explanation that distinguishes the browser session identifier, the fast cache, and the recovery cache, including the current retention period and what resets it.
  • The interface accurately states that the modeling data is protected in transit by HTTPS. It only claims encryption at rest when that protection has been verified for the deployed Redis and PostgreSQL services.
  • The data-and-privacy explanation identifies Boavizta as the service operator and Clever Cloud as the hosting provider and, where applicable, data processor. It states that the application containers and the PostgreSQL and Redis add-ons are hosted in Paris, and publishes vincent.villet@publicissapient.com as the security contact.
  • Recovery availability in the live application is distinguished from residual presence in daily PostgreSQL operational backups retained for seven days. The interface only describes those backup files as encrypted after that separate guarantee is verified.
  • The detailed explanation says that backups are observed to run overnight. Short recovery periods reduce the chance that a modeling is present at snapshot time but never guarantee exclusion: any modeling still stored when a backup runs may be captured and retained with that backup for seven days.
  • The data-and-privacy panel shows the latest successfully saved workspace size and configured shared workspace limit in human-readable units. It clearly presents 50 MB as a capacity policy of the shared public instance, not a limitation of the e-footprint model or file format, and points advanced users to configurable self-hosting for larger workspaces. The value refreshes after successful persistence without requiring an extra full serialization; the interface does not expose “JSON” as an implementation concept.
  • A user can choose a recovery-cache retention period of 1, 3, 6, or 12 hours, or any whole number of days from 1 through 14, capped by the configured session-cookie lifetime. The default remains 12 hours, while the short choices give privacy-sensitive users deliberate alternatives. The choice applies to all modelings in the session and is remembered for that session.
  • Changing recovery retention immediately updates the expiry of recoverable data already stored for the session, and future saves use the chosen duration.
  • Expired recovery-cache rows and expired server-side Django sessions are removed from the live PostgreSQL database by scheduled cleanup independently of whether a user tries to read them; the privacy explanation states the maximum cleanup lag.
  • Below 80% of the shared size limit, no persistent quota indicator competes with modeling controls. At or above 80%, a concise warning appears near the modeling canvas, states the current size and limit, links to the detailed panel, and remains actionable before a save is rejected; the existing authoritative size guard remains unchanged.

3. Scope

Capability-level only. Implementation details and operational recommendations are captured in the reviewed implementation plan.
In scope
  • A discoverable support entry point for bug reports and general feedback.
  • Prefilled GitHub and email handoffs, with optional modeling-file download and clear manual-attachment guidance.
  • A data-and-privacy explanation covering the cookie, fast cache, recovery cache, retention triggers, session loss, operational-backup rotation, transport protection, and verified at-rest protection.
  • Verified operator disclosures: Boavizta's role, Clever Cloud's hosting/subprocessor role, Paris hosting for the application containers and both data stores, and a clearly labeled security contact.
  • An on-demand saved-workspace-size detail in the privacy panel, plus a contextual warning only from 80% of the shared storage budget.
  • Session-scoped recovery-retention choices from one hour to at most the session-cookie lifetime, applied across the whole workspace, with 12 hours as the default.
  • Bounded scheduled deletion of expired recovery-cache rows and expired server-side session rows from the live PostgreSQL database.
  • The same truthful reporting guidance on the existing recovery experience, where a broken modeling can already be downloaded safely.
  • Desktop and best-effort mobile access through the existing global navigation and modeling-toolbar menus.
Out of scope (this iteration)
  • An in-application ticket database, feedback inbox, account system, or automated email delivery.
  • Automatic upload of a modeling file to GitHub, email, or another storage service.
  • Collecting personal information, analytics, model contents, or diagnostics in the background.
  • User control over the fast-cache duration; it remains an operator-level performance setting.
  • Changing the shared JSON limit or redefining which serialized representation the limit measures.
  • Guaranteeing restoration after the browser cookie is deleted, the session expires, a cache entry is evicted early, or infrastructure is unavailable.

5. Constraints

  • The feature remains session-driven and does not introduce user accounts or persistent per-user libraries, in line with mission.md.
  • Feedback handoff and privacy controls stay in the Django/HTMX adapter layer. No presentation or session concern enters the domain or application layers, preserving constitution §1.1.
  • The existing repository remains the authority for cache persistence and payload-budget enforcement, preserving constitution §1.2.
  • Wording must describe observed guarantees, not infrastructure assumptions. In particular, Redis eviction is policy-dependent rather than FIFO, and encryption at rest is deployment-dependent.
  • The selected recovery duration describes availability through the live application, not immediate physical erasure from provider backups. PostgreSQL backups run daily and are retained for seven days; any encryption statement about the backup files still requires provider confirmation.
  • Backup timing is operational and may vary. The interface may describe it as an observed overnight schedule, but must not claim that choosing six hours or another short duration guarantees exclusion from backups.
  • The 50 MB production value is a configurable shared-instance capacity policy. Copy must not imply an inherent e-footprint model or JSON-format ceiling, and should identify self-hosting as the path for appropriately provisioned larger workloads.
  • The compact recovery representation may require lazy recomputation after the fast copy expires; the interface should explain this as a possible slower first load, not as data loss.
  • The retention selector cannot offer a duration longer than the configured session-cookie age.
  • JSON sharing is always opt-in and manual. The application must not place the file or user-authored content in query parameters.
