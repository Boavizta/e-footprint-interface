User feedback and data transparency — Implementation plan

Status: Plan — approved · 2026-09-07 · Spec: approved spec

1. Approach

Respect the existing chrome hierarchy instead of adding two more toolbar buttons. On desktop, replace the top navbar's generic “View on GitHub” link with the more useful global “Feedback” entry. Its ordinary href opens a standalone support route from pages without a modeling side panel (including Home and recovery); progressive enhancement opens the same content in the existing builder side panel when that target is present. Put “Data & privacy” inside the modeling-toolbar Help menu, because its explanation and retention preference belong to the current browser session. Keep detailed workspace size inside that panel; only show a canvas-adjacent warning from 80% of the shared limit. On mobile, where the global navbar is hidden, Feedback joins the existing toolbar burger while Data & privacy remains under Help.

The feedback UI collects no free-form text. It gives the user an explicit “Download my current modeling to include” action, explains that the file must be reviewed and attached manually, then separately opens a prefilled GitHub issue or email draft. This avoids implying that the application can upload an attachment and keeps user-authored content out of URLs. Existing dead-state recovery retains its raw, hydration-free downloads and receives the same truthful attachment guidance.

Keep all support, disclosure, and retention behavior in adapters. The session repository continues to own cache TTLs, but resolves the PostgreSQL recovery timeout from a validated session-level preference. Changing the preference updates only the PostgreSQL expiry for every occupied workspace slot; future saves use the same value. The existing workspace index supplies the last-saved canonical byte sizes, so size presentation never hydrates or reserializes a modeling. A shared response helper refreshes the conditional warning after every persistence boundary that can change the indexed size.

Make data minimization operational rather than merely logical. A supervised Django maintenance worker removes expired django_cache recovery rows and expired django_session rows immediately at startup and hourly thereafter. The browser cookie remains only an opaque session identifier; small server-side workspace indexes and preferences expire with the session. PostgreSQL live storage is confirmed encrypted at rest, while its daily seven-day backups are confirmed unencrypted at rest unless Clever Cloud's custom encryption option is activated; user-facing copy is derived from explicit deployment settings and must state the deployed truth.

Reporting flow
  1. A thin GET view renders one reusable support partial with “bug” and “feedback” choices. A non-HTMX request wraps it as a standalone page; a small delegated progressive-enhancement module intercepts the global navbar link only when the builder's #sidePanel exists and loads the partial there.
  2. The panel contains no free-form text field. GitHub and email own authored report content; their prefilled templates contain prompts only.
  3. “Download my current modeling to include” is a separate ordinary download link using the existing active-model export. Nearby copy states that the file may contain business data, must be reviewed, and must be attached manually. No automatic download/open sequence or new file format is introduced.
  4. The GitHub action opens the e-footprint-interface issue form with a type-appropriate title and prompt-only body. The email fallback opens a prefilled mailto: subject/body with the same manual-attachment instruction. Neither URL contains report text, model content, a traceback, or an exception message.
  5. General feedback uses the same panel and download action; attaching a modeling remains an explicit user choice rather than a bug-only checkbox.
  6. The dead-state recovery page reuses the same URL builders and adds the email fallback and public-attachment warning, while keeping its raw download path independent of ModelWeb.
Data, size, and retention flow
  1. A shared adapter helper creates a presentation-only data-status object: session-cookie age, Redis TTL, selected PostgreSQL TTL, summed saved bytes, maximum bytes, ratio, caution state, and explicit operator disclosures. Those disclosures cover Boavizta, Clever Cloud, Paris hosting for containers and both data stores, daily PostgreSQL backups with seven-day rotation, the separately configured backup-encryption state, and the security contact.
  2. The helper reads stored sizes from WorkspaceIndex. It never calls ModelWeb.to_json(); the repository already records the authoritative canonical size after every successful save.
  3. The initial builder render includes a stable workspace-storage-status region above the canvas that is empty below 80% and becomes a concise warning at or above 80%. A shared adapter helper appends its out-of-band replacement after successful CRUD, result-materialization, and Sankey persistence. Import, reset, add, and remove paths already re-render the builder and therefore receive fresh initial context.
  4. The card-order autosave remains a lightweight fetch. After a successful save, its script asks the dedicated status GET endpoint to replace only #workspace-storage-status; it never fetches or serializes either modeling.
  5. The privacy side panel always renders the detailed human-readable saved size and limit from the same status object, without calling the payload “JSON”. Wording describes TTLs as “after the latest save or retention change”: cache reads do not renew expiry, while a deliberate retention change does. It labels 50 MB as the configurable capacity policy of this shared public deployment and links larger-workspace needs to self-hosting rather than implying a format limitation.
  6. Backup detail says that snapshots are observed overnight and retained for seven days. It may explain that short recovery durations reduce capture likelihood, but never infer exclusion from a six-hour or other TTL: a modeling present at the actual snapshot time can be included, and the provider schedule may vary.
  7. A POST endpoint accepts only the closed set of recovery periods: 1, 3, 6, and 12 hours, followed by every whole-day duration from 1 through 14 days. The minimum is 3,600 seconds (one hour), matching the hot-cache duration; the default remains 43,200 seconds (12 hours); and options above settings.SESSION_COOKIE_AGE are never offered or accepted (Django's current default is 1,209,600 seconds / 14 days). The selected value lives in the session as workspace-level UI policy and is not exported inside a modeling file.
  8. On a valid change, the adapter calls the PostgreSQL DatabaseCache.touch() path for each occupied slot, setting expires = now + selected duration without selecting or rewriting its stored value. It persists the preference for future writes even if a key vanished concurrently, and reports whether all or only the still-recoverable entries were updated.
  9. Subsequent repository writes use the validated session preference for the PostgreSQL timeout. Redis remains an operator-level fixed TTL.
  10. A Django management command deletes rows whose expires timestamp has passed from the dedicated django_cache table and clears expired rows from django_session through the configured session backend. In production, the existing Supervisor process manager runs it as a lightweight worker: immediately on startup, then every hour. This bounds residual presence in the live database to one additional hour during normal service operation.

3. Cross-cutting concerns

  • Tests: unit-test allowed retention values, session-age capping, size aggregation, the exact 80% boundary, deployment-disclosure context, URL encoding, and absence of model/user/exception-message content from outbound URLs. Django adapter/database tests cover expiry touch across one and two slots, partial failure, future writes, removal of expired cache and session rows while preserving live rows, and OOB status responses at each persistence boundary. Jest covers progressive enhancement and the card-order status refresh using real rendered fixtures. One E2E flow covers Help discoverability, retention persistence, absence of a quota indicator below 80%, warning appearance/refresh at 80%, operator/region/security disclosures, the explicit download action, and GitHub/email links. Recovery-page tests remain hydration-free. The Django-free tests/integration/ suite is not used for this adapter-only feature.
  • Migrations: no Django model or JSON-schema migration. The new session key is additive, defaults to 12 hours when absent, accepts one hour as its privacy-minimizing value, and must not enter exported interface_config.
  • Security and privacy: treat the session cookie as an opaque locator, not encryption. Never embed a traceback, exception message, user-authored text, or model content in external URLs. The support UI never stores report text. Use noopener noreferrer on new tabs and a CSRF-protected POST for retention changes.
  • Accessibility: the storage warning and detailed progress need textual values; color is supplementary. Side-panel forms need associated labels, keyboard operation, and an aria-live confirmation.
  • Performance: at the application level, size presentation is O(number of slots) over existing integer metadata and retention change performs one expiry touch per occupied slot. With the current two-slot cap both are bounded constant-time operations, apart from cache/database round trips. Neither path may hydrate, materialize, or serialize a modeling. Card-order refresh adds one metadata-only partial request after an infrequent drag save.
  • Operational validation: before copy is finalized, verify production Redis at-rest encryption and TLS (or an equivalent encrypted private path), maxmemory, maxmemory-policy, cache hit rate, evictions, rejected writes, memory headroom, and presence of the supervised cleanup worker in deployment logs. The application containers, PostgreSQL, and Redis are confirmed in Paris; live PostgreSQL encryption at rest is confirmed; PostgreSQL backups are confirmed daily with seven-day rotation and confirmed not encrypted at rest today; and the security contact is vincent.villet@publicissapient.com. Clever Cloud offers custom backup encryption for €100, whose one-off/recurring nature and exact activation scope still need confirmation. Task generation must place a final Clever Cloud harmonization task after functional work: reconcile settings and copy with the provider's final written state for Redis encryption/TLS/backups and PostgreSQL backup encryption.
  • Docs: update the persistence/security sections of specs/architecture.md and the save/load design journey. This is a new user-controlled persistence policy and should not be left only in feature history.

4. Risks

  • False encryption assurance: the application performs no payload encryption of its own. Live PostgreSQL encryption is confirmed, but its seven-day backups are confirmed unencrypted at rest today; Redis facts remain pending. Mitigation: represent each store and backup layer separately in deployment settings, render only configured facts, and update the configuration after Clever Cloud's custom backup encryption is actually activated—not merely quoted. See Clever Cloud's encryption-at-rest documentation.
  • GitHub attachments are not URL-prefillable: a new-issue URL can fill title/body but cannot safely attach the current file. Mitigation: make download/review/manual attachment explicit and keep the email fallback equally clear.
  • TTL semantics become misleading: cache expiry resets on writes, not reads; the retention POST deliberately resets the PostgreSQL expiry from the time of that change. Mitigation: consistently say “after the latest save or retention change”, test the copy inputs against configured values, and avoid “active session” wording.
  • Backup timing creates a false safe window: observed PostgreSQL backups run overnight, but their exact time varies and a six-hour recovery copy can still overlap a snapshot after late-evening use. Mitigation: describe short TTLs as reducing likelihood only, and base the guarantee on actual presence at snapshot time plus seven-day backup rotation.
  • Large workspaces displace several casual workspaces: production Redis is currently capped at 128 MB while the production shared JSON limit is 50 MB. Most expected workspaces are below 3 MB, but one near-limit canonical snapshot can evict several of them and Redis serialization overhead is not represented by the JSON byte count. Mitigation: monitor payload distribution, Redis memory, evictions, hits, and misses; increase Redis capacity if normal traffic produces cold-cache churn.
  • Retention preference outlives or underlives data: the two-week cookie can disappear before a server cache entry, leaving an inaccessible orphan until expiry; eviction can remove data earlier. Mitigation: state “up to”, cap the preference, and explain that clearing cookies or infrastructure eviction can end recovery sooner.
  • Database-cache and session expiry are lazy: Django makes expired cache/session data unusable but does not guarantee prompt physical row deletion without maintenance. Mitigation: run and monitor the hourly supervised purge worker for both tables, describe logical expiry separately from the maximum one-hour live-table cleanup lag during normal service operation, and disclose the independent seven-day backup rotation. Concurrent workers during scaling or zero-downtime deployment are safe because deletion is idempotent; log only counts and duration, never cache keys, session keys, or payloads.
  • Touch failure creates a false success: cache operations currently swallow backend errors. Mitigation: make the retention-change path observe per-key touch results and report partial/unavailable updates rather than confirming blindly.
  • Stale size display: result materialization, Sankey changes, and card-order autosave can change canonical size outside standard CRUD. Mitigation: centralize the OOB partial append for HTMX persistence responses, explicitly refresh after the existing card-order fetch, and cover the enumerated boundaries with tests.
  • Global Feedback target is absent: the navbar also renders on Home and the standalone recovery page, where the builder's #sidePanel does not exist. Mitigation: use a real standalone support URL as the baseline and intercept it only when the builder target is present.
  • Public disclosure: a modeling JSON may contain names, comments, sources, and business assumptions. Mitigation: no automatic upload, an explicit opt-in, a public-issue warning, and a reminder to review the file.

5. Alternatives considered

  • Submit feedback through an application form: rejected for this iteration because it requires storage, abuse controls, personal-data handling, and an operator inbox. External handoff is lighter and more transparent.
  • Automatically upload JSON to GitHub or temporary object storage: rejected because issue URLs cannot carry attachments and a relay service would materially expand the privacy and security surface.
  • Automatically download then open the destination: rejected because browsers may block the second action and the sequence can imply that the file was attached. Keep “Download my current modeling to include” and “Continue on GitHub” / “Use email instead” as explicit separate actions.
  • Collect report text in the application: rejected. Without an application-side submission endpoint the field would be misleading, while copying it into a GitHub or email URL would expand URL exposure and length. Users write their report at the selected destination.
  • Show a permanent size chip in the modeling toolbar: rejected because most expected workspaces are below 3 MB, making a permanent 50 MB implementation limit distracting and potentially anxiety-inducing. Keep detailed size on demand in the privacy panel and surface an actionable canvas warning only from the selected 80% threshold.
  • Present 50 MB as a model-format ceiling: rejected. MAX_PAYLOAD_SIZE_MB is deployment-configurable and exists to protect this shared public instance; larger models can use a suitably provisioned self-hosted e-footprint-interface.
  • Re-serialize on every render: rejected because the authoritative byte count is already stored after persistence; re-serialization would add latency and could materialize or duplicate work.
  • Save recovery retention inside interface_config: rejected because retention is browser-session/workspace policy, not modeling content, and should not silently travel with exported files.
  • Keep Redis retention at 10 minutes: rejected. It needlessly sends a casual returning user through the slower inputs-only recovery path and recomputation after a short pause, even when the 128 MB Redis cache is lightly used.
  • Set Redis retention to one hour: selected. Production uses allkeys-lru, so memory pressure evicts approximately least-recently-used keys rather than blocking all new keys; PostgreSQL remains the recoverable inputs-only fallback. One hour improves the common 10–60 minute return path without promising that Redis will retain a key for the full hour under pressure. Monitor the cumulative evicted_keys counter and hit/miss deltas. See Redis key-eviction documentation.
  • Use Clever Cloud native cron or a separate Clever Task for cleanup: rejected for this iteration. Native cron is unavailable for Docker applications, while a Clever Task has no built-in cron trigger and would add a second application plus an external trigger. The already-deployed Supervisor is the proportional execution boundary; a separately scheduled worker can replace it later if cleanup must continue while all web scalers are stopped.
  • Disable PostgreSQL backups: rejected. Seven-day daily backups support platform recovery and are required by the forthcoming durable shared-model capability, even though that feature remains outside this plan. The proportional target is to encrypt retained backups, not remove them; until activation, the interface must disclose their unencrypted state accurately.

6. Constitutional notes

The plan keeps Django sessions, external URLs, cache TTLs, and templates in adapters, respecting constitution §1.1. It retains ISystemRepository as the modeling persistence boundary (§1.2) and does not change e-footprint's modeling or serialization truth (§1.3). HTMX renders the side panels and OOB size update; any JavaScript is limited to the browser-required “download, then open external destination” enhancement (§1.4). No constitutional amendment is required.

7. Remaining operational gate

  • No implementation-design question blocks task generation. Provider facts intentionally remain a final operational gate: confirm whether Clever Cloud's €100 PostgreSQL-backup encryption is one-off or recurring and when it is active; obtain the pending Redis at-rest, TLS/private-path, and backup answers; then harmonize production settings and copy as the final task.
