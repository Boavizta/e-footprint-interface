analyse-results Analysis Prospective — not built

⚠ Prospective journey — target-state design, not the deployed app.
This journey is the normative design for the results-analysis feature (spec + plan in specs/features/results-analysis/). The faithful description of today's results panel remains view-results — nothing in the deployed app looks like this yet. When the feature ships, this journey supersedes view-results Phases B–C and this banner comes off. Decisions here were ratified in the 2026-07-03 design discussion (attributed-footprints serialization contract, Sankey-card pattern reuse).

The model computes — now build the analysis, don't just read a chart. analyse-results turns the Results panel's two fixed CO2 charts into a stack of configurable emission chart cards: each card picks its angle (the same "analyse by" mental model as the Sankey — categories, hardware, journeys, steps, jobs…), its mode (per period or cumulative) and its refinements (granularity, lifecycle phase, small-contributor folding), and carries its own commentary. Success isn't "a chart appeared" — it's an ordered, annotated stack of views that reads as a standalone analysis and travels with the model file.

Prospective — grounded in view-results (the current panel and its Sankey card pattern, which this design generalizes to charts) and the library's pull-based results contract (serialized per-source hourly footprints; serialized daily attributed footprints for every other object — the companion library feature). Tracing any number to its inputs stays the job of audit-a-result; this journey designs the seams that lead there. Code-level pointers for agents in Implementation pointers at the foot.

2

One card, any angle — the Sankey's mental model, on a time axis

A card's settings mirror the Sankey's: the same class groups answer "analyse by what?", gated on what exists in the model. The chart re-renders on every change (server computes the series, browser draws), and the settings persist on the card. Per-period and cumulative are modes of one card, not different chart types — so any angle can be read either way.

Break down byObject category (default) · Hardware · Usage patterns · Usage journeys · Steps / Functions · Jobs / component needs · Countries — the Sankey's "Analyse by" groups; only present classes offered.
Phase handlingThe category view keeps today's split Fabrication / Usage legend. Object-level views sum phases per object by default — the Lifecycle phase select refines — so series counts stay readable.
Sums to totalWhen an angle doesn't cover every flow (e.g. device fabrication isn't a job's), an explicit grey "Not attributable to …" remainder series keeps every stack equal to the system total. A silently short stack reads as a bug.
AggregationThe slider folds sub-threshold contributors into "Other (n)" — same control, same semantics as the Sankey card.
LegendCapsules toggle a series; hover offers Only to isolate one — today's legend behavior, kept.
Day granularityThe data contract already stores daily series; a Day option in Granularity is a later UI addition, not a data change.

3

Stack as many views as the analysis needs

An analysis is rarely one chart. Add another chart appends an independent card — same defaults, own settings — and the ↑ ↓ controls order the stack. This is the Sankey's proven "stack analysis views" pattern, extended with ordering because a report reads top to bottom. Everything persists: close and reopen Results, reload the session, export and re-import the model — the stack comes back as left.

Add / delete＋ Add another chart appends with defaults; ✕ removes after the same confirm pattern as a Sankey card.
Reorder↑ ↓ move a card one slot — deliberate, HTMX-simple, no drag machinery.
PersistenceCard list, order, settings, titles and commentary live in the model file's UI config — they survive reload and travel with export / import, exactly like Sankey cards.
Charts + SankeysThe Impact repartition Sankey section keeps its own card stack below, unchanged — charts answer "how much, when"; Sankeys answer "through what".

4

Annotate — the stack becomes the report

A chart shows what; the commentary says so what. With titles, ordering and per-card commentary, the Results panel is the analysis report — no separate document to maintain, nothing to drift. Because it lives in the model file's UI config, sharing the .json shares the full annotated analysis: the recipient opens the model and reads the same story over live, auditable numbers.

Plain textCommentary is plain text this iteration — rendered escaped, edited inline, saved on blur.
Config-only saveSaving commentary (or a title) never recomputes the model and never reloads the chart — metadata semantics, like source edits.
Report = the stackTitle + chart + commentary, in card order. The export / import round-trip carries it whole.
Report outputA print / PDF / share rendering of the stack is deliberately out of this iteration — the panel is the report for now.
Rich textMarkdown or formatting in commentary — deferred until plain text proves limiting.

5

Every series is an auditable model value

Because chart series come from the library's attributed footprints — real calculated attributes with full ancestry — the chart is the natural entry point into explainability. This iteration designs the seams and ships the tooltip; the destinations are their own prospective journeys — impact-on-canvas (the object's impact panel) and audit-a-result — target (the rebuilt audit mode).

TooltipObject name · value · share of the period total — precomputed server-side, like Sankey tooltips.
Identity in payloadEvery series carries its object's id — the load-bearing seam that makes click-through possible at all (the Sankey payload lacks it today).
Click → objectClicking a series opens the object's side panel on its impact — lands with impact-on-canvas.
Click → auditFrom the tooltip's "Attributed … footprint ↗" into the rebuilt audit mode — lands with audit-a-result — target.

Decisions taken

DecisionWhy / why-not-X
One configurable card type replaces the two fixed charts; the default stack reproduces today's read.Continuity for every existing user (zero-config parity) while unlocking the analysis system beneath. A zoo of chart types would multiply UI and code paths; per-period vs cumulative is a mode of one card, not a different artefact.
Chart angles mirror the Sankey's "Analyse by" class groups, gated on present classes.One mental model for "angle of analysis" across all of Results. The groups already exist in the library and the gating logic is proven on the Sankey card.
Series come from the library's attributed footprints — the interface never computes attribution.The library is the domain truth (constitution §1.3). Chart values, Sankey values and the system total agree by construction because they fold the same attribution; the interface-side per-category aggregation path retires.
Non-covering angles show an explicit "Not attributable to …" remainder series.Some flows can't belong to some classes (device fabrication is nobody's job). A stack that silently sums below the headline total reads as a bug and erodes trust; an explicit grey remainder keeps every chart conservative and honest.
The category view keeps the split Fabrication / Usage legend; object-level views sum phases by default, refined by the Lifecycle phase select.Category view = today's read, preserved exactly. Object views can carry dozens of series; doubling each into two phases would drown the signal — the phase select recovers the split on demand, mirroring the Sankey's phase filter.
Cards persist in the model file's UI config (settings, order, titles, commentary).An analysis angle and its narrative are viewing choices, not model facts — same posture as Sankey cards. Riding the existing UI-config round-trip means share-by-file works with zero new persistence machinery.
Commentary is plain text on a card; the report is the ordered stack.A separate document model (report builder, rich text) would drift from the live charts and triple the scope. Title + chart + commentary in reading order already is a report — and it stays live over the model.
Reorder via ↑ ↓ buttons, not drag-and-drop.HTMX-first, minimize JS (constitution §1.4): two buttons are one POST each; drag needs a library, ghost states and touch handling for a rare, deliberate action.
Month / Year granularity now; Day designed-for but deferred.The serialized data is daily, so Day is purely a UI toggle later — no data or contract change. Shipping it now adds legend/axis complexity without a validated need.

Today's anchors (what this replaces / mirrors)
Fixed charts: result/result_graph.html + result_charts esbuild bundle (chart.js, config.js, legend.js — split-capsule legend, timeseries_utils.js rollups), fed by window.emissions = ModelWeb.system_emissions → EmissionsCalculationService.calculate_daily_emissions (daily per category — to retire). Card pattern to mirror: adapters/views/sankey_views.py (sankey_cards / sankey_form / sankey_diagram / sankey_delete_card), templates result/sankey_{section,card,diagram}.html, persistence repository.interface_config["sankey_diagrams"] + persist_to_cache().
Data (library, companion feature)
Impact sources: serialized hourly energy_footprint / instances_fabrication_footprint pairs (pull-based contract) — daily reduction computed on read. Other objects: serialized daily attributed footprint projections per phase (@lazy_attribute(serialize=True) over a lazy hourly @computed_attribute). Category view = category grouping over source pairs (System.energy_footprints / fabrication_footprints). The Sankey's impact_repartition_matrix is untouched.
Target shape (draft — see plan.html)
Chart-card routes/views/templates mirroring the Sankey set; per-card series payload with efootprint_id on every series (the audit seam) + precomputed tooltips; server-side rollup to the requested granularity so payloads stay small; config persisted under interface_config["result_charts"] (list — id, title, breakdown, mode, granularity, phase, aggregation, commentary, order). Chart.js stays the renderer.
