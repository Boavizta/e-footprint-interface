Start a modeling with AI WebBeta

A fresh start from a description. Instead of picking an example or an empty canvas, the user writes what their digital service does — its usages, their volumes, the infrastructure behind them — and gets back a complete, computable web modeling in the active slot, built from one AI request. Success isn't "the AI answered": it's an ordinary modeling the user goes on to review and edit with the normal editor, the generation's details shown once and then gone. The feature is Beta and only exists on instances configured for it.

Today's shipped behaviour, faithful to the deployed app. Drawn from the two AI side panels, the Modeling actions menu and the example picker, the two AI views (start and generate) and the browser and narrative tests of the bootstrap. Code-level pointers are collected for agents in Implementation pointers at the foot of the page. The modeling the user then edits is the build-a-model loop.

2

Confirm replacing the active modeling

Starting with AI discards the active modeling immediately, not when a generation succeeds — so the question spells out the consequence of every later exit. It is the same guard as the app's other replacing actions (Reset, picking an example, opening a file), with its own wording.

Asked only if neededThe question appears only when the active canvas holds at least one object. Starting over an empty modeling goes straight to screen 3.
CancelNothing is sent: the modeling, its canvas and the current view stay exactly as they were.
OKThe active modeling is replaced by an empty one, its interface settings dropped. The other modeling is untouched.

The description panel

The guidance asks for the three things a modeling needs — usages, how often they happen, the infrastructure — and for volumes per usage journey, users kept apart from visits. 4

Build my modeling — one request

Submitting sends one request to the AI provider, with the description and nothing else. While it runs, the page offers no other action: a second click cannot send a second request, and the user cannot close the panel or switch modeling halfway. The wait ends in one of two screens: the panel again with an error (screen 5), or the generated modeling with its summary (screen 6).

Locked pageEvery enabled button is disabled until the answer arrives, then restored. Buttons that were already disabled stay so.
Nothing saved yetThe slot still holds the empty modeling. It is replaced only once the generated modeling has been built, prepared like an imported file and found computable — in one save.

5

Refused — the panel, the description kept, one message

Whatever fails, nothing reaches the modeling: the slot keeps the empty one, and the user's text is never thrown away, so editing the description and retrying is one click. The message names the kind of failure, not its technical detail — an answer the AI got wrong can contain generated text, which is never shown.

Provider failure"The AI provider could not complete the request. You can try again." — unreachable, timed out, or an unfinished answer.
Unbuildable answer"The AI answer could not be built into a modeling. Review your description and try again."
Not computable"The generated modeling could not be computed. Review your description and try again."
Memory limit"The generated modeling could not be computed within this instance's memory limit." — when the final save's computation runs out of memory.
Incomplete"The generated modeling is incomplete. Describe its usages and infrastructure, then try again." — it built, but is not complete enough to compute results.
Size limit"The generated modeling exceeds this workspace's size limit. Try a smaller description."
Slot no longer empty"Start with AI again to replace this modeling." — the active modeling gained content since Start with AI; a generation never overwrites work. No request is sent.
Blank description"Describe your system before building your modeling." — only spaces were submitted. No request is sent.

6

The generated modeling and its summary

The modeling is already saved in the active slot: complete, computable, the Results bar available. The summary is a one-time read: it tells the user the modeling is a starting point to review, points at the three places where a description is most often wrong — time spent, volumes, infrastructure — and reports what the call cost and what the app changed in the AI's answer to make it fit.

Call estimateThe cost comes in US dollars with the date of its rate card, plus the cached-input caveat. The impact is the parent model's EcoLogits estimate, often a range. Either reads "Cost estimate unavailable" / "Impact estimate unavailable" when it cannot be computed — the modeling is kept anyway.
Web + edge checksAfter a Web + edge generation, four checks follow the web ones: Deployments, Devices per group, Device characteristics and Server calls. The canvas shows the edge devices, groups and usage patterns, with Edge modeling on.
Changes made to the AI answerEach value the app replaced to match its catalogs — a network, a device, a provider, a cloud instance, an AI model, an object name, a comment it could not attach — and, after a Web + edge generation, a usage cut at the editor's limit, a device written as a sub-group and moved, or a device no deployment runs, left out of the footprint; each as kind: requested → used (how). Shown only when there is one.
Ignored answer fieldsFields of the AI's answer the app does not know, dropped rather than failing the run. Shown only when there is one.
Your descriptionFolded by default; opened, it shows the text exactly as sent, selectable so it can be copied and kept.
Comments on valuesValues the AI set from the description carry a comment, visible in the ordinary edit panels; everything else is a library default.
Results closedThe Results panel is not opened for the user; the bar is available once they want it.

7

Close — an ordinary modeling

From here the user is on the build-a-model loop: open a card, check the assumptions the checklist pointed at, edit, look at results, export. The generated modeling has no special status — it is saved, exported and compared like any other.

Summary gone for goodThere is no way to reopen the summary. Opening an edit panel replaces it, and reloading the page drops it too.
Not saved with the modelingNeither the description nor the estimates are kept in the session, the saved modeling or an exported file — hence the panel's advice to save the description.
Other modeling untouchedWith two modelings open, the other tab's modeling is exactly as it was before Start with AI.
Start againStart with AI again replaces this modeling, through the same confirmation (screen 2).

Decisions taken

DecisionWhy / why-not-X
The AI starts a modeling; it never edits one.Start with AI replaces the active modeling with an empty one, and a generation goes on only while that modeling is still empty. Why-not-merge into existing work: a generated graph mixed with the user's objects would be impossible to review, and a generation must never overwrite work.
The active modeling is emptied at the start, and the confirmation says so.The question names every later exit — closing the panel, a failed generation — so the user decides once, knowing the outcome. It asks only when there is something to lose, like the app's other replacing actions.
Only a complete, computable modeling is installed; anything else is refused in the panel.A half-built or uncomputable modeling would be a worse start than the empty canvas. The refusal keeps the description, so retrying costs one edit and one click; the message names the kind of failure, never generated text.
One request, the whole page locked while it runs.Each call has a cost and an impact the panel announces; a double click must not pay twice, and the modeling must not change under a running generation.
Cost and impact are stated before and after the call.The panel gives the indicative cost and impact up front, the summary the call's own estimate — consistent with the app's purpose of making digital impact visible, including its own.
The summary is shown once and kept nowhere.The description and the answer are not logged or stored, in the session, the saved modeling or an export. The panel tells the user to save the description if they want it, rather than the app keeping it for them.
The result is an ordinary modeling, reviewed in the normal editor.Why-not-a-special-review-mode: the editor already shows every value with its source and comment. The checklist points at the inputs most worth checking; comments on values say what came from the description.
The entry is absent, not disabled, where the feature is not configured.The app's disabled-with-a-reason rule guides the user toward an unblocking step. Here there is none — it depends on the instance, not on the modeling — so the entry is simply not offered.
⌗ Implementation pointers for agents — routes, views, templates, the confirmation and the tests

Where the functionality above lives in code. Start with AI bootstrap · Fresh AI bootstrap and active slot · Examples and onboarding.

Availability
adapters/ai_provider.py::is_available — AI_BOOTSTRAP_ENABLED and a MISTRAL_API_KEY. Exposed to templates as AI_BOOTSTRAP_AVAILABLE by adapters/context_processors.py::ai_bootstrap; the picker card is appended by adapters/presenters/example_picker_presenter.py::build_picker_groups to the scratch group. Both views raise 404 when unavailable.
Entry points and confirmation (Phase A)
Menu: upload_download_reboot_model_tooltips.html (data-ai-bootstrap-entry="toolbar"); picker: onboarding/template_picker.html (data-ai-bootstrap-entry="picker"). Both hx-post start-ai-bootstrap/ → #main-content-block and carry data-confirm-when-model-not-empty, read by the body-level htmx:confirm listener in theme/static/scripts/model_builder_main.js (native window.confirm, only when the active canvas has a .model-builder-card). First-run tour suppression: theme/static/scripts/onboarding_first_run.js ([data-ai-bootstrap-panel]).
Start (screen 3)
adapters/views/views_ai_bootstrap.py::start_ai_bootstrap — empties interface_config of the active repository, loads get_example_system_data(SCRATCH_ID) through load_system_into_session, renders the builder with ai_panel="input" and show_example_picker=False. model_builder_main.html includes side_panels/ai_bootstrap_input.html (header "Start with AI · Beta") into #sidePanel already open; both AI panels extend side_panel_structure.html (close: warnBeforeClosingSidePanel() → closeAndEmptySidePanel(); the textarea never sets formModified).
Generate (screens 4–6)
views_ai_bootstrap.py::generate_ai_bootstrap: is_empty_model guard → blank guard → application/ai_bootstrap/service.py::generate with complete_mistral (one call, ProviderError on any failure) → system_to_json → prepare_system_for_session → SystemValidationService.validate_for_computation → persist_to_cache (the one save) → application/ai_bootstrap/metrics.py::estimate_call (optional, after the save). Every refusal goes through _input_response (ai_error, ai_prompt). The form's hx-disabled-elt="button:not(:disabled)" is what locks the page. Summary: side_panels/ai_bootstrap_summary.html (header "Your starting modeling is ready", no save button); substitutions are Resolutions with how != "exact" (catalogs.py, dsl.py), ignored fields from dsl.py::validate_tolerating_extras.
Tests
Narrative: tests/narratives/test_ai_bootstrap.py. Browser: tests/e2e/test_ai_bootstrap.py (cancel sends nothing, the lock during the request, the summary gone after close / edit / reload, picker entry and tour suppression, return to Modeling from Simplified inputs).
