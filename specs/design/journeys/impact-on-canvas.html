impact-on-canvas Web + edge Prospective — not built

⚠ Prospective journey — target-state design, not the deployed app.
Normative design for the future impact-on-canvas feature (spec to come in specs/features/impact-on-canvas/). Today, no impact number appears anywhere in the building view — object cards show a name, and calculated values hide in an edit-panel accordion (build-a-model / audit-a-result stay the faithful descriptions). At ship time this journey folds into build-a-model (cards, panel) and the banner comes off. Decisions ratified in the 2026-07-03 design discussion.

Today the model and its footprint live in separate rooms: you build on the canvas, then open Results to learn what it weighs. impact-on-canvas puts the weight where the work is: every object card carries its footprint badge, a system total rides the Results bar, and the edit panel leads with the object's impact — updated after every edit, so modeling gets the feedback loop of a live instrument. Success is a modeler who can say, mid-edit, "that change moved this object from 0.4 to 1.1 tonnes and the system by 8%" — without leaving the canvas.

Prospective — depends on the library's serialized attributed footprints (every object, not just hardware; the companion library feature) so badge values are read, not recomputed. The badge's deeper story — charts per object, full derivation — belongs to analyse-results and audit-a-result — target; this journey is the canvas seam. Code-level pointers in Implementation pointers.

1

An object's impact is its first-class information

Clicking an object answers "how big is this thing?" before offering the knobs. The impact header reads the object's attributed footprint — the same value its badge, its chart series and its audit view show — so every surface tells one consistent story. For a modeler deciding where to spend effort, the share-of-total is the triage signal the panel never gave.

One number, sharedHeader = the object's attributed footprint over the modeling period — identical source as badges and chart series (the library's persisted results).
Share of totalPercentage + proportion bar against the system total footprint.
Phase splitUsage / Fabrication sub-figures, matching the results legend vocabulary.
Impact sources tooFor hardware (servers, devices, network…) the attributed footprint is its own footprint — same header, no special case for the user.
Not computable yet?While the model can't compute (no usage pattern…), the header shows a dimmed "No impact yet — complete your model" with the live validation reason — the app's disabled-not-errored rule.
⌕ AuditOpens the audit view on this object's page — lands with audit-mode; until then the header links the calculated-attributes accordion (a stopgap that retires into that page).

2

The canvas becomes a heat map of the model

Badges turn the canvas from a wiring diagram into a triage view: the eye finds the heavy objects without opening anything. Values come straight from the persisted attributed footprints — displaying them costs no computation, on any model size.

Badge valueThe object's attributed footprint, period total, compact display unit. Absolute number — the share lives in the tooltip (two numbers on a card is noise).
Total badgeSystem total on the Results bar, always in view — the model's headline without opening Results.
Zero-compute displayBadges are read from the saved model (serialized attributed footprints) — rendering the canvas never triggers computation.
Incomplete modelNo badges while the model can't compute — cards stay clean, the Results bar stays locked with its live reason (disabled-not-errored).
Edge paradigmEdge devices, functions and recurrent needs carry the same badge — attribution covers both paradigms uniformly.
Badge toggleA toolbar switch to hide badges (presentation / screenshot mode) — add if badge noise proves real.

3

Feedback with every save — precise, not wholesale

The instrument only works if it responds. After a save, the system total and the edited object's badge update in the save's own response; badges of other affected objects follow within a beat. Crucially the update is precise: the engine knows exactly which objects' attributions an edit invalidates, so only those badges change — a stable canvas signals "this edit was local", a wide ripple signals "this touched everything".

Total: synchronousThe system total is recomputed as part of every save (the engine's standing guarantee) — the total badge is always current in the save response.
Badges: one beatAffected badges refresh in the save response if the recompute proves cheap, else asynchronously right after with a … pending chip — the library feature's measurement decides the default; the design accommodates both.
PrecisionOnly the dirty objects' badges change (the engine's invalidation is exact). No global shimmer, no full-canvas reload.
Ripple as signalWhich badges move is itself information — the visible blast radius of an edit.
Delta flashA transient +/− delta next to a changed badge ("2.4 t ▲ +0.6") — nice-to-have, add after the base loop proves calm.

Decisions taken

DecisionWhy / why-not-X
Every object shows its attributed footprint — one number reused by badge, impact header, chart series and audit.Consistency builds trust: the same value everywhere, from one source (the library's persisted attributed footprints). Inventing a different "card metric" would create two truths.
The edit panel leads with the impact header; the calculated-attributes accordion is demoted to a stopgap and retires with audit-mode.The panel is an editor — its read-only job ends at the headline (footprint, share, audit entry), and it renders only persisted values so opening it computes nothing. The full attribute list moves to the audit view's Object page (audit-a-result — target); the accordion survives only until that page exists, so the list is never unreachable.
Badges are display-only reads of persisted values; rendering never computes.The canvas renders on every request — it must stay computation-free (the app's binding constraints are store weight and round-trips). Serialized attributed footprints make display a lookup.
Total badge synchronous; attributed badges synchronous-if-cheap, else async with a pending chip — measurement decides.The total is already recomputed on every save (engine guarantee) so it's free to show. Attribution's per-edit cost is real but bounded to the dirty cone; the library feature measures it, and the UI is designed to be correct under either policy rather than betting the edit latency on it.
Precise updates only — affected badges change, others are untouched.Wholesale refresh would flicker the whole canvas on every save and destroy the "ripple as signal" read. The engine's exact invalidation makes precision free.
Badge shows the absolute value; share and phase split live in the tooltip / impact header.One number per card keeps the canvas legible; percent-vs-absolute toggles and split badges were rejected as card-level noise.
No badges while the model isn't computable.Zeros or stale numbers on an incomplete model would be lies; absence + the locked Results bar (with its live reason) already communicates the state — disabled-not-errored, applied to numbers.
⌗ Implementation pointers for agents — prospective: target shape + today's code anchors

Status: prospective. Feature spec to come in specs/features/impact-on-canvas/. Depends on the companion library feature (serialized daily attributed footprints — badge = period sum of those series; for impact sources, of their own serialized footprint pairs).

Today's anchors
Cards: object_cards/* + components/button_card_header.html (name-only today; the ✎ pencil and card chrome live here). Panel: views_edition.py open_edit_object_panel → side_panels/edit/edit_panel__generic.html (impact header slots above the form; calculated_attributes_section.html stays as a stopgap and retires with audit-mode's Object page). Results bar: components/results_bar_button.html (total badge rides this region). OOB machinery for precise patches: oob_regions.py / htmx_presenter.py — the badge updates are new OOB regions keyed by object id.
Update flow (target)
Save → ModelingUpdate eagerly recomputes the system total (existing contract) → response carries OOB swaps: edited card badge + total badge + pending chips on dirty badges. Then either (a) the same response already contains all refreshed badges (eager pull of dirty attributed slots — if the library's per-edit measurement says cheap), or (b) a follow-up hx-get fetches the refreshed badges once the lazy fill lands. The dirty set comes from the engine's invalidation — expose "which object ids' attributed footprints were invalidated" on the update result.
Consistency & gating
Badge visibility gates on the same computability signal as the Results buttons (creation_constraints["__results__"]). Display unit: compact form of the system-wide display unit — shared helper with the results charts.
Supersession
At ship: folds into build-a-model (card anatomy, panel anatomy) — this journey then retires into it rather than living on separately; banner and hub pill come off at that point.
