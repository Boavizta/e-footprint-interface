audit-a-result — target Methodology Prospective — not built

⚠ Prospective journey — target-state design, not the deployed app.
This is the rebuilt audit mode — normative design for the future audit-mode feature (spec to come in specs/features/audit-mode/, after analyse-results and impact-on-canvas). The faithful description of today's audit surfaces remains audit-a-result. At ship time this journey replaces audit-a-result's derivation phases (B–C) — its provenance phase (A · source & confidence, the Sources tab) carries over unchanged — and the pyvis calculus-graph dump retires. Decisions ratified in the 2026-07-03 design discussion.

Every number e-footprint produces can already be traced — the engine records the full derivation of every value. But today that trail is scattered (a formula expander buried in the edit panel, a raw graph dumped in a new tab) and navigating it means bouncing between side panels. audit-a-result — target makes auditing a place: enter from any number on screen, understand one value completely (its meaning, its formula, its cited inputs), walk the derivation with a history you can retrace, and zoom out to the map of how objects feed each other. Success is a reviewer's question answered in seconds: "where does this number come from, and how sure are we?" — at any depth.

Prospective — grounded in audit-a-result (today's surfaces) and the library's explainability machinery: every calculated value carries its ancestry and formula, every calculated attribute has a docstring, the model file persists the values-free calculation graph, and valueless intermediates compute lazily on read. Entry seams from charts are designed in analyse-results; from object cards and the impact header in impact-on-canvas. Code-level pointers in Implementation pointers.

3

Click through the derivation — never lose the thread

Every calculated input variable and every child is a link that navigates the audit surface itself. The breadcrumb is the investigation's memory: where you started, how you got here, one click back to any step. Today the same walk means opening a different object's side panel at every hop and holding the path in your head.

In-place navigationAncestors (upstream) and children (downstream) swap the value card — the surface, breadcrumb and history persist.
History‹ › move through visited values; breadcrumb nodes jump directly. Closing the surface returns to the canvas untouched.
Lazy depthIntermediate values aren't stored — the engine pulls them on demand, computing only the requested value's cone. Depth costs nothing until visited.
Weak links surfaceProvenance chips ride along the walk — a Low confidence or missing source deep in the trail is visible the moment it appears.
Hourly zoomExpanding a timeseries chart to hourly resolution inside the audit view — later; daily covers the audit read.

4

Zoom out — the dependency map

The macro question — "what depends on what in this model?" — doesn't need seven hundred formula nodes; it needs the object-level picture. The Map draws objects and their feed relationships, expands any object into its calculated attributes on click, and focuses on one value's ancestry when you come from the Value view. It replaces the old raw calculus-graph dump — same underlying graph, rendered at the altitude a human can read.

Object altitudeNodes = model objects; an edge = "values of A feed computations of B". Dozens of nodes, not hundreds.
Expand on clickA node unfolds to its calculated attributes; clicking one opens its Value view — Map and Value are two zooms of one surface.
Focus mode⌖ dims all nodes outside the current value's ancestry cone — "what could possibly influence this number" at a glance.
Zero computeRendered from the calculation graph persisted in the model file — no values needed, so the map is instant even before any lazy fill.
RetirementThe pyvis calculus-graph page (new-tab iframe) retires — legacy of the pre-product era, superseded by Value + Map.

Decisions taken

DecisionWhy / why-not-X
Audit is one navigable in-place surface (Value + Map), not side-panel hopping or a new-tab dump.An audit is an investigation — it needs memory (breadcrumb, history) and a stable frame. Panel-bouncing loses the thread; the pyvis tab was a demo-era artefact with no navigation, explicitly not product vision.
The micro view keeps today's formula-expander anatomy and adds the docstring + inline provenance chips.Input variables · formula · children is proven and already served by the library; what readers lacked was the value's meaning (docstrings exist as doc-as-code on every calculated attribute) and seeing the trail's end (source/confidence) without a detour.
One audit affordance (⌕ Audit) on every computed value, everywhere; views addressed by (object, attribute).Discoverability comes from repetition of a single verb, not from one deep menu. Addressability makes every present and future surface (charts, badges, Sankey) a deep link for free.
The macro view is object-level first, attribute-level on expand.Hundreds of slot nodes are noise (the failure mode of the current graph); dozens of object nodes are a map. The full detail remains one expand away, and Focus mode narrows to one value's ancestry.
Drill-down computes lazily; the map renders from the persisted calculation graph.The engine's pull design makes depth free until visited (only the requested cone computes); the values-free topology is already in the model file, so the map needs zero computation ever. Nothing is precomputed for auditing.
Provenance semantics are unchanged; the inline ∑ expander retires into the audit surface.Source/confidence stays metadata on inputs (audit-a-result Phase A carries over verbatim). Keeping a second, reduced derivation surface in the edit panel would drift from the audit view — one home, one click away, instead.
Timeseries render daily-aggregated in audit; hourly zoom deferred.Consistency with Results; daily answers the audit read ("when and how much"). Hourly is reachable later without contract changes since intermediates compute on demand.

Docstrings

Library assets the surface reads
Ancestry/children per value (direct_ancestors_with_id / children, formula tuples on serialized slots); lazy pulls fill valueless intermediates on read (pull-based contract); the values-free calculation graph section of the model JSON (slot-level edges + labels) — group by owning object id for the Map's nodes/edges; provenance (source/confidence/comment) on input values.
Target shape (draft)
Audit surface = in-place overlay like the Results panel (HTMX partials; Value and Map as sub-views); navigation = address stack of (object id, attr) pairs held client-side, each hop one hx-get; Map = server-derived object-graph JSON rendered client-side (renderer TBD at plan stage — keep it dependency-light). Entry points post the address; chart/Sankey payloads must carry object ids (seam noted in analyse-results).
