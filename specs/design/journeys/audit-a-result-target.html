audit-a-result — target Methodology Prospective — not built

⚠ Prospective journey — target-state design, not the deployed app.
This is the rebuilt audit mode — normative design for the future audit-mode feature (spec to come in specs/features/audit-mode/, after analyse-results and impact-on-canvas; its Contribution lens is a second increment, audit-attribution). The faithful description of today's audit surfaces remains audit-a-result. At ship time this journey replaces audit-a-result's derivation phases (B–C) — its provenance phase (A · source & confidence, the Sources tab) carries over unchanged — the pyvis calculus-graph dump retires, and the edit panel's Calculated attributes accordion retires into this view's Object page (the panel keeps only the impact header). Decisions ratified in the 2026-07-03 discussion; revised 2026-07-07 (dedicated view; panel keeps footprints only; global map dropped for anchored lenses; calculus vs attribution split into two lenses of one surface).

Every number e-footprint produces can already be traced — the engine records the full derivation of every value. But today that trail is scattered: a formula expander buried in an edit-panel accordion, a raw graph dumped in a new tab, and no place that is the audit. audit-a-result — target makes auditing the third workspace mode — you build on the canvas, read in Results, trace in Audit. One surface: pages (the System's and each object's) list what there is to audit, the Value view explains one number, and two graph lenses answer the two big questions — Influence (what shapes this footprint? — the calculus, upstream) and Contribution (which footprints land on this object, and why? — the attribution, downstream). Success is a reviewer's question answered in seconds, at any depth.

Prospective — grounded in audit-a-result (today's surfaces) and the library's explainability machinery: every calculated value carries its ancestry and formula, every calculated attribute has a docstring, the model file persists the values-free calculation graph, valueless intermediates compute lazily on read, and attribution atoms record how source footprints distribute. Entry seams from charts are designed in analyse-results; from the impact header in impact-on-canvas; the Sankey stays the system-level rendering of the attribution truth this view drills per object. Code-level pointers in Implementation pointers.

Audit is a destination, not a corridor

Build on the canvas, read in Results, trace in Audit — three modes of one workspace. The standalone entry makes the flagship capability visible before a user ever wonders about a specific number; the contextual ⌕ Audit entries on values remain the fast path in. Every entry resolves to an address — an object, optionally an attribute — so the view opens at the right place.

5

Click through the derivation — never lose the thread

Every calculated input variable and every child is a link that navigates the audit view itself. The breadcrumb always shows where you are — System › object › value, at most three nodes — and ‹ › replay where you've been, however deep the walk. Crossing into another object's value simply rewrites the middle node; the history keeps the whole investigation retraceable. Today the same walk means opening a different side panel at every hop and holding the path in your head.

Location ≠ historyBreadcrumb = current address (System › object › value), never longer. ‹ › = the visited sequence — a deep walk doesn't grow an unbounded trail.
In-place navigationAncestors (upstream) and children (downstream) swap the value card; crossing objects rewrites the breadcrumb's middle node.
Lazy depthIntermediate values aren't stored — the engine pulls them on demand, computing only the requested value's cone. Depth costs nothing until visited.
Weak links surfaceProvenance chips ride along the walk — a Low confidence or missing source deep in the trail is visible the moment it appears.
Hourly zoomExpanding a timeseries chart to hourly resolution inside the audit view — later; daily covers the audit read.

6

The Influence lens — what shapes this footprint

The macro question, anchored: "which objects' inputs influence this footprint?" For one audited number the answer is small — a handful of objects, each showing which of its inputs participate. This is where non-obvious influences (the country's carbon intensity, a journey's frequency) become visible — the edges the model canvas never draws. One zoom down, the same cone at calculated-attribute level shows how the influence travels.

Objects altitudeNodes = the objects in this footprint's ancestry cone, annotated with their participating inputs; edges = "feeds". Typically 5–15 nodes — read at a glance.
Attribute altitudeThe chip toggle re-renders the cone as the scoped DAG of calculated attributes across those same objects — the spine of the derivation; each object's lateral side-branches are collapsed by default (expandable). Node detail stays in the Value view.
Anchored onlyThere is no whole-model graph — every Influence view belongs to one audited footprint. (The System total's cone is the whole model; its Influence view is the one case that resembles a global map, reached deliberately.)
Zero computeBoth altitudes render from the calculation graph persisted in the model file — structure needs no values; values appear on hover/click via lazy pulls.
ExitsClick an object → its page; click an attribute node → its Value view; × on the lens → back to the Value it came from.
RetirementThe pyvis calculus-graph page (new-tab iframe) retires — legacy of the pre-product era, superseded by this lens.

7

The Contribution lens — why this object carries this weight

The attribution story runs the other way: source footprints distribute down the consumption chain, and an intermediate object's number is the sum of its shares. The Contribution lens makes each share defensible — which source, how much, and why that fraction — and hands off to the calculus story per source. It's the differentiating half of e-footprint's auditability, shipped as its own increment (audit-attribution) on the same surface.

Per-source rowsAmount · share of the object's attributed total · the share's rationale in words (drawn from the attribution's own keys — usage-driven, capacity-driven…).
Loop to calculusEach contribution links to the source footprint's Value view / ◉ Influence — attribution explains the split, calculus defends the number being split.
Lens by natureAttributed footprints offer ◎ Contribution; source footprints offer ◉ Influence — one surface, the audited value picks the lens.
Sankey kinshipThe Sankey remains the system-level rendering of the same attribution truth; this lens is its per-object drill — same atoms, same totals, by construction.
Second incrementShips as audit-attribution, after the core audit-mode (pages · Value · Influence). Until then, attributed Value views show their calculus ancestry only.

Decisions taken

DecisionWhy / why-not-X
Audit is the third workspace mode, with a standalone gated entry beside Results — landing on the System page.Auditability is the product's strongest asset; a capability reachable only by stumbling onto the right icon stays invisible (today's failure). The landing is an index of auditable numbers (total + per-source pairs), because an audit always starts from a number.
No whole-model dependency map.The canvas already renders the model's structure; a global computational graph is anchored to nothing and repeats the pyvis failure one altitude up. The non-obvious edges (carbon intensity, journey frequency…) surface in the anchored Influence lens, where they're readable.
Two lenses on one surface, picked by the audited value's nature: ◉ Influence (upstream calculus) for source footprints, ◎ Contribution (downstream attribution) for attributed footprints.The engine computes two different stories — how a footprint arises, and where it goes — with different directions, data and questions; one "Map" muddled them. But entries, navigation and the Value view are identical, so they're lenses of one mode, not two modes. Delivery splits accordingly: audit-mode (core calculus) then audit-attribution.
The Influence lens is object-altitude first (inputs annotated), scoped-DAG on toggle, lateral branches collapsed.5–15 annotated objects answer "what shapes this number" at a glance; the attribute-level DAG shows the spine of how, with per-object elaboration one expand away and per-node detail in the Value view. Spine over completeness — completeness is what made the old graph unreadable.
The edit panel keeps only the impact header; the Calculated attributes accordion retires into the Object page.The panel is an editor — its read-only job ends at the headline. The surface boundary matches the serialization boundary: the panel renders only persisted values (zero compute on open); the audit view computes on demand, scoped to what's asked.
One surface, one breadcrumb (System › object › value · lens); ‹ › history is separate from location.Pages, Value views and lenses are places in one investigation. A location breadcrumb stays ≤ 4 nodes however deep the walk; history covers retracing.
The Value view keeps today's formula-expander anatomy and adds the docstring + inline provenance chips.Input variables · formula · children is proven and already served by the library; what readers lacked was the value's meaning (docstrings exist as doc-as-code on every calculated attribute) and seeing the trail's end (source/confidence) without a detour.
One ⌕ Audit verb on every computed value; entries are addresses landing at the right place; the pyvis dump retires.Discoverability comes from repetition of a single verb; addressability makes every present and future surface (charts, badges, Sankey) a deep link for free.

Library assets per surface
System / Object pages: serialized footprint slots + calculated_attributes / computed_slots for the row list (intermediates lazy-pulled on page open). Value view: ancestry/children per value (direct_ancestors_with_id / children, formula tuples on serialized slots); lazy pulls fill valueless intermediates. Influence lens: the ancestry cone of one slot from the persisted values-free calculation graph — object altitude = cone grouped by owning object id (leaf ancestors = the participating inputs); attribute altitude = the cone's slot DAG with per-object collapse (collapse rule is a plan-stage decision). Contribution lens: the attribution atoms behind the object's attributed footprint (per-source rows; share rationale from the atoms' chain semantics) — same data the Sankey folds, filtered to one object.

Lens graphs = server-derived JSON rendered client-side (renderer TBD at plan stage — keep it dependency-light). Entry points post an address; chart/Sankey payloads must carry object ids (seam noted in analyse-results).
